## §0 先报两条会改变结论的实测异常

理论框架的 Phase 2 第 1 步要求「分析 `git log --since="3 months ago"` 的文件变更频率，标记热数据（>10 次/月）」。**本仓该信号不可用**，实测证据：

| 信号 | 实测 | 结论 |
| --- | --- | --- |
| `git rev-list --count HEAD` | **57** 个 commit，首 commit `2026-07-25`，单一作者 `孔浩原` | 历史被压扁/重建过，无 3 个月粒度可言 |
| `git log --since="3 months ago" --name-only` | 每个文件计数**恰好为 1** | 等价于「全仓一次写入」，无频率分布 |
| 文件 mtime 分布（10 730 项） | 30 天内 **8 667** / 90 天内 2 059 / 180 天以上 **4** | 批量重写痕迹，mtime 同样被污染 |

**替代口径**：本报告改用**不被时间污染的结构信号** —— require 图的 **fan-in**（入度）做热/温/冷分级（§1.4、§2.1）。依据 5-3-1 §2「热温冷分离」的**语义**（访问频度与共享度），而非其字面实现（git 频率）。

第二条异常：`git fsck` 实测多条 `hash-path mismatch`（对象库损坏）。这直接击穿 5-3-1 §5「渐进式迁移」与 Phase 3「`git mv` 保留历史」的前置条件 —— **当前 `.git` 不可依赖，任何 `git mv` / `git filter-repo` 都必须排在 `.git` 重建之后**（§3.0 第 0 步）。

## §2 架构设计（按 5-3-1 五域模型推导）

### 2.1 五个顶级域（依据 §3「按生命周期/变更频率划分」）

命名取**业务术语**（§3 明确要求，禁技术词），每域标注 §1.4 的热温冷档与实测来源：

| # | 域 | 生命周期职责 | 现状映射（实测落点） | 档位 |
| --- | --- | --- | --- | --- |
| **D1** | **运行时内核**（boot & runtime） | 「平台作为操作系统跑起来」：引导、启动器、Node 运行时、CLI 会话 | L0 `kernel/` + L1 `platform/` + L2 `services/` | 热 |
| **D2** | **业务上下文**（bounded contexts） | 平台对外提供的业务能力，各自内聚一块业务 | `services/backend/src/services/domain/`（**625 文件 / 14+ 上下文**：messaging 52、trajectory 50、project 47、network 43、security 37…）**已存在** | 热/温 |
| **D3** | **共享底座**（shared substrate） | 被大量复用的策略与设施，只被依赖、不反向依赖 | fan-in>30 的 **30 个枢纽**：`utils/dataHome.js`、`constants/serviceDefaults.js`、`flagRegistry`、`formatters`、`tools/_baseTool.js` | 温 |
| **D4** | **交付与接入**（delivery & surfaces） | 面向人的产物与接入面：前端、桌面、手机、拓展、便携包 | L3 `apps/` + L4 `software/` + L5 `extensions/` + `electron/` + `entries/` + `packaging/` | 热/温 |
| **D5** | **工程与档案**（works & archive） | 造它/验它/记它的东西，以及已退役与实验残留 | `scripts/` + `docs/` + `.github/` + `deploy/` + `patches/` + `tests/DEBT.md` + **911 图孤儿** + `18_归档/` | 冷 |

**正交性自证**（§3 要求）：五根判据互不相同且覆盖全仓 —— D1「是否平台自身运行所需」、D2「是否一块可独立演进的业务」、D3「是否被 ≥30 处依赖」、D4「是否面向最终用户的交付物」、D5「是否只在开发/记录期被触达」。一个文件至多命中一域（D3 优先级最高，因它是 §5 的依赖终点）。

### 2.2 每域 3 层（依据 §3「每域按单一维度分层，禁混用」）

| 域 | 第 2 层唯一维度 | 第 3 层唯一维度 | 依据 |
| --- | --- | --- | --- |
| D1 | 抽象层级（boot / launcher / runtime） | 会话形态（cli / gateway / tui） | §3「抽象层级」 |
| D2 | **业务上下文**（messaging / trajectory / …） | 上下文内角色（capability / adapter / store） | §3「DDD Bounded Context」 |
| D3 | 设施类别（config / io / format / policy） | 稳定性档（frozen / stable / evolving） | §3「抽象层级」+ §5「接口稳定」 |
| D4 | 交付形态（web / desktop / mobile / extension） | 版本容器（`v1.2/` 等） | §3「时间/版本容器」+ §4「时间容器」 |
| D5 | 生命周期阶段（build / verify / record / quarantine） | 时间容器（`2026-Q3/`、`<日期>/`） | §4「状态迁移」+ §2「冷数据放深层/隔离存储」 |

**混用禁令自查**：每域第 2 层只用一根轴（D2 全用业务上下文，不掺技术分层；D5 全用工程阶段，不掺语言）——这是 5-3-1 §3 最易违反处，列为 §4 验证清单 C-3 项。

### 2.3 一个功能单元（§3「最小高内聚，含代码/测试/文档」）

以 D2 内一个上下文为模板，**测试共置**（直接治 §1.3「共置率 <1%」这条实测痛点）：

```text
D2/trajectory/                 # 一个业务上下文 = 一个功能单元
  capability/  traceRecorder.js     # 业务逻辑（不 require 任何基础设施）
  adapter/     traceStore.js        # 基础设施适配（唯一允许 require D3 的位置）
  store/       <数据契约>
  traceRecorder.test.js             # 与源同目录（5-3-1 §3 功能单元含测试）
  README.md                         # 单元级说明：谁要 / 为什么 / 怎么验（本仓规则 9 三问）
  khy.module.json                   # 声明所属域、允许依赖的域、fan-in 预算
```

**依赖方向**（§5）：`capability → 无外部依赖`；`adapter → capability + D3`；`D1 → D2 → D3`，`D4 → D1/D2 的公开接口`，**D5 不被任何域依赖**。禁止边：`D3 → D2`（基础设施不得反向知道业务）、任何 `→ D5`。

### 2.4 认知负载验证（§1「任何目录直接子项 5±2，绝不超 7」）—— 诚实结论

复算命令：`git ls-files | awk -F/ '{p=$0; sub(/\/[^\/]*$/,"",p); print p}' | sort | uniq -c`

| 统计 | 值 |
| --- | --- |
| 含被跟踪文件的目录数 | **336** |
| 直接子项 >7（违反 §1） | **118 个（35%）** |
| 直接子项 >9 | 109 个 |
| 直接子项 >50 | **35 个** |
| 仓库根 | **67 项**（Phase 0 清创后；理论值 ≤7） |

**结论必须直说**：把 §1 当成**硬约束**逐目录达标，需要新建 **~118 个中间抽象层目录**，其中根目录这一层**物理上做不到 ≤7**——因为 5-3-1 §5「零破坏/接口稳定」与本仓工具契约互为充分条件冲突：`package.json`、`pyproject.toml`、`pnpm-workspace.yaml`、`.gitignore`、6 个根启动器、`Dockerfile`、`README.md` 必须留在根，仅此已 **15 项**。

故本报告对 §1 采取**分档执行**（这是推导结果，不是回避）：

| 范围 | 目标 | 依据 |
| --- | --- | --- |
| 新建/新改的目录（D2/D3 内部） | **硬约束 ≤7**，超即拆 | §1 原样执行 |
| 存量宽目录（118 个） | **棘轮**：只降不升，按 §2.2 的单一维度逐轮拆 | §5「渐进式迁移」优先于 §1 的字面达标 |
| 仓库根 | 目标 **≤20**（已裁决的 A 档），**不承诺 ≤7** | §5 零破坏约束的直接推论 |

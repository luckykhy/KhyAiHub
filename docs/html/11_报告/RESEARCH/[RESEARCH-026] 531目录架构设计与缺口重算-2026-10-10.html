§0 先报六条改变结论的实测#

0.1 施工方式被一条硬闸改死：单次提交 ≤20 件#

[RESEARCH-025] §0 已实测：pre-commit 的 check-change-safety（SECURITY-001）对
单次提交改动文件数 > 20 判 changed-count-error（error，阻断）；近 4 条历史提交均为 2–4 件。

对本文的影响是全局性的：§5 里 D2–D11 每批要搬几百到两千个文件，「每批一提交」字面不可执行。
⇒ 每批必须实现为按 ≤18 件切片、连续提交，逐片过全闸。
切片器先例：.khyos/tmp/q0-commit.js（NUL + :(literal) pathspec，禁 git add -A / commit -a）。
本文批次表因此是「批 × 切片」两级，不是「批 = 提交」。

0.3 工具位已是符号链接，不是物理目录#

根上 7 个"点目录"里，6 个工具位 + khy-Trajectory 全是符号链接，指向 works/data/：

.codeartsdoer  .cursor  .opencode  .workbuddy  .workbuddy-ai  .zcode  → works/data/<同名>

即 W9′ 走的是「建别名」路线。而 [DESIGN-LAY-008] §22.3 已实测判定：
junction/符号链接在资源管理器仍显示为一个目录条目，不减视觉数。
要让根视觉数下降必须「改指向、不建别名」——即让工具自己写到 works/data/ 下，
或退役工具位。这是 §17.4「终局 10 依赖你用不用那些工具，不依赖施工」的物理根因。

7.4 与并发车道的协调协议（本轮新增，必须遵守）#

实测该车道行为：自行建分支（backup/workspace-20261010 → chore/hygiene-20261010）、
按 ≤20 件/批提交未跟踪文件（快照①~⑥）、
提交信息规范（chore(backup): 快照N <主题>（N 件，仅存在于工作树））。
它是在抢救未入仓的工作，不是在破坏。

规则理由
任何 git 操作前先 git branch --show-current分支一天内换了两次
绝不用 git reset --hard / git checkout <分支> / git stash drop会摧毁工作树里他人未提交改动
我的提交不往它的分支上放批次规划会撞车；要么等它收口，要么请它指定分支
我的批次也按 ≤18 件切片、连续提交与它的规格一致，预跑同一把闸
每批提交前重跑一次守卫树是移动靶，上一轮绿的这一轮可能红

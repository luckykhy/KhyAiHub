[DESIGN-ARCH-203] 智能体统一管理#

定位：在桌面端给出「本机全部 AI 编程智能体」的单一管理入口——一张表列出已发现的所有智能体（含发现但未纳管的），安装/卸载、模型配置、MCP、skill、记忆都在这一个地方管。
不是从零起：仓内已有 khy agent-assets（6 家 × 三类资产读写）、khy tools（4 家便携安装）、externalApps 11 家配置适配器、ccSwitch 卡片矩阵四套皮肉，本文做的是补一个统一入口 + 把纳管面从 6 家扩到用户点名的 9 类 + 目录扫描。
状态：设计（todo）· 待人裁决后落地。本文只做设计，不含实现代码。
上位约束：AGENTS.md 工程规则 1–12；[DESIGN-LAY-005]（层级与落点）；[DESIGN-ARCH-071]（通道选择）；[MGMT-STD-007]（文档命名）。

0. 结论先行#

  1. 一个 service、两条互不重叠的暴露路径，两个前端表面。后端 service（services/domain/agents/agentHub/）与注册表是全功能唯一真源；桌面 Electron 主表面走 CH-2 服务层直调（createRequire 载入 service 模块，与 host/index.ts、keyManager/keyStore.ts 同一条既有通道——桌面端没有登录态、从未调过后端 /api/*，走 HTTP 会每个请求 401）；/api/agent-hub HTTP 命名空间只服务 Web 管理台第二表面（有真实 JWT 登录态，挂 authenticateToken）。两条路径共用同一份 service，不造第二个真源，也不给桌面端硬造一个它没有的 token。
  2. 适配器是唯一的扩展点。每家智能体一个适配器文件；注册表是一张冻结的声明式表，加一家 = 加一个文件 + 加一行，编排层与暴露层零改动。MCP 的跨家读写不新造契约——直接复用 agentAssets 的 tool 类资产（claudeCode.js:405-428 今天就能把 mcp_server 合并进别家 mcpServers 并用目标侧现值填回凭据），本功能只做「发现与呈现」，不做第二套 MCP 形状。
  3. 未知智能体走两条路，都不猜：① 内置登记表（人工增补，条目带证据）；② 目录扫描命中已知指纹才生成候选，纯未知指纹只报「发现未识别项」并给手动登记入口——沿用 mcpEcosystemRegistry.js:300 已立下的「不猜路径」规矩。
  4. 写操作一律干跑优先 + 备份 + 可回滚，但回滚分两类、不共用一份账。安装/卸载/改别家配置默认只出计划不落盘，显式确认后才写。「改别家 live 配置」的回滚 = 从 backups/ 把原文件原子写回，记在 agentHub 自己的备份索引里；它绝不写进共享的 .install-ledger.jsonl——那份账的唯一读者 khy uninstall 会把每条当 khy 自己的安装副作用回滚（cli/handlers/uninstall.js:401-410），而 installLedger.js:67 的 meta 白名单记不下「属于哪个 agent」，串台会让 khy 下次卸载时去删别家工具的配置文件（详见 §6.2 与 §11 R2/R3、§12 R2/R3）。
  5. 不新增任何 CLI 命令。[DESIGN-DELIV-002] §2.3 的任务面棘轮（命令 245 / 别名 591 / handler 155，只降不升）下，新增顶层命令即破闸；本功能的命令面是扩展现有 khy agent-assets 的子命令，零新命令、零新别名、零新 handler 文件。
  6. 模型配置写腿今天只覆盖 9 类中的 5 类，且其中 2 家已有双写者。externalApps 11 家 + ccSwitch/appWriters.js 的 APPS 12 项里没有 qoder / workbuddy / kiro / cursor；本轮不为这 4 家新写后端写器，其 tier 封顶在 assets。更隐蔽的是：claude-code 与 opencode 今天就有两个活着的写者——桌面 agentWriters.ts:191-224 直写 ~/.claude/settings.json 与 ~/.config/opencode/opencode.json，后端 externalApps/*Adapter + ccSwitch/appWriters.js 写同一批文件。新统一页的「改模型」会成为同一文件的第三个写入面，这一点必须在 UI 上显式告知（详见 §2.1 双写者审计与 §12 R5）。

1.4 三条设计原则（从上面两张表推出来的）#

  1. 「未安装」是常态，不是错误。registry.js:94-97 已确立「任何一家探测失败都不影响其余家」；统一表必须把「未检测到」与「已安装」并排显示，并列出检查过的路径——只说「未找到」让用户无从下手（_adapterBase.js:96-106 已实现此契约）。
  2. 一个工具可能有多实例。workbuddy CN / Intl 两套、Qoder IDE / CLI 两套、zcode 桌面端 / CLI 两套，各自有独立数据根。统一表的行粒度是实例（installation），不是品牌。
  3. 「装没装」的判据不能只有一种。本机 9 类里 5 类是便携二进制、1 类 npm 已卸、3 类未装；npm ls -g 只能看到 npm 渠道。探测必须按「PATH 可执行 → 安装候选目录 → 注册表 Uninstall → 用户数据目录 → 运行中进程」五源交叉，任一源命中即报「已检测到」并记录命中源。

两条暴露路径的分工不是偏好，是被现实逼出来的（§12 R1）：

表面通道为什么
桌面 Electron（主表面，用户原话载体）CH-2 服务层直调桌面端没有登录态（App.tsx:149-151 自述「ZCode has no login/welcome gate… LoginPage stays in components/auth for that future entry point」），也从未调用过后端 /api/*（apps/khyos-desktop/src 全量 grep /api/ 只命中一个外部供应商 URL 字符串 keyStore.ts:760）；它的后端集成全是 host 进程内 require（src/host/index.ts:120/164/200）。而 /api/* 挂的 authenticateToken 只认用户 JWT、无回环豁免（middleware/auth.js:175-199：extractBearerToken + authSessionService.authenticateAccessToken，拿不到 token 直接 401）。走 HTTP = 桌面端每个请求 401 = 用户点名的载体开箱即死
Web 管理台（第二表面）CH-4 HTTP /api/agent-hub前端有真实登录态与 Bearer token（api/authedFetch.js 从 useUserStore() 取 token），与既有全部管理页同款

这也修正了第 1 轮 §4.5 的一处错误前提：原文写「Electron 主进程不满足 CH-2 的同一 Node 进程前提」，但本仓早已为关键路径做过相反的裁决——src/host/index.ts:3-4 的文件头明写「通道选择（AGENTS.md 五通道决策矩阵）：host 与 backend 同为 Node 进程语义，用 CH-2 服务直调（运行时 require aiGateway）；main↔host 用 Electron fork IPC」，并实际在 :120/164/200/233/264/325 用 createRequire 载入六个后端模块。keyManager/keyStore.ts likewise（createRequire 载 gateway/providerPresets.js）。故 agentHub 跟随这条既有先例，而不是新开一条 HTTP+JWT 的路——那才需要给桌面端造一个它没有的 token，或给 auth.js 加一个回环豁免（后者是安全模型变更，不在本功能范围）。

关键约束：agentHub 是薄编排层，不重复实现任何一家的磁盘布局知识。凡是 agentAssets 已认的记忆/工具/技能（含 MCP，见 §3.1），agentHub 直接委派；凡是 externalApps 已认的 provider 增删改查，直接委派；凡是 ccSwitch 已认的卡片矩阵，直接委派。这与 marketInstallService.js 的头注释自述「only dispatches」是同一个模式——装进与 khy skill add / khy mcp add 同一个 store，杜绝第二写者。

第 1 轮「两层都要接」的教训仍然有效，且适用范围收窄：installLedger.recordSideEffect 是纯函数（零 IO，:13-17 自述），只调它不落盘 = 台账只在内存。第 1 轮据此要求「必须同时接 ledgerWriter.appendSideEffect」——那条对写共享台账成立（ledgerWriter.js 是共享台账的唯一 IO 边界，:4-9 自述）；但本设计已改为不写共享台账，故 B 类的落盘由 agentHub 自己的 append 完成，ledgerWriter 不再被 agentHub 调用。这条修正同时消解了 R1 的风险（不再有「接了计算层没接落盘层」的中间态），但 R1 的诊断——「零 IO 叶子不能当落盘用」——作为通用教训保留。

卸载的边界：官方卸载通道只删程序、不删用户数据（kiro 官方文档明说「using your operating system's standard application removal process」，trae 本机即是「程序目录已不在、~/.trae 残留至今」的活证）。所以 agentHub 的「卸载」默认只走官方卸载通道 + 摘 PATH/注册表条目，删用户数据目录是单独的、更高一级确认的 W3+ 动作，且必须先把 §6.1 的 losses 清单摊开。

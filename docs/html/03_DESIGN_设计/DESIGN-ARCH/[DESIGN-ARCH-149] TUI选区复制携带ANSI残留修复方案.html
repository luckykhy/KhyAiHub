[DESIGN-ARCH-149] TUI选区复制携带ANSI残留修复方案#

0. 一句话结论#

用户从 TUI 拖选复制出的文本里带着 \x1b[1m、\x1b[38;2;97;175;239m 这类着色转义序列（粘贴后 ESC 字节被接收方丢弃，只剩 [1m、[36m 残骸），病灶是 markdown 渲染层的 ANSI 着色原样进入 _mainContentLines，而 extractText 按原样切片、零剥离；修法是让选区叶子层「列换算跳过序列、产出前剥净 ANSI」两处纯函数级修复，不碰渲染层、不碰剪贴板出口。

环节病灶严重度
复制产出文本夹带 SGR 转义序列，粘贴即乱码主诉
列换算ESC 字节被当可见字符计宽，反色高亮在带色行上与指针错位同族次要

1. 现状实证（file:line 可复核）#

1.1 颜色从哪来：markdown 渲染层#

  • services/backend/src/cli/renderTheme.js:9-10 — c() 懒加载 chalk，真彩输出 ESC[38;2;R;G;Bm。
  • services/backend/src/cli/markdownRenderer.js:68-74 — 着色默认值：
    • mdBold: '#E5C07B' = RGB(229,192,123)；
    • mdListNumber / mdH3 / mdBullet: '#61AFEF' = RGB(97,175,239)。
  • 与用户粘贴残骸逐一吻合：粘贴里的 [38;2;229;192;123m（粗体标题）与 [38;2;97;175;239m（有序列表序号 1. 2.）正是这两个色值经 chalk 输出的 SGR 序列、ESC 字节在粘贴时被丢弃后的残骸。

1.2 带色文本怎么进入复制来源#

  • services/backend/src/cli/tui/ink-components/Transcript.js:33-52 — renderMarkdown 委托 markdownRenderer.renderMarkdownLite，返回已着色的整段字符串。
  • services/backend/src/cli/tui/transcriptLines.js:197,249,255 — buildTranscriptLines 把渲染结果按 cols 折行后逐行 push，行内容含 ANSI。
  • services/backend/src/cli/tui/ink-components/App.js:5925-5943 — _mainContentLines 投影直接消费上述行 ⇒ 投影行数组整体带 ANSI。
  • App.js:6066 — _mainContentLinesRef.current = _mainContentLines，选区层拿到的就是这份。

1.3 复制产出点为什么不干净#

  • App.js:1694-1701 — 松手即定稿：const text = sel.extractText(_mainContentLinesRef.current, finished) → clip.writeClipboard(text)。整条链路唯一的产出点。
  • services/backend/src/cli/tui/selection.js:501-530 — extractText 对行原样 slice(from, to)，无任何 ANSI 处理 ⇒ 剪贴板拿到带 SGR 的文本。
  • services/backend/src/cli/tui/utils/ccClipboard.js — 统一出口只搬运传入文本（:157-191），自身无病；病在来源。

1.4 次要病灶：列换算把 ESC 字节当可见字符#

  • selection.js:148-167 — charColForDisplay 逐字符 visWidth(ch) 计宽换算「显示列 → 字符下标」。ESC（0x1B）、[、数字、m 这些 SGR 组成字节被当作各占 1 列的可见字符参与累计 ⇒ 带色行上，指针显示列 → 原文下标的映射整体后移，反色高亮与取词在带色行上双双偏离指针（与 [DESIGN-ARCH-132] 的锚点漂移不同源、独立存在）。

1.5 对照组：CC 模式为什么没事#

  • services/backend/src/cli/tui/ink-components/ccMessageProjection.js:257,502,848 — CC 模式复制走 extractByAnchors，从 msgTexts（消息原文）取词，不经过屏幕行切片 ⇒ 天然干净。本案只需修 legacy 路径。

1.6 修具已存在，不许另造#

  • services/backend/src/utils/stripAnsi.js — 「剥 ANSI」单一真源，委托 cli/ansiSanitizer.js（完整 CSI/OSC/DCS 覆盖、零依赖、永不抛）。其头部 :12-19 明确记录：旧式 /\x1b\[[0-9;]*m/g 正则实测漏剥 5/6 种形式（冒号真彩、光标模式、清屏、光标移动），且 1m 残骸症状 2026-09-22 已在输出卫生层修过一次 —— 同一症状家族的第二处发病点。

3. 目标形态（组件级契约）#

两处改动都在 selection.js 纯叶子内（零 IO / 不抛 / 不改入参 / 不读 env），App 层零改动：

  1. charColForDisplay(lineText, displayCol)：走字符串时识别 CSI/SGR 序列（\x1b 起头的完整控制序列），序列内字节计宽 0、下标整段跳过。⇒ 带色行上「指针列 → 原文下标」重新对准；纯 ASCII / 纯中文行为逐字节不变（无序列时退化恒等，现有 DC-01~DC-07 断言原样绿）。
  2. extractText(lines, sel)：切片仍在原文（raw 下标）上进行 —— 与 Viewport.sliceLineForSelection 的 raw 下标口径保持同源；产出前对每段 stripAnsi（经 ../../utils/stripAnsi 委托 ansiSanitizer，外裹 fail-soft 保「绝不抛」纪律）。⇒ 剪贴板拿到的是纯文本。

顺序不可颠倒：只做 2 不做 1，会得到「干净但错位」的复制（切片边界仍按「ESC 计宽」的旧口径算）；只做 1 不做 2，复制产物仍带 SGR。

回滚能力走可选参数（undefined → 新行为；显式传旧开关 → 旧行为），不新增 KHY_* env 门 —— 「让功能变正确」不构成用户可见权衡（判据见 check-tui-gates 的门预算棘轮与 selectGates.js:18 注释）。

5. 诚实边界（刻意不纳入）#

  • 不动 markdownRenderer 的着色 —— 屏幕上要颜色，那是显示层职责；病只在「复制产出没剥」。
  • 不动 ccClipboard.js —— 统一出口是搬运工；把剥离塞进去会连带污染 CC 锚点路径提取的原文（原文不该被二次加工），且混淆「提取」与「写出」两层职责。
  • 不动 _fp 指纹逻辑 —— 指纹在按下帧与松手帧之间自洽比较，剥不剥 ANSI 两帧一致即可；改它要重写 R-01~R-16 全套断言，收益为零。
  • 不处理跨软换行多 \n —— selection.js 头部已登记的已知偏差，独立议题。
  • 不碰 [DESIGN-ARCH-132] 的 D-02/D-04 两条红 —— 基线实测 56 条中 54 绿 2 红（§7），那两条是锚点漂移的既有病灶，本案验收只要求不新增失败，不替别的提案收账。

6. 反模式（这条路别走）#

✗ 别做为什么
在 writeClipboard 统一出口里全局剥 ANSI把「提取层」的债记到「写出层」头上；CC 原文路径会被连带加工，违反 P1-1 单一真源的职责边界
内联手写 /\x1b\[[0-9;]*m/g 正则stripAnsi.js:12-19 实测该式漏剥 5/6 种序列形式；仓里已有全量覆盖的 ansiSanitizer，再造一把轮子就是把 2026-09-22 修过的坑再挖开
列换算改成「先 stripAnsi 整行、再按净文本算下标」产出的下标对不上 raw 行，而 Viewport.sliceLineForSelection 高亮切片吃的是 raw 行 ⇒ 反色错得更远。正解是「跳过序列但保留 raw 下标」
为回滚新开 KHY_CLIP_PLAIN 之类的 env 门撞门预算棘轮（check-tui-gates.js:32 MAX_GATES 只降不升）；「让功能变正确」不构成用户可见权衡；且会把纯叶子拖进「读 env」的违约区
把 D-02/D-04 顺手修了两套病灶一套测试，混修后回归无法归因（[DESIGN-ARCH-132] 的账）

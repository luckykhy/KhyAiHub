0. 一句话结论#

khy-os 的需求理解散件齐全、编排缺席：taskScale / intentGate / clarificationCards /
referenceDisambiguation / mathSolvePolicy 五个意图件各自向系统提示词注入指令，互不知晓；
需求五问只活在 CI 存证层（.khy/feedback/），运行时对话管线从不产出可回看、可编辑、
执行时可引用的需求制品；Web 前端把 AskUserQuestion 协议渲染成只读状态文本，
用户只能干看不能答。本方案不新增第五个意图件，而是新增一个聚合前置层
requirementIntakeService（五路裁决一次出、单一指令出口），加一个需求固化制品
.khy/requirements/<id>.md（执行时回灌、收尾时对账），加 Web 端交互式问询卡
（复用 TUI questionCardModel 数据形状）。全部按 PROCESS-008 走 S1 观察者档，
门控 KHY_REQUIREMENT_INTAKE（默认关，置 on 启用）。

1. 需求五问（RUNTIME-008 / 规则 6）#

  1. 谁用？ —— 通过 REPL/TUI 或 Web 端向 khy-os 提需求、希望「一次说清、少来回返工」

的终端用户；以及在长任务执行中途发现「AI 做的不是我说的」而无处修正的用户。
（source: 用户原话「准确的理解用户需求是核心，希望你多调研一下网络资料与开源项目
看看怎么实现的，然后设计一个方案」）

  1. 什么时候用？ —— 用户每轮输入进入 aiChatCore 五步管线的**步骤 2（任务规模识别）

与步骤 3（RAG）之间**：五路意图件聚合裁决一次，之后按裁决结果决定走澄清轮、
直接执行轮还是降级轮。长任务执行中按需回看固化制品（步骤 5 之后）。

  1. 现在的替代做法是什么？ —— 五个意图件各自独立注入（现状即替代做法），

已实测出问题：同一轮可能同时命中「澄清卡指令」与「消歧指令」，模型收到两份
互相竞争的问询指引；且没有任何机制保证模型答完澄清后需求被记住——
多轮之后跑偏只能靠用户重申。（source: 内部盘点纪要 §1「各检测件各自独立注入，
缺一个聚合前置层」）

  1. 成功长什么样？ —— 命令 + 期望输出，见 §7 验收判据 A1–A6。核心一条：

在 REPL 输入「优化一下代码」后，收到的是一张可左右切换的选项卡问询
（优化什么文件 / 什么指标），答完后 REPL 内出现
需求已确认 → .khy/requirements/20260927-xxxx.md（可编辑），
长任务执行中每阶段日志引用该制品，收尾输出「交付 vs 需求」对账。

  1. 不做会怎样？ —— 五件各自为政的竞争指令继续随机打架；模糊需求继续

「猜错方向白跑一轮」；长任务跑到一半偏航只能整轮作废；Web 端用户面对
只读的「权限确认」文本永远无法回应，只能切回终端。

2. 调研结论（外部铁律 → 本仓对应缺口）#

全量来源 URL 见附录 B；此处只留设计决策级结论，每条注明来源编号。

#外部铁律（出处）本仓现状采纳方式
L1模式门而非模型猜：意图/权限用显式状态机裁决，LLM 只在门内活动（Claude Code plan 模式 [1]、Aider 四模式 [6]、Cline Plan/Act [8]）五个意图件并行注入，无统一裁决状态机聚合器一次算出五路裁决 → 单一 understandingDirective 出口，互斥排序
L2结构化选项 + 自由文本兜底是澄清的标准形态，一次 1–4 题多卡（AskUserQuestion [3]、Cline AgentAskQuestion [12]）TUI QuestionPrompt（755 行）+ questionCardModel 已实现该形态；指令源 clarificationCards 已就绪复用现有数据形状，聚合器按裁决决定何时注入 clarificationCards 指令，不重写指令文本
L3澄清是计划阶段的常规步骤，不是异常兜底（Cline /deep-planning 第 2 步就是「提定向问题」[9]）仅「提示词不清」时才触发澄清（clarificationCards.need 条件）裁决新增 needPlan 级：中大型任务且缺验收口径时，即使提示词「清晰」也建议澄清轮
L4需求固化成用户可编辑的制品：plan 文本 / SPEC.md / implementation_plan.md，好 spec = 点名文件接口 + 声明范围外 + 端到端验证收尾（[4]）无任何运行时需求制品；五问只在 CI 存证新增 .khy/requirements/<id>.md 制品，字段按「好 spec」三件套设计
L5执行时固化物必须反复可见：任务列表跨压缩持久 [1]、GoalController 按迭代审计 [16]澄清结论只存在于会话历史，压缩后即失每阶段状态广播附带制品引用；收尾强制「交付 vs 需求」对账
L6拒绝也是澄清：拒绝动作必须带原因回灌（OpenHands reject_pending_actions [15]）澄清卡「可讨论/自由输入」已有；无「用户答完 → 需求改写」环节澄清答案回灌后由模型复述改写需求（含 source 标注）再固化
L7防自答要出处机制：系统提示明令"ask instead of making assumptions" [13]；本仓规则 6 已有 source: <用户原话> 判据该判据只在 CI 层校验 .khy/feedback/ 存证运行时制品沿用同一判据：需求条目必须带 source（用户原话或澄清答案），无 source 的条目标 ⚠ 由用户确认
L8理解/执行上下文分离：面试完换新会话执行 spec [4]无此分离S1 阶段不做会话分裂；把「压缩后回灌」作为最小替代（成本/收益再评估）
L9学术评测可做回归集：ClarifyGPT 三段式（歧义检测→定向追问→改写需求）[19]、ClarifyCodeBench [22]无任何澄清质量评测列入 §9 未来工作，不在本期

边界声明：本方案是「理解人类用户」的管线；[DESIGN-ARCH-037] 的需求内源发生器
是「系统自产需求」的进化引擎，二者在 EvoRequirement 层面可对接（进化需求也应
过同一固化格式），但本文不展开。

4.1 裁决语义（互斥排序，首个命中即停）#

route触发条件（按序判定）动作
短路① 纯问候（既有 isGreeting，快路径不变）走既有问候管线，聚合器不注入任何指令
clarify④ 指代歧义且引用对象唯一性 < 阈值 → 消歧优先（答不出引用就谈不上需求）；否则 ③ clarity.clear === false注入 referenceDisambiguation 指令或 clarificationCards 指令（二选一，当前散装会双注入）
plan② scale ∈ {normal, large} 且 ⑤ 缺验收口径 且 ③ 已清晰注入「先复述需求 → 列执行计划 → 列验收标准 → 询问是否按此执行」的系统指令（一次性，不阻塞）
proceed其余零注入
  • ⑤ acceptance 判定是新增的确定性启发式（不调模型）：消息中无「文件/模块/命令/

数值/验收动词（跑通、验证、测试、输出、修复 X 报错）」且长度 ≥ N 时判「缺验收口径」。
判据真源放 requirementIntakeService 内，零假阳性保守起步（宁可漏判走 proceed）。

  • 互斥排序原则：消歧 > 澄清 > 计划——先弄清「在说什么」，再弄清「要什么」，

最后才「怎么做」。同一轮至多注入一份问询指令。

6. 数据流与协议#

  • 跨端问询协议：TUI 与 Web 共用 questionCardModel 的数据形状

（{questions:[{question,header,options:[{label,description}],multiSelect}]}），
经既有 AskUserQuestion 控制协议下发。Web 端 ClarifyCard.vue 消费同一形状，
答案回传走既有 control_response 通道（aiChatEventUtils.js 已能收到事件，
只补「可回应」）。

  • 制品生命周期：`created（澄清轮组装）→ confirmed（用户未异议的下一轮）→

amended（用户编辑后）→ superseded（同会话新需求单生成时）`。状态只进制品头注释，
无独立状态机——制品即真相（CH-1 只读豁免适用：任何端要看需求单，直读文件）。

  • 失败语义：聚合器任何一路判据抛错 → 该路按「未命中」处理并 console.warn

具体原因（动作+目标+进度，规则 2）；制品读写失败 → 会话照常进行、状态行提示
需求单写入失败（.khy/requirements/ 权限），本轮不固化（规则 2.2：问题+原因+建议）。

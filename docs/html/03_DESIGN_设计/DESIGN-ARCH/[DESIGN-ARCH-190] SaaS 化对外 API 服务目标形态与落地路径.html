二、目标形态与它的准入门槛#

2.1 目标形态（一句话）#

一个 API Key = 一个计费租户。 第三方拿标准 SDK 调四协议端点，
我按真实 token 用量计价、计量、限流、落审计行；客户能自助注册、开 key、充值、查用量、
下载对账单、吊销 key。

为什么是这个粒度：全库无应用级 tenantId / orgId，组织/席位是与现状不相称的粒度跃迁。
但请注意——「不做组织」不等于「不做多租户」。多个客户的 key 会打同一进程、共享同一份
customerRegistry、同一份 usage 文件、同一份 SQLite、同一批审计 JSONL。
这本身就是多租户隔离问题，验收标准见 §五 P1-3，第一版文档漏了这条，是读者指出的正确批评。

2.2 路线选择的准入门槛（本文未论证的部分，先摊开说）#

要判断「值不值」，需要下面这些数字。本文一个都给不出，因为它们不存在于本仓任何文件里：

维度需要什么现状
单位经济每 token 卖多少、上游成本占比、毛利率零个数字。 pricingService.js 有计价机制（分组 ratio × 每模型 CNY），但那是机制不是定价决定。全文无一个价格、无一个毛利、无一个盈亏平衡点
工期与人力各阶段几人天零个估算。 P0–P4 有依赖顺序，无量级
客户证据有没有真实客户在用 / 愿意付费无。 无访谈、无试点、无意向
需求规模预期多少 QPS / 多少 token无。 而 P3（扩容）整节建立在「要扩容」的假设上——这是循环论证，见 §三 缺陷⑫
运营责任谁值班、谁赔、谁处理盗刷与申诉零。 见 §八

诚实结论：本文能证明「现在不能开端口」，不能证明「应该走这条路」。
若要论证后者，最小充分证据是：（i）一次真实第三方 SDK 端到端成功调用（§三 缺陷⑬）；
（ii）一份单位经济测算（毛利结构 + 保本点）；（iii）至少一个愿意试用的客户。
这三样在本次调查范围内都不可能拿到。

实测推翻了「补 CAS 即可」这一做法。 本文原写「需 CAS 版 saveStore」，实测表明不够：

候选病因实测结果
saveStore(store) 不传 baseVersion，无条件覆盖写成立，但补上 CAS 后仍有丢更新（125 / 100）——CAS 的「检查再写」非原子，两个进程可在对方写入前都通过版本检查（TOCTOU）
writeJsonAtomic 的 tmp 名 .tmp.<Date.now()> 不含 pid，同毫秒两进程算出同一路径成立，但不是主因；补 pid 后 ENOENT 消失，EPERM 仍在
tmp+rename 在 Windows 上不支持并发写同一目标成立且是主因之一：EPERM: operation not permitted, rename …tmp.PID.TS -> …customers.json，即支付回调会直接崩

改前实测（repro-cas-before.txt，6 轮 × 6 并发各 +25 元，期望 150）：
75 / 75 / 125 / 100 / 100 / 125，并伴随子进程 EPERM 崩溃。

实际修法（withStoreLock，基于 fs.openSync(lock, 'wx') 的跨进程互斥）：

  • 锁覆盖整段 read-modify-write，saveStore(store, store.version) 的 CAS 降为锁内第二道防线；
  • 冲突时重读并在对方结果之上重放 delta，最多 8 次，超限报「lost N consecutive races」；
  • 锁过期 10 秒自动打破（应对进程被 SIGKILL 的残留），5 秒拿不到锁则报错并指明手工删除路径；

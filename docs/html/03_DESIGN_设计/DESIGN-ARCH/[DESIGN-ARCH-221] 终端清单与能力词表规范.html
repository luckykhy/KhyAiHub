0.4 三问直答（ask 明确要求：入库 / 逐字节复算 / DATA-SSOT 授权镜像）#

  1. 生成物是否入库：是。 entries/entries.json 作为 7 份 khy.terminal.json 的机器投影入库。理由：读取方横跨 L1（Python 启动器）/ L2（entrypoints 服务）/ 横切（scripts、文档），checkout 后不跑生成器也必须可用；先例是同样入库的生成物 docs/10_规范/registry/ATOMIC-CAPABILITIES.json（:12-15 自述「本文件是生成物……不要手改本文件——改 ATOMIC_GROUPS 后重跑生成器」，守卫 scripts/ci/check-atomic-capabilities.js）。
  2. 如何逐字节复算： node scripts/ci/gen-entry-matrix.js --check —— 生成器在内存里重建三份产物（投影 + 两份分发副本），与盘上文件做原始字节比较（不做 JSON 语义归一），不等则以非零退出码表达（本地便利入口，不发射规则 finding）。finding 的唯一发射器是 check-manifests.js（它是 counts 契约的提供者）：entry-matrix-stale 判投影、sdk-dist-stale 判两份副本。字节规则钉死：2 空格缩进、LF、文件末尾单换行、键序按生成器源码固定顺序（不写时间戳；meta.version / meta.updated 是生成器里的手写常量，先例 atomicCapabilityRegistry.js:2013-2014）。执行面 = pr-gate.yml 显式步骤（形状照 :279-280 的 atomic 步骤）。
  3. 在 DATA-SSOT 如何登记为授权镜像：投影不能登记为授权镜像；分发副本只能登记为「标量级」mirror。 「授权镜像」是 facts[].mirrors[] 的概念，判据是「同一标量事实的另一处表述」：每条 mirror 必须给 kind（6 种取值之一）+ pointer + reason（ssotDataGuard.js:52、:444-457），且镜像失步按标量值比对（:580-611）。投影是 7 份清单 → 1 份聚合，不是标量事实：
    • 走 json-pointer 且 detect.identifiers=[] → ssot-registry-invalid（缺 identifiers，:441-443）；exempt 不是合法 kind（:52 的集合里没有它）。
    • 走 json-count 合法，但 json-count 只判「真源自洽」，没有影子副本这一层（:440-443、:283-293 只取数组长度）。

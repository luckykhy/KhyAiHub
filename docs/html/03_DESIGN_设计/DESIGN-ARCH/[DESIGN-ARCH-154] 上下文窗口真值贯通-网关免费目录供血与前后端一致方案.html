0. 一句话结论#

「总上下文永恒 128k」不是检测逻辑写死，而是真值断供：zen 免费端点 /models 实测不返回任何窗口元数据 → 网关唯一真源缓存 _contextWindowCache 对 zen 系模型永远空 → 全部显示面与预算面落到 128000 保守兜底。而真值（models.dev：mimo-v2.6-flash-free = 200,000）仓库里已有解析代码（dynamicFreeModelService），只是从未接进网关缓存。修复 = 给既有真源供血一处，TUI 底栏 / /context / CtxInspect / Web 端指示器同源同亮——不需要也不应该逐面各修。

5. 诚实边界（刻意不纳入）#

不做的事原因
把 mimo-v2.6-flash-free=200000 写进静态 MODEL_CAPABILITIES 表一行看似修复，实则固化「每加一个模型改一次代码」的债：zen 目录 113 个模型且频繁更替；且静态表平行实现正是本次要收敛的对象（contextWindowDefaults.js:10 自述「散落 6+ 文件」的前科）
把默认兜底 128000 改大（如 1M）违反 contextWindowDefaults.js:13-16 明文契约「宁可写小不可写大」：写小多压缩一次（可恢复），写大运行时 400/413（不可恢复）
每轮预算路径 await 探测（3s）每轮 +1 网络往返，免费池限流风险；且 E3 实测探测对 zen 必败——probe 只配当最后兜底，维持现状不动
修 contextWindowClamp.test.js / contextWindowGuard.test.js 的 jest 存量红非本提案病灶；动它们属于另外的条目（顺带修复纪律：只登记不顺修）
「362.3k 已用怎么压回窗口内」压缩管线既有职责（contextRouter/seamManager），本提案只保证分母诚实
models.dev 数据的实时性保证目录有滞后/谎报可能 → 既有 MAX_PLAUSIBLE_CONTEXT_WINDOW=1048576 天花板钳制（aiRequestAnalysis.js:191）+ 4h TTL + zen 真值优先级更高，三层兜住

6. 反模式（这条路别走）#

✗ 别做为什么
前端自己再拉一份 models.devdynamicFreeModelService 与网关已经各拉一次同一批上游（Z2 正是双管道的产物）；Web 端必须消费后端缓存（handleAiContextStats 已如此），再造第三条管道 = 债复发
全目录批量灌入 _contextWindowCache跨池同名模型（如 deepseek-v4-flash 在 zen 与官方池同 id 不同窗）会互相覆盖；只按「本轮 rows 的 bareId 精确反查」才能保证 key 语义正确
在 ccContextWindows / ctxWindowStats 纯叶子里 require 网关或读 env叶子契约（零 IO / 绝不读 env / 绝不抛，check-leaf-contract.js 执行）；数据一律调用方注入（可选 prop / 可选入参）
为了「前后端一致」在 Web 端复制一份百分比算法两端已经通过 computeContextStats / analyzeWebContextStats 共享叶子 SSOT；分母修一处，两端自动一致——「一致」的正确实现是同源，不是对称复制
用 git log/索引取本文件编号已按目录枚举取 154（目录实况 max=153，含 140 撞号两件的历史教训）

0. 一句话结论#

这 5 个诉求不是一件事，是 5 件不同性质的事，必须拆开裁定，不能一锅端。

#用户原话真实性质本提案裁定
1「像 Mika 一样给 khyos 做个后台屏」G5 后台独立屏（VirtualDisplay 承载 activity）不翻案、不实施。[DESIGN-ARCH-200]:113 已裁「不押」，[DESIGN-ARCH-207] 刚重估过但期 2/3 冻结。悬浮框 ≠ 后台屏
2「悬浮球的样式需要美化，不要再只是一格桥字」既有 BridgeOverlayService 的绘制层改造可做（期 2）。但要先说清：现状不是「没美化」，是 DESIGN-UI.md §6.7 已从黑方块改成 44dp 圆形渐变，问题是恒为一个「桥」字 + 二态变色
3「悬浮窗点击展开后会随悬浮球的位置移动」几何缺陷（面板坐标硬编码，与可吸边的气泡解耦）可做（期 1，最小、独立可回滚）
4「像灵动岛一样播报现在 ai 在做什么要做什么的关键执行情况」复用既有 AmooLoop 零 IO 事件源 + 补一个「要做什么」事件源可做（期 2），但「现在」与「要做什么」是两种数据，不能混
5「展开后随时可以输入提示词，进入队列，用户也可以选择立即发送」本仓此前不存在的新能力域（悬浮窗向 AI 执行链注入 prompt）B-P1 触发 → 必须走 B-P2 提案（本文件）+ 期 1 补登能力域。且撞 3 个硬约束，见 F5/F6/F7

⇒ 本提案不新增任何实现。只做：①把「后台屏」这个词从悬浮框需求里剥离，继承既有裁决；②给出 L1–L4 的组件级契约；③把「输入提示词」这个新能力域的三重冲突摆到台面上，等批准后再分期落地。

12.3 关键设计决策（逐条给原因）#

决策原因
不做队列自动排空，改为显式消费（面板「发送下一笔」/ 输入页「立即发送」）自动消费会在「上一笔 worker finally 放锁 → 取队首 → 再调 ask()」这段与前台预检、单飞锁形成竞态，而本机无真机可验证该竞态（§11.2）。显式消费可观察、可回滚；队列是待发清单，不是后台守护循环
消费只走 Tools.dispatch("amoo_ask") 一处§6 反模式：不在悬浮窗 / 输入页另开 amoo_ask 调用链；sendPendingPrompt() 是唯一调用点
失败保留队首并回人话F7：askRunning 时 Tools.amooAsk 返回 code=single_flight，旧行为是 ask() 直接 return null 静默丢第二笔；F6：amoo 不在前台返回 amoo_not_foreground，按既有预检诚实拒绝，不绕过
队列读走 volatile 镜像，不加 synchronized2s ticker 是契约上的零 IO 主线程路径；sendPendingPrompt() 持 class 锁时会一路走到 Tools.dispatch → 前台预检，不能让 ticker 为读个计数去抢那把锁
输入按钮另起一行，不塞进原四颗胶囊320dp 是原四颗「不裁切」的下限（togglePanel() 注释），加第五颗会撑爆；改宽又要连改 snapToEdge 三个常量，正是 §6 的「局部对齐破坏既有合理功能」
Q4 选 B 后仍不摘 FLAG_NOT_FOCUSABLE方案 B 的全部价值就在「悬浮窗保持纯展示态」；摘 flag 会同时踩 F5（抢输入法）与 F6（前台包变化 → ask() 预检失败）

12.4 ⚠ 方案 B 的固有代价（必须说清，不许粉饰）#

从悬浮窗跳进 App 内输入页时，amoo 会被切到后台；AmooLoop.ask():329-334 的前台预检因此大概率拒绝 —— Tools.java:2235 那段实测注释写的正是这个坑。所以「立即发送」很可能返回：

amoo 不在前台，提问没有发出、已保留在队首：…

这不是 bug，是 §3.2 明写的「代价：需要一次界面跳转，且 amoo 前台预检仍需按既有语义诚实处理」。用户需回到 amoo 聊天页后点面板「发送下一笔」重试。本实现不绕过预检、不伪造前台包、不改道 amoo_apex_ask（§11.1 已裁定那条属另案）。要彻底消除这次跳转代价，属后续独立提案（例如通知气泡 / 全屏 Intent 直填），不在本期。

另有一个未验证项：从 Service 用 FLAG_ACTIVITY_NEW_TASK 启动 Activity，在 Android 10+ 有后台启动限制；本 App 有 SYSTEM_ALERT_WINDOW 权限，但真机行为待验证。

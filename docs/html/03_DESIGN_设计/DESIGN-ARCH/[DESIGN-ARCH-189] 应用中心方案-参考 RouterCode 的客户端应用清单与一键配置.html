[DESIGN-ARCH-189] 应用中心方案 —— 参考 RouterCode 的客户端应用清单与一键配置#

状态：§8 八条决策与 §1 需求五问已于 2026-10-14 经用户逐条裁决（见 §8「裁决」列与 §1 source 列）；仍未动一行代码
适用范围：delivery/web/ai-frontend/（页面）、runtime/node/backend/src/routes/ + src/services/domain/config/（目录、探测、写配置）
解决的问题：khy-os 已经有能力把外部 AI 客户端（Claude Code / Codex CLI / OpenCode …）指到自家网关——ccSwitch 卡片矩阵 + externalApps 写配置器 + MyGateway.vue 我的网关页，路都通了；但这些能力没有一个"以应用为中心"的门面：用户看不到本机装了哪些客户端、每个客户端该配什么模型、配置到底成没成、想拆掉怎么写回。RouterCode Desktop 的应用中心把这个面做成了卡片清单（截图见 §3），本方案定义 khy-os 侧等价的客户端应用目录与一键配置架构，并明确它与既有 ccSwitch / appRegistry 的边界。
强制手段：本方案落地后由 check-client-apps-catalog.js（登记表 ↔ 实际写配置器双向可达）与前端 nav/router wiring 测试执行；文档命名与放置遵循 [DESIGN-LAY-005] 与 [MGMT-STD-001]。
相关文档：[DESIGN-ARCH-101]（代理模式统一 Agent 模型管理与协议桥接方案 —— 卡片矩阵语义真源，本文只用不重定义）、[DESIGN-ARCH-011]（应用接入标准 —— 平台应用，与本文对象不同，见 §0）、[DESIGN-ARCH-026]（系统级服务调用审批网关）、[DESIGN-ARCH-111]（规则绑定层）、[DESIGN-ARCH-071]（通道选择）、[DESIGN-DELIV-002]（棘轮阈值）、[DESIGN-LAY-005]（层级与命名）、[DESIGN-LAY-007]（数据落点）
参考来源（外部行为参考，非本仓真源）：RouterCode Desktop 应用中心。证据两类：① 用户提供的界面截图 upload_20261014_093134_1.png；② 本机 RouterCode 运行时资料 %LOCALAPPDATA%\routercode\（skills/installer/references/appcenter-and-gateway-pages.md、skills/installer/tools/<app_id>/config.json、appcenter.ccswitch）。其源码不在本机、不可读，故本文只对齐行为与信息架构，不复刻其实现、不引入其运行时文件名（见 §0）。

0. 术语红线（先读）#

本仓已有两个词会被本方案撞上，不先钉死必然混淆：

词本仓既有含义（真源）本文一律怎么用
应用runtime/node/backend/src/services/appRegistry.js：khy 平台的独立子应用（khyquant 一类），落 ~/.khyquant/apps/<name>.json本文对象一律写「客户端应用」＝ 外部 AI 客户端（Claude Desktop / Codex CLI / Cursor …）。不写"应用"两个字单独出现——单独出现即指 appRegistry 那一类
一键配置无既有含义本文特指：一次操作把「网关地址 + 密钥 + 模型绑定」写进某客户端应用的配置文件（§7.3 的三档模式）
卡片 / switchccSwitch（[DESIGN-ARCH-101] §5/§7）：provider 卡片，改写本机 CLI 的 live 配置保持不变。应用中心是卡片之上的目录面，不新造第二套切换语义

命名约束（落地时强制）：

  • 代码标识符用 clientApps / client-apps，禁止用 appcenter / app-center 作文件名或模块名——appcenter.ccswitch 是 RouterCode 的运行时文件名，同名会在两个产品之间制造「同一个文件」的错觉。
  • 现有运行时写者（services/domain/network/externalApps/*Adapter.js）不改名、不搬家；应用中心是调用方，不是它们的替代。
  • 「应用中心」的英文在代码里统一 client apps；文档里保留中文「应用中心」以便与用户口吻对齐。

2. 目标 / 非目标#

目标（一个页面 + 一个目录真源 + 三类动作）：

  • 目录真源：一份机器可读的客户端应用登记表（§6 给出落点），每项描述：app_id、中文名、英文包名、描述、分类（桌面端 / CLI）、图标、安装探测方式、配置写者、模型能力分组。登记表是唯一真源，页面与 API 都从它派生。
  • 扫描（只读）：探测本机每个客户端的「装了没 / 配了没 / 配对了没」，产出徽章所需的三信号（对齐 §3 的 configured / configuredVerified / manualConfig）。
  • 一键配置（写）：复用既有写配置能力（ccSwitch/appWriters.js + services/domain/network/externalApps/*），前置备份，事后逐键回报。
  • 页面：卡片清单 + 分类页签 + 搜索 + 扫描按钮 + 三档配置模式选择 + 每卡模型下拉 + 安装/一键配置/诊断/恢复厂商配置/卸载五个动作位。

非目标：

  • 不新增 CLI 命令。[DESIGN-DELIV-002] §1 的三只棘轮（命令 245 / 别名 591 / handler 155）只降不升，新增命令要退役一条旧命令才谈得上。本方案全部能力走 Web（§5）。
  • 不改 appRegistry 语义，~/.khyquant/apps/ 那一套与本文无关。
  • khyquant 不在本方案内（独立项目，人 2026-09-28 明示）。
  • 不在本阶段做"下载并静默安装客户端"。安装涉及系统级服务调用与外部安装器，须先过 [DESIGN-ARCH-026] 审批网关，列为 S3（§9）。
  • 不做密钥分发/账号体系（routes/apiKey.js 的 /generate /refresh /revoke /current 已存在，本文只引用）。
  • 不引入 RouterCode 的运行时契约：clients/*.json、configs/*.json、appcenter.ccswitch、backups/app-configs/*.orig 一律不读不写（即便同机存在）。khy-os 自己定契约（§7）。

{
  "appId": "claude-desktop",

7.3 三档配置模式（语义映射需裁决，见 §8 D1）#

RouterCode 三档的实际差别（证据：skills/installer、skills/installerccswift、skills/installerapi 三个技能包的定位）：永久 = 静态写入本机网关地址与密钥；动态 = 走 CC-Switch 卡片、可随时切换、单模型绑定；API = 不改本机文件，应用直连远端数据面（Bearer）。

khy-os 侧的候选映射（本文不给结论）：

档候选语义落点
永久配置静态写入：网关地址 + 用户密钥 + 绑定模型，写死进目标文件appWriters.js 现有路径
动态配置走 ccSwitch 卡片：配置随卡片切换而变，支持多卡ccSwitch 既有 store + 写者
API 配置不改本机文件，只给「base_url + key」让用户自填/复制分发复用 routes/apiKey.js，本中心只读展示 + 复制

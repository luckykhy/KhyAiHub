[DESIGN-ARCH-194] 原子能力聚合与接口目录#

需求来源：用户原话——「khyos 的原子能力不清晰，需要你把原子能力聚合在一起列出接口，这样二级能力，三级能力直接复用即可就没有必要再重复造轮子，让项目变得巨大」。
定位：把 khy-os 的原子能力（L1）聚合成一张可机检的清单，并规定二级能力、三级能力如何复用它。本文是原子能力目录的方案真源。
状态：已落地。机读注册表 docs/10_规范/registry/ATOMIC-CAPABILITIES.json + 守卫 scripts/ci/check-atomic-capabilities.js 均已生效。
不改：不改任何既有工具的功能；不改 FEATURE-OWNERSHIP.json（那是 L2/L3 能力域登记表，与本文的 L1 原子能力目录分工不同，见 §2.3）；不改 PROCESS-014 棘轮（本文不新增规则 ID，只新增注册表与守卫）。
例外（v1.2）：改了 amooBridgePolicy 的参数契约与校验——收敛 §3.7 的 5 组真跨端冲突时，
读原生实现挖出 3 个参数名 bug（write.text / volume.value / start_app 漏参），
改的是「PC 侧契约与手机原生对不上」这一层，不碰原生实现、不碰工具功能。
同时补上「未知参数拒绝」——原实现放行未知参数，导致传错名字的参数到手机侧被静默丢弃
（write 传 text → 用空串覆盖目标文件）。这是修 bug，不是改行为。
上游依赖：[DESIGN-LAY-005]（L1/L2/L3 层语义）、[DESIGN-SOURCING-001] §3/§4（能力域唯一 canonical）、[DESIGN-ARCH-059]（能力即代码）、[DESIGN-ARCH-193] §六（手机端原子能力复用矩阵）。
证据时效：全部实跑与读码发生于 2026-10-24（目录与守卫）、2026-10-25（分歧收敛），工作区 HEAD ed684bfe，分支 chore/hygiene-20261010。

一、问题：原子能力不是「不清晰」，是根本不存在#

用户说「原子能力不清晰」。实测的结论比这更硬：khy-os 里没有一张原子能力清单，而且当前结构下也不可能有。

实测（§四）：同一种能力——比如「列目录」「执行命令」「搜索网页」——在仓内有 6 份互不重合的工具清单：

#暴露面真源暴露名数
1后端工具注册表runtime/node/backend/src/tools/index.js192
2PC 侧手机桥目录runtime/node/backend/src/services/domain/network/phone/phoneBridgeCatalog.js39
3Android 原生delivery/mobile/.../bridge/Tools.java39
4手机端 Dartdelivery/mobile/.../core/tools/builtin_tools.dart32
5amoon bridge 契约delivery/extension/bridges/khy-amoon-bridge/lib/contracts.js12
6amoo 桥策略runtime/node/backend/src/services/domain/network/amoo/amooBridgePolicy.js22
合计337

337 个暴露名，零处说明它们之间的关系。后果直接命中用户诉求：

  • 二级能力（编排类服务）想「读文件」，后端有 readFile、还有 Read——该用哪个？参数还不一样（path vs file_path）；
  • 三级能力（手机端、amoo 协作）想「跑命令」，exec.shell 到底走 bash、shellCommand、cmd、还是手机侧的 exec_shell？手机侧还自带一套更弱的危险命令白名单；
  • 「列目录」这一个动作，六个面各有一份。

于是每做一个二级能力，开发者都要重新判断「已有的是不是能直接用」，判断不了就再写一份。项目变大就是这么来的——不是某个人偷懒，是没有可查的清单这件事本身在制造重复。

本文的解法不是「再写一份文档让人去查」，而是把这件事变成机器能拦的约束。

二、方案#

2.1 核心决策：清单必须是生成物#

手维护的清单会漂移，而漂移的清单比没有清单更危险——它会让「我查过登记表，没有重复」变成一句假话。所以分工是：

部分谁维护为什么
能力语义（哪几个工具名其实是同一个原子能力）人工，写在 scripts/lib/atomicCapabilityRegistry.js 的 ATOMIC_GROUPS这是需要人拍板的判断，机器猜不了
已登记的重复与分歧人工，同文件的 DUPLICATE_GROUPS / DIVERGENT_GROUPS「允许不一致」是治理决定，不是技术判断
能力清单本体（工具名、canonical、参数契约）生成，从 6 个暴露面实时实测工具的进出是高频事件，人工跟不动

三件套：

scripts/lib/atomicCapabilitySurfaces.js   ← 抽取器：从 6 个面读出真实工具名 + 参数契约
scripts/lib/resolveCanonical.js           ← 解析器：工具名 → 仓内真实定义文件
scripts/lib/atomicCapabilityRegistry.js   ← 语义层：人工维护的能力分组 + 已登记重复/分歧
        ↓
scripts/ci/gen-atomic-capabilities.js     ← 生成器 → ATOMIC-CAPABILITIES.json
        ↓
scripts/ci/check-atomic-capabilities.js   ← 守卫：漂移即红

2.2 守卫拦什么#

规则判据级别
atomic-registry-stale注册表与当前代码不一致（有人加了工具却没归组）error
atomic-registry-missing注册表不存在error
atomic-orphan-exposure某暴露面有工具名未归入任何原子能力error
atomic-name-cross-registered一个暴露名同时属于两个原子能力error
atomic-no-canonical / atomic-canonical-missing原子能力没有 canonical，或 canonical 指向死路径error
atomic-interface-divergent同一能力的参数契约在各面不一致（类型不兼容 / 必填性不一致），且未登记error
atomic-canonical-shared-same-family同族能力共用同一 canonical（疑似拆错）warning
atomic-known-duplicate已登记的存量重复（附收敛理由）warning
atomic-interface-divergent（已登记）已登记的接口分歧（DIVERGENT_GROUPS），附判据warning
atomic-surface-unavailable某暴露面读不到（代码未入仓等）warning

atomic-orphan-exposure 是核心闸门：它把「新增一个工具」这件事，从「随手加个文件」变成「必须先说清它复用哪个原子能力」。这就是「不重复造轮子」从愿望变成机制的地方。

atomic-interface-divergent 是第二道闸门：它管的是「复用时会不会踩坑」——
同一个能力在 A 面必填的参数在 B 面是选填，照抄调用方式就会被拒。
只比「同一动作」跨面的差异：同一面内不同工具名（gitBlame vs gitLog）不算分歧，
同名但语义刻意不同的受限面（amoo bridge 的只读 phone_exec vs 任意 shell）已拆成独立能力组。
已登记的 3 组（平台/粒度差异）只警告，新出现的即红。

2.3 与 FEATURE-OWNERSHIP.json 的分工（不冲突）#

两者都登记能力，但层次不同、粒度不同：

FEATURE-OWNERSHIP.json本文 ATOMIC-CAPABILITIES.json
登记什么L2/L3 能力域（如 ai-gateway、cli-router、shell-command-risk）L1 原子能力（如 fs.read、exec.shell、net.web-search）
数量16 个能力域124 个原子能力
回答什么「这个能力域归谁实现」「这个原子动作在哪些面暴露、真源在哪」
守卫check-feature-ownership.js（SOURCING-004）check-atomic-capabilities.js（本文）

二者互补不重叠：能力域是「能力簇」，原子能力是「簇里的单个动作」。一个能力域可以由多个原子能力组成（shell-command-risk 能力域的 canonical commandRiskClassifier.js，其原子动作是 exec.shell 的风险分级面）。

2.4 分层复用规则（用户诉求的正题）#

用户要的是「二级能力、三级能力直接复用即可」。规则如下：

R-复用-1：二级、三级能力需要某个原子动作时，必须先查 ATOMIC-CAPABILITIES.json 找到该动作的 canonical，直接调用/复用它。

R-复用-2：确需新建原子能力时，必须同时登记：新 id、唯一 canonical（磁盘上真实存在的实现文件）、各暴露面的工具名。先登记后实现（与 [DESIGN-API-002] §4 同一体例）。

R-复用-3：不得为已有原子能力另写一套实现。确需差异化时，走参数差异化（同一 canonical，不同参数契约），不新建实现文件。

R-复用-4：跨端接入（手机侧要一个 PC 已有的动作）走转调，不复制实现——转调在注册表里体现为「同一原子能力在多个面各有一个暴露名」。

R-复用-4 是关键：「一个能力在多个面各有一个名字」是正常且被鼓励的（那是多个接入点）；「一个能力在多个面各有一套实现」才是重复。注册表把两者显式区分开，正是为了让人能一眼分辨「我在加接入点」还是「我在造轮子」。

3.3 一个容易漏掉的事实：amoo-policy 是 phone-bridge 的真子集#

实测（E3）：amooBridgePolicy.BRIDGE_TOOLS 的 22 项全部包含在 phoneBridgeCatalog.BRIDGE_TOOLS 的 28 项里，差集只有 6 个（loop_start/loop_stop/loop_status/amoo_ask/amoo_result/amoo_memory）。

也就是说：PC 侧有两份几乎相同的手机工具契约。amooBridgePolicy 那 22 项各自带 risk/readOnly/requiresConfirm/args——与 phoneBridgeCatalog 的契约是两份独立的。这是「同一个能力域在同层有两个实现」的教科书案例（SOURCING-004 B-L1 P1 级）。

3.5 存量重复的处置（本轮裁决：只登记不改动）#

按用户裁决「只登记不改动」，9 组已登记的存量重复在注册表里标 status: duplicate-logged，守卫只警告不拦截：

每条都附了收敛理由。收敛时把 status 改为 active 并更新 note 即可——守卫会立刻开始拦截新的重复。

3.6 接口目录：参数契约与「分歧」#

只登记能力名是不够的。二级能力真正要问的是：「我要复用这个能力，参数怎么传？」
所以注册表每个原子能力都带一个 interface 段：

字段含义
params参数并集——跨面去重后的规范参数名、类型、必填性、出现在哪些处
perSurface每个面每个工具名的实际契约——供逐字段比对，不做归一
divergent分歧参数名（类型不兼容 / 必填性不一致 / 数值族放宽）
divergenceDetail每处分歧的判据：类型、必填处、可选处

124 个能力里 118 个带参数契约（6 个是无参能力，如 device.ping），归一后共 726 个参数条目。

分歧 ≠ 重复：这是两个不同的病#

重复是「同一动作写了两套实现」——看得见，因为有两个文件。
分歧是「同一个动作，各暴露面对参数的要求不一致」——看不见，因为它只体现为
「在 A 面必填的参数，在 B 面是选填」。二级能力照抄 A 面的调用方式，到 B 面可能被拒。

判据：只比「同一动作」跨面的差异#

首轮判据报出 17 组分歧。其中 12 组经实测是判据缺陷，不是缺陷本身——两类：

  1. 同一面内的不同工具名：gitBlame 要 file、gitLog 不要。那是两个不同动作，

参数本就该不同。强行收敛等于让 gitLog 也要求 file——把正确改错。

  1. 同名但语义刻意不同的受限面：amoo bridge 的 phone_exec（只读诊断白名单，

契约明写「不是手机 shell」）与 phone-bridge 的 phone_exec（任意 shell）。
它是 PHONE_RESTRICTED_TOOLS 之一（phone-tools.js:58）——刻意更窄。
把它并进普通能力组，会让「复用」变成「放宽到任意 shell」，那是降级不是复用。

修正判据后收敛到 5 组真跨端冲突，逐组改代码修掉（见 §3.7）。

两条判定纪律#

  1. 缺元数据 ≠ 契约冲突。 原生 Java 面没有结构化 schema（只有 a.optString("cmd") 这类取参痕迹），

类型恒为 unknown。它不参与类型/必填性比较——否则每个含手机侧的能力都会误报。
实测 22 个参数属「仅原生面有、无类型元数据」，单独标注而非当成冲突。

  1. 数值族内放宽不算严重分歧。 number vs integer 是放宽不是冲突，标为

numeric-widening 仅提示；只有类型不兼容（如 string vs number）或
必填性不一致才进 severeDivergent。

分歧守卫会拦住新分歧#

已对抗验证：把 exploreTool.js 的 query 从 required: true 改成 false，
sys.query 立刻报 [ERROR] atomic-interface-divergent（该能力未登记分歧）；
已登记的组仍为 warning。改回后复归绿。

3.7 分歧收敛：5 组真冲突已修掉#

判据修正后剩下的 5 组跨端冲突，逐一读手机原生实现（Tools.java）定方向——
原生是运行时真源，两份 PC 侧契约都向它对齐。结果挖出 3 个真 bug。

3.7.1 三个真 bug（参数名与原生不符）#

amoo-policy（PC 侧 amoo 桥策略）与 phone-bridge（手机桥目录）描述的是同一套手机工具，
但前者有 3 处参数名与原生不符。evaluateBridgeCall 校验通过后，参数直发手机 /call：

工具amoo-policy 原来声明原生实际接受原生证据后果
writetextcontentTools.java:949必失败 + 用空串覆盖目标文件
volumevaluelevelTools.java:835音量静默不变（比报错更坏）
start_app缺 action/extras/uri全支持Tools.java:587-600这三个参数被当「未知参数」拒掉

write 那条最严重：调用方传 text → PC 侧放行 → 手机侧只读 content → 拿到空串
→ 把目标文件覆盖成空。而 volume 传 value → 音量一点没变，调用方却以为调成功了。

旁证：StepOS 云侧实际发的是 {"path":...,"content":"hi"}
（stepneoCloud/agentLoop.test.js:146）——content 才是真源参数名。

修法：amoo-policy 的参数名与必填性改为对齐原生；write 补回 append；
start_app 补齐 extras/action/uri；volume/level、brightness/value
按原生 optInt 统一为 integer。

3.7.2 未知参数必须拒（补上被漏掉的判据）#

修了参数名还不够：evaluateBridgeCall 原来只校验已声明的参数，未知参数直接放行
（args 原样返回，amooBridgePolicy.js:279）。于是传错名字不会被拦，而是到了手机侧
被静默丢弃——这正是上面三个 bug 之所以能造成数据损失而不报错的通道。

phone-bridge 侧策略早有这条判据（phoneBridgePolicy.js:229-231「工具 X 不接受参数 Y」），
amoo-policy 侧漏了。现已补齐（arg_unknown），两侧一致。

而 PC 侧标成必填，于是「用默认值即可」的合法调用被 PC 侧拒掉：

3.7.4 收敛后剩下的 3 组：目标平台差异，不是契约冲突#

原子能力差异为什么不该统一
fs.writecontent 必填 vs 可选PC 写本机文件系统，手机写 /sdcard——不同目标。手机侧可省略是对的（原生默认空串，写空文件在手机合法）
fs.listpath 必填 vs 可选Dart 的 list_files 列应用工作目录（FileService.listFiles），手机 ls 列 /sdcard，后端 ListDir 列 cwd——三者目标本就不同
device.clipboardtext 必填 vs 可选Dart 侧把剪贴板拆成 read_clipboard/write_clipboard 两工具，写工具天然只需 text；其余面是单一 clipboard 配 op 判别（get 时不需要 text）——切分粒度不同

这 3 组按「目标平台差异 / 切分粒度差异」登记在 DIVERGENT_GROUPS，附具体理由。
强行统一会改变一端的真实语义（如让 ListDir 必须传 path、或让 read_clipboard 要求 text），
那是把正确改错。

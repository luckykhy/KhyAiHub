一、问题与需求五问#

需求原话（人，2026-11-11）：「khyos的命令太多杂乱，模型心智负担太重需要建立索引，分类精简，按照原子组装分级使用」。

五问回答
谁用两类。① 接入 Khy OS 的编码智能体（Claude Code / Codex / Cursor / Kiro / ZCode 等）——它们在每次任务开始时读指令文件，需要一份「名字 → 域」的常驻索引；② 使用 khy CLI 的人——记不住命令名，需要按场景找入口。
何时用模型侧：每次会话注入指令时（常驻 L0）与任务意图命中某类目时（按需 L1）、要查某个命令的参数时（按需 L2）。人侧：忘了命令名、或想知道「这件事该用哪条命令」时。
现在的替代做法① khy help <名字> 逐条查（实测 292/309 条有可用回显，见第三节样本口径订正）；② khy commands --all 平铺 265 个动词；③ khy features 按类浏览 slash catalog；④ 桌面设置页「命令」页 258 条。四条路都存在，但没有一条是给模型上下文准备的：khy help 全量 292 条标题合计 9791 字符（平均 33.5 字/条），平铺即击穿生态层 4000 与 own 层 8000 两个字符预算（runtime/node/backend/src/services/instructionEcosystemRegistry.js:12-13、runtime/node/backend/src/services/instructionFileService.js:42-43）。基线是 0：今天模型上下文里根本没有任何命令表——原稿「全塞 help 标题会涨到约 13113 字符」是对比用的构造数（13113=9791+3322，不是任何现状读数），本版删除该假想敌；基线为 0 时「省 66%」无对象可省，本方案要回答的是「首次常驻注入，预算内装不装得下」
成功长什么样模型收到任务「帮我看下今天烧了多少 token」时：L0 索引（含 12 条 mission 图例）已在上下文 → 第 ①② 步 mission 与名字均 0 命中（12 条 mission 合计 454 字符无一条含 "token"，本会话复算；295 个命令名也无一个含 "token"）→ 第 ③ 步场景触发时机命中「查账」组 → 注入该组入口 → 给出 khy cost。期望输出可复核：注入的命令索引文件 ≤4000 字符（ECO_MAX_FILE_CHARS），12 张类目卡按 inventory.schema.json purpose 口径合计 6029 字符（本会话复算）、单次最多注入 2 张（≤1352 字符），单条详情一次 khy help <名字> ≤1398 字符（本会话复跑 309 条全量确认）。验收命令与期望输出见第八节示例
不做会怎样模型继续在 265–309 个平铺名字里猜命令。代价已实测存在：clean 在 help 与斜杠菜单里广告却无分派（本会话实测裸命令 exit 1「未知命令 clean」；复核结论是补分发而非退休，见第七节）、cleandisk 一跑就崩（本会话实测阶段 2/3 扫描处中断）、sync 是被 portable sync 完全覆盖的遗留入口（本会话实测输出自述「已被 khy portable sync 取代」）——三处坏入口都会把模型引向死路；同类还有 118 个重复入口名字（duplicate-entry 状态计数；按 implementedIn 全量分组复现为 55 组、覆盖 130 个名字，两个基数不同，见 2.3）

三、分级使用模型（L0/L1/L2）#

分级的唯一目的：让模型按任务强度逐级取信息，不一次性吞下全部命令面。L0/L1/L2 三级规则取自 framework.json tiers（本会话已读原文）；二次修订增设第 4 行「场景（附加层）」——原稿的 83 组场景分组没有级、没有预算、没有注入点，却占 7662 字符，本版把它定为按需注入层并写入下表。

级名称准入规则预算（实测）何时升级到下一级
L0常驻索引每个 atom 一行进模型上下文：<代表名> TAB <类目键> [ TAB =<别名1>,<别名2> ]。名字 = 首个 TAB 前的全部内容，故 prompt compose 这类多词名可无歧义解析；类目键恒为第 2 字段、长度 2，与 309 个命令名逐一比对过不相撞。别名不单独占行。只做「名字 → 域」路由，不含中文用途；首行图例扩展为「键→中文名→mission」12 行常驻（mission 归属见下表后裁决）261 行 / 3322 字符（含图例；本会话逐行复算：261 行 name+键 2740 + 48 个别名字段 426 + 图例 116 + = 号 ≈3296，与 3322 差 <1%），约 831 token（÷4 粗估，未过真实 tokenizer）。三种口径分歧已统一：原稿及评审曾给出 3322（逐行复算）/ 3755（行均 12.73 字符 ×295）/ 5113（§8.2 三条示例行均 17.33 ×295）三个相差 39%–55% 的数——本版以逐行复算的 3322 为权威值，其余两种记为上限估计不采用。mission 常驻后 L0 ≈ 3780 字符（+454），占 ECO_MAX_FILE_CHARS=4000 的 94.5%。减负只来自别名折叠：295→261 全部是 48 个别名折进第 3 字段（行数 −11.5%），分级本身没有减少任何一个名字；余量由命令面棘轮背书——AGENTS.md 工程规则 12 / PROCESS-014 / [DESIGN-DELIV-002]「命令/别名/handler/规则数只降不升」，守卫 npm run check:delivery（scripts/ci/check-delivery-baseline.js）：新增 atom 须先退役一条，6% 余量有机制兜底而非文档自称任务意图已能对某条命令点名、需要知道它干什么 → 取该命令所在类目的 L1 卡

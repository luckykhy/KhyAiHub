0. 一句话结论#

截图里那行 [Watchdog] 事件循环曾阻塞 383.3s（同步长任务或死循环嫌疑），现已恢复调度。
大概率是冤案：同屏的资源探针已判定「机器余量 空闲 10%/≥15%……非 khy 缺陷」。
383s 的「阻塞」最可能是整个进程被停走（低余量换页 / 系统休眠 / 被调度走），
不是 khy 在跑同步长任务。病灶：stall 检测器只证明「计时器晚到了」，
文案却断言了归因。方案 = 用 process.cpuUsage() 窗口增量 + os.freemem()
做零 spawn 归因，按归因分化文案与处置，环境性停滞不再背「死循环嫌疑」。

环节位置（runtime/node/backend/src/services/）问题
检测sessionWatchdog.js:616-627drift = 计时器晚到的时长；同步阻塞 / 换页停走 / 休眠三种原因不可区分
文案sessionWatchdog.js:519硬编码「同步长任务或死循环嫌疑」——把三种可能说成一种
上屏政策sessionWatchdog.js:525-526单次 ≥ stallAlertMs(300s) 必报 ⇒ 383.3s 触发单条上屏
同屏矛盾runtimeResourceProbe.js:354资源探针同屏说「低于判据（非 khy 缺陷）」——两条消息归因打架
早有预言runtimeResourceProbe.js:271「可用内存只剩 N%……此时任何常驻开销都会因换页被放大成卡顿」——探针知道会卡，watchdog 不读

判别性事实（方案立足点）：真同步阻塞期间进程烧满单核，process.cpuUsage()
窗口增量 ≈ drift × 单核；进程被整体停走（换页/休眠/调度）时增量 ≈ 0。
process.cpuUsage() 是 Node 内置、微秒精度、零 spawn —— 与
runtimeResourceProbe.js:4 的 zero-spawn 原则一致，恢复瞬间采样不放大卡顿。

3. 目标形态#

3.1 归因叶子（新增 services/stallAttribution.js）#

纯叶子：零 IO（原始读数由调用方采好传入）、确定性、绝不抛、绝不读 env、不改入参。

// classifyStall({ driftMs, cpuDeltaUs, freePct })
//   → { kind: 'sync' | 'external' | 'unknown', cpuRatio, reason }
const SYNC_CPU_RATIO = 0.5;      // 窗口内单核占用 ≥50% ⇒ 真同步阻塞
const EXTERNAL_CPU_RATIO = 0.05; // ≤5% ⇒ 进程被整体停走
  • cpuRatio = cpuDeltaUs / (driftMs * 1000)（µs 对 ms 换算）
  • freePct 只作文案佐证（「当前空闲 N%」），不作硬判 —— 判据唯一真源仍在

runtimeResourceProbe（FLOOR_FREE_MEM_PCT），本叶子不抄它，避免第二真源

3.2 watchdog 接线（只动 sessionWatchdog.js 内部，宿主零改动）#

  • 每拍 beat 顺手记 lastCpu = process.cpuUsage()（两个数，零成本）；

drift ≥ stallMs 时算 cpuDeltaUs 并采一次 os.freemem()

  • recordStall(driftMs) → recordStall(driftMs, attribution)；安装点

（replSession.js:870 / tui/app.js:95）不需要动

  • 文案分化：
归因文案（示意，落地时定稿）
sync[Watchdog] 事件循环曾阻塞 Xs（同步长任务嫌疑：期间本进程 CPU 打满约 Ys/Xs），现已恢复调度。若反复出现，设 STARTUP_PROFILE=1 启动一次定位慢子树。
external[Watchdog] 事件循环曾停滞 Xs——期间本进程几乎未获 CPU（≈0s/Xs），系统换页/休眠/调度嫌疑，非 khy 同步任务。处置：先释放系统侧内存（当前空闲 N%）；低余量机器可 clipboard bridge stop 省约 85 MB。
unknown两种可能如实并列，不猜。
  • burst 合并行（:540-542）同样带归因；stats().stalls 增 byAttribution 计数
  • 上屏政策不动：quiet 默认、单次 ≥300s 仍报 —— 383s 的冻结用户能感知，

该报，但措辞和处置必须指对方向

5. 诚实边界（刻意不纳入）#

不做原因
阻塞「期间」的检测物理不可能（sessionWatchdog.js:22-25 自述），只能事后归因
自动处置（自动 clipboard bridge stop / 杀进程）处置权在用户（runtimeResourceProbe.js:280-281 的既有公理：报告成本，处置留人）
调整 stallAlertMs / quiet 政策那是 2026-09-23 降噪政策的既有平衡，本提案不动
改动 runtimeResourceProbe 的任何判据180 号已落地，本提案不碰
归因到具体系统进程（谁抢的内存）需要 spawn / 性能计数器，违背 zero-spawn 原则
修 jest 风格文件被 node --test 误伤的既有伤情同型受害者至少三处，是独立条目，不顺手修

6. 反模式（这条路别走）#

❌ 别做为什么
调大 stallAlertMs 或把超长 stall 也静音掩盖真死循环信号；quiet 政策本意是降噪不是灭迹
加 KHY_* env 开关控制归因门预算 227 已顶格；「让归因正确」不构成用户可见权衡；还会把 B-P1 豁免变成非豁免
spawn wmic / PowerShell 取系统指标违背 runtimeResourceProbe.js:4 的 zero-spawn 原则；恢复瞬间进程正卡，spawn 放大卡顿
把 freePct < 15% 的判据抄进 watchdog第二真源。freePct 只做文案佐证，判据永远属于 runtimeResourceProbe
用 wall-clock 跳变当唯一休眠判据换页停走不产生「跳变感」；cpuUsage 增量才是判别性证据
把新用例追加进 jest 风格的 sessionWatchdog.test.js一个文件被两套 runner 扫到（jest 因 describe( 命中、node --test 因 glob 命中）；另建文件

13.4 落地中抓到的两个真缺陷（都不是「测试写错」）#

#缺陷后果修法钉它的用例
E1_finite(null) 走 Number(null) === 0探针没读到数会被判成「烧了 0 CPU」⇒ 直接判 external —— 把「无读数」变成一个结论，正是本提案要消灭的那类错误改为类型收紧：只收 number / 非空数字串，其余一律 nullno usable measurement says so instead of accusing khy、a probe returning null is "no reading", not "zero CPU"
E2测试假体按调用次数计 CPUprocess.cpuUsage() 是按墙钟连续累加的；按调用计数让 sync 分支在测试里永远测不到（曾误判为接线失败）假体改为按 Date.now() 差 × rate 累加，rate 可在拍与拍之间切换a busy stall is reported as a sync block、a mixed burst…

[DESIGN-ARCH-156] TUI 帧生成管线契约化 —— 高度账本与字节出口的单一所有者方案#

0. 一句话结论#

帧高这条硬约束（H1：帧高 ≤ rows − 1）目前没有所有者：同一个不等式由 5 个互不知情的控制器（前馈预测、测量反馈钳制、overlay 独占、App.js 内联算术、出口尾切）从 5 个位置各自逼近，chrome 分项清单存在 3 份抄本（文档表格 / App.js 手加 / chromeBudget 字段枚举），两端行单位还不一致（ink 数「逻辑行」、本仓数「视觉行」），差额由 5 个 +2/+4 魔法余量吸收；出口层则同时存在 1 个改写者 + 2 个写者，「本帧要不要清屏」这一意图只能靠直写 ink 私有字段 inst.lastOutputHeight 来表达。

S0 实测已把病灶定位收窄（308 例扫描，见 §5.1）：三份 chrome 抄本今天数值彼此一致（Δ=0），其危害是「三处必须同时改」的漂移敞口而非现存分歧；真正的分歧在账本与前馈预测器undefined之间（306/308 例不等，−11..+12 行）与 overlay 独占者 C3（16 例），另有 40/308 例属于「谁都算不对」——小终端 + 补全框/长清单时 LIVE_MIN 与清单下限互不相让，那一项要的是裁决（X-004），不是收敛所有者。

本方案不重写界面，而是把这条既成链路具名为六段管线，并引入两个契约对象（FrameGeometry 几何账本、CommitPlan 提交意图）与一个唯一出口（frameWriter）：一处算高度、一处出字节、一处记帧账。门控数按 H7 净减 6，App.js 巨石与 legacy/CC 双投影明确不在本次范围（见 §7）。

#环节病灶处置
1几何一个不等式 5 个控制器，无所有者收编为 framePlan 单点 + heightController 单控制器（§3.1/§3.4）
2几何chrome 清单 3 份抄本，文档与代码靠手抄对齐chromeRegistry.js 代码化登记表，表格由它生成（§3.2）
3几何逻辑行 vs 视觉行两端不一，用魔法余量弥合账本内统一视觉行，换算只在 ink 边界发生一次（§3.3）
4意图resize 要清屏只能改 ink 私有字段CommitPlan.intent.repaint 显式化，ink 私有写收敛到一处（§3.5）
5出口四层字节改写无序列、无记录，H2 靠出口兜底才成立具名有序 rewriters 链，逐层留痕（§3.6）
6出口ink 注入流之外还有 rail/topicBar 裸字节写者唯一出口 frameWriter.submit(frame, plan, overlays[])（§3.6）
7可观测KHY_TUI_DIAG_H 只看内联账本，看不到实测与出口字节帧账三元组（计划/实测/字节），复用既有诊断出口（§3.7）

  • 代码抄本 B：chromeBudget.js:46-59 chromeRows() 的 shares 字段枚举。
  • 凑数证据：liveRegionBudget.js:44-55 _baseChrome() 为了走「单一账本」同时保持旧行为，构造 { inputRows: 3, statusRows: 1, slack: 1, extraRows: 4 } 求和得 9，正好等于 :57 的 LEGACY_BASE = 9，注释亦写明「与 legacy 逐字节一致」。账本已存在，但值是反向伪造以匹配旧常量的——这不是收敛，是把三处抄本焊成了三处。

1.3 两端行单位不一致#

  • ink 的判定用逻辑行且取上一帧：tui/AGENTS.md:185-187（outputHeight = output.split('\n').length，ink.js:320）。
  • 本仓钳制用视觉行（含软换行 + CJK/emoji）：liveHeightClamp.js:355-363 导出 wrappedRows / measureVisualRows / tailToVisualRows，宽度度量单源 formatters.displayWidth（注入点 app.js:211）。
  • 该差额正是 WIN_SAFETY_MARGIN = 2 / CLAMP_MARGIN = 2 存在的原因（liveRegionBudget.js:79-91 注释自陈：前馈追不上，故「用静态余量吸收」）。
  • [DESIGN-ARCH-102] H6（:220-224）早已要求「折行与计费同一函数」，判据是 visualRows(t,w) === wrapCell(t,w).length 属性测试——但它约束的是文本内部，没有约束「账本 vs ink」这一次换算。

1.4 意图只能靠改上游私有字段表达#

App.js:4445-4468：resize 时先问 outputIntegrityMonitor.assessResize() 决策，随后在 :4464 直接赋值 inst.lastOutputHeight = _decision.rows，再手动调 inst.calculateLayout() + inst.onRender() —— 用「预置上一帧高度 ≥ rows」来反向触发 ink 的 fullscreen 分支。于是 H1 在本仓是双向的：常态要严格小于 rows，resize 时要恰好命中 ≥ rows。没有任何显式字段表达这层意图，只有对私有状态的两次相反写入。私有实例的取用本身已有降级告警机制（inkRuntime.js:170-202，注释称 bubbletea nil_renderer 式显式降级），但该降级只覆盖「取不到实例」，不覆盖「取到之后被我们写脏」。

1.5 出口层：1 个改写者 + 2 个写者#

  • 写者 ②：带外看板，在同一次 write() 里前插清槽字节、后贴重绘字节（app.js:224-228），字节序被注释判定为「根因级的关键」。
  • 写者 ③：置顶主题条 OSC 标题（runtime/topicBar.js，app.js:408 关），另有 app.js:241-244 的启动锚点裸写与 :288/:303 的鼠标 DECSET 裸写。

1.6 H2 的判据错位（假绿）#

[DESIGN-ARCH-102]:196-202 的 H2 要求「零 ESC[2J/ESC[3J，全量重绘一律 ED0」，判据是「全仓静态扫描零命中（CI 门）」。但实际达成路径是：ink 运行时照样发射 clearTerminal（scrollbackPreserve.js:11-15 记录 ink.js:327/instance.js:132），由出口层在字节上改写为 ED0。静态扫描只看本仓源码，扫不到 node_modules 里的运行时行为——条文靠出口兜住了结果，判据却只证明了源头清白，两者不是同一件事。见 §9-X-002。

1.7 可观测性断层#

  • App.js:6753-6757（KHY_TUI_DIAG_H=1）打印的是 C4 的内联账本，看不到undefined是否真的切了字节。
  • healthScorecard.js:50-54,96 的 h1Holds 用 chromeBudget.liveBudget() 算出来的，不是实测帧——它检查的是「算术自洽」，不是「屏幕真的没超」。
  • frameBudget.js:133 只导出 createGuard（渲染耗时），与高度无关。
  • 结论：没有任何一处能把「计划高度 / ink 实测高度 / 出口实际字节」三元组放在同一行里对照。上述每一次定位（AO/repro-before.txt、AU/repro-before-bug77b.txt）都靠外部字节流探针手工完成。

3. 目标架构：六段管线 + 两个契约 + 一个出口#

3.1 管线阶段与所有者#

P1 投影  events/messages ──▶ screenLines[]          (既有，本次不动)
P2 几何  screenLines + registry ──▶ FrameGeometry   ★ framePlan.js        ← 唯一算高度的地方
P3 布局  FrameGeometry ──▶ React tree (props 下发)   (App.js，瘦身为「只消费 plan」)
P4 合成  tree ──▶ frameString                        ink（外部，私有字段只允许 1 处写）
P5 改写  frameString + CommitPlan ──▶ bytes          ★ frameRewriters.js   ← 收编 4 层
P6 提交  bytes + overlays[] ──▶ 一次 write()          ★ frameWriter.js      ← 唯一碰真 stdout 的地方

依赖方向单向：P2 不知道 P5 存在，P5 不知道 React 存在。每段的输入输出都是可冻结的纯数据，因此每段可独立单测（沿用本仓「纯叶子：零 IO、确定性、绝不抛」的既有纪律）。

3.2 chromeRegistry.js —— 把 AGENTS.md 的表变成代码#

  • rows 允许是 fn(ctx)，但 when/evidence/owner/kind 必填；缺 evidence 视为未登记，守卫记样本（§5）。
  • kind: 'paint' | 'reserve' 是强制字段，不是注释：paint 是这一帧真的画到屏幕上的行，reserve 是刻意留空的上界行（conpty 软换行余量、ink 追加的尾部 '\n'）。H1 只对 paint 求和；把 reserve 当 paint 记账会双计并制造出「308/308 全违规」的假红（S0 首版实测踩过，见 §5.1）。chromeBudget.js:117-119 早已就「cap 里的换行余量是 reserve 而非 paint」写过这句话，本节把它从注释升格为契约字段。
  • 取代关系：AGENTS.md:204-212 表格改为由登记表渲染（docs:rules-cards 同法，构建产物不得手改），从此「文档说的」与「代码算的」不可能不一致。
  • 收编：App.js:6403-6404 手工相加、:6492-6507 兜底副本、liveRegionBudget.js:44-55 的凑数 _baseChrome()（其 9 必须拆成真实分项，允许总行数变化，因为「凑成 9」本身已说明真值未被测量）。
  • chromeBudget.js 保留为算术核（chromeRows/liveBudget/LIVE_MIN），只换数据源：shares 由 registry 产出，不再由调用方拼装。换算处不得把 inkTrailer 塞进 shares——liveBudget() 自带那 - 1，两处都给就少画一行（frameDivergence.sharesFrom() 已把这条例写成断言）。

3.3 单位统一#

  • FrameGeometry 内部一律视觉行，unit: 'visualRow' 显式声明。
  • 与 ink 的换算只发生在 P6 边界一处：toInkOutputHeight(frameString)（逻辑行），并断言 planned_visual ≥ ink_logical 的方向性。
  • 一旦单位统一，SAFETY_MARGIN/WIN_SAFETY_MARGIN/CLAMP_MARGIN 三个魔法 2 降级为可解释的登记项（「conpty 软换行离散化，evidence: BUG 编号」），不再参与正确性。

3.4 heightController.js —— 5 个控制器合成 1 个#

C1（前馈）与 C2（反馈）本质是同一条控制律的两项，合并为单函数、单状态：

next({ plan, measuredFrame }) -> { seedRows, correctionRows }   // pure, monotonic
  • 保留既有的收敛条件（单调非降 + 相等守卫防渲染循环，App.js:4555-4557）。
  • C3（overlay）不再是「另一处预算」，而是 registry 里一条 when: ctx.overlay !== null 的登记项 ⇒ overlay 激活时其行数以普通 chrome 身份参与同一次求和。
  • C5（尾切）保留在 P5，但降级为纯保险：它只在 plan.overflow != null（几何不可能）时动作，并在帧账里如实记 tailCut ——「切了」不再是静默行为。

3.5 CommitPlan —— 把「我要清屏」变成显式意图#

CommitPlan = { repaint: 'incremental' | 'full', reason: 'resize-cols' | 'h1-overflow' | null }
  • 唯一消费者是 frameWriter；只有它被授权写 inst.lastOutputHeight（现为 App.js:4464），写前断言 repaint === 'full'，写后计入帧账。私有字段的取用沿用 inkRuntime 的降级标志（:209-211）。
  • App.js:4445-4481 的 resize 分支改为：算 CommitPlan → 交给 frameWriter，自身不再持有任何 ink 内部引用。

3.6 出口收敛#

frameWriter.submit(frameString, commitPlan, overlays = [])
// rewriters: ordered, named, each returns { bytes, applied: reason|null }

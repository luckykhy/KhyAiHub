0. 一句话结论#

「甩出去」（跨通道兜底）本身是正确能力 —— 问题不在甩，在于什么时候甩的判据分散在 6 处补丁里、故障归属不分、甩出事件不可存留。用户实测体感「不通时不会清楚报错，反而总是发去什么桥接或 claude 渠道」，正是这三件事叠出来的：

#病灶位置性质
①判据分散且互不一致：同为「不通」，HTTP relay 通道要命中 dead-endpoint 类（404/4xx/5xx）才放宽，process-sensitive 通道（claude/codex/kiro/cursor/trae…）遇 process/timeout/network 就放宽aiGatewayGenerateMethod.js:2497-2549 vs :2499-2527 vs :2528-2548缺单一真源
②环境级故障无判定：断网/代理挂时「换通道也无意义」无法识别，系统会对每个远端通道逐一甩一遍，再叠 jitter 4 轮重跑，最后才报「所有 AI 通道均不可用」:3890-4100（级联）+ :2214-2228（jitter）+ :6529（报面）归属缺失
③甩出披露只活在转瞬的状态帧里：切换说明全走 emitStatus → {type:'status'} 流式帧，非流式面不可见、滚动即消失；成功回复零披露；routeFact 有 attempted/served 但无切换链与原因:1168-1195、routeFact.js、cliFailureEnvelope.js观测面缺口
④失败引导反向推销兜底：报错建议里出现「切换到 API/桥接通道」「配置 RELAY_API_ENDPOINT + RELAY_API_KEY 启用中继兜底」「GATEWAY_CLAUDE_MODE=direct 直连」——用户词汇里的「总发去桥接/claude」与这些文案吻合aiGateway.js:2063、:2071-2072文案错位

术语对齐（本仓语境）：用户说「桥接」= PROCESS_SENSITIVE_ADAPTER_KEYS（aiGateway.js:1214-1224：cli / codex / claude / kiro / cursor / trae / vscode / warp / cursor2api —— IDE/CLI 桥接类通道）；「claude 渠道」= claudeAdapter（CLI 桥接 / 直连 API 双模，GATEWAY_CLAUDE_MODE=auto）。两者都属于有本地进程副作用的桥接类。

本提案的答案一句话：把「甩」显式化为三态决策（原地重试 / 甩并披露 / 停下报错），以「故障归属」为第一判据，环境级不通走「等待网络恢复」而非继续甩，判据收拢到一个纯叶子。

1.2 判据集互不一致（同失败，不同待遇）#

失败类别HTTP relay 首选（S2）process-sensitive 首选（S3）差异
network✗ 不放宽（需 dead-endpoint 类）✓ 放宽（直接甩）同型失败，取决于通道类型
timeout✗✓同上
process✗✓同上
bad_request(400)✓ 放宽（在 DEAD_ENDPOINT 集合内）✗400 常是请求构造问题——换通道大概率同样失败或掩盖真因
auth / rate_limit✗（注释声明刻意排除，:2517-2518）✗✓ 已正确
server_error(5xx)✓—✓ 通道侧故障，甩合理

auth/rate_limit 的排除是口头哲学写在注释里（「活着但被限流/鉴权失败的端点应就地重试或换 key，不该被级联甩掉（否则会掩盖 1302 之类）」）——没有叶子、没有单测钉住。下次谁改判据，无人拦截。

1.3 环境级缺失与既有「等待网络恢复」错层#

断网/代理挂时的现状行为链（实测代码路径）：

首选失败(network) → 可能放宽(S2/S3) → 逐通道甩(含桥接类/claude)
→ 每个远端都 network 失败 → jitter 4 轮重跑（退避,每轮全失败）
→ 级联耗尽且全瞬态 → 才进入「等待网络恢复」（:6295-6402,周期性轻探）
→ 最长等 _networkResumeMaxMs 后放弃 → 报「所有 AI 通道均不可用」( :6529 )

两个问题：

  1. 判定太晚：环境级证据（≥2 个远端同型 network 失败）在第 2 个通道失败时其实已经成立，但系统把剩余通道全试完 + 4 轮 jitter 之后才用上它（作为「等待网络恢复」的触发）；buildChannelFailureAdvice 的 network 指引（buildChannelFailureAdvice.js:140-141）也要等全穷尽才显示，且主标题仍是「通道不可用」——真因果被倒置（不是通道坏，是网络坏）。
  2. 「等待网络恢复」是正确机制但触发条件错层：它已有探针、轮次闸、诚实披露（:6346、:6402），这正是「环境级不通」应有的归宿。缺的只是把触发从「穷尽后」提前到「可判定时」，并在等待期间不甩远端（除本地 ollama/localLLM）。

3. 目标形态（组件级契约）#

D1（单一真源）甩出资格判定表#

把「什么时候甩」显式化为 归属（ownership）→ 三态决策 两段式。故障归属是第一判据：

归属判定材料决策
channel-scoped（通道自身故障）server_error(5xx) / process / unavailable / 瞬态传输（reconnecting/channel closed/socket hang up）/ 单通道 timeout、networkF = 甩（级联下一通道）
environment-scoped（环境级）证据 A：同一轮内 ≥2 个不同远端适配器 key 均以 network/timeout 类失败；证据 B：错误含本机解析/代理特征码（EAI_AGAIN/getaddrinfo/ENOTFOUND/proxy tunnel/tunneling socket）。注：ECONNREFUSED 单独不构成环境证据（更像目标端点死）E = 不甩远端：跳过剩余远端适配器（留痕），把控制交给既有「等待网络恢复」（§1.5）；本地通道（ollama/localLLM）仍可尝试
request-scoped（请求/凭证侧）auth(401/403) / rate_limit(429/1302) / bad_request(400) / model_not_found(模型名形状错)B = 不甩，明确报错 + 修复指引（auth→查 key；rate_limit→等窗口；400→查请求；404→查模型名）

三态的含义（合法性闭合）：R（原地重试——不换通道，用于 rate_limit 冷却等待）、F、B、E 四出口，其中 R 与 E 是本提案显式化的两个新命名（R 行为现状已有，仅命名；E 是新增判定）。

钉选身份 × 决策（与现状语义对齐，不变）：

钉选身份判定来源通道侧故障时请求侧故障时
用户显式钉选options.userPinnedAdapter / options.preferredAdapter + strictPreferred:true（:2160-2165）B（现状：绝不放宽——保持）B
env 钉选GATEWAY_PREFERRED_ADAPTER 非 autoF + 披露 + 租约（现状 S4——保持，受归属判据约束）B
auto无钉选F（S1 级联——保持）B（现状 auth 等仍会级联——一期先披露，二期收）

目的地资格（甩去哪，按成本分级）：

目的地类别成员资格
本地无网络依赖ollama / localLLM自由甩；环境级判定后是唯一仍可尝试的远端之外选项
远端 API / 中继api / relay_api自由甩
桥接类（有本机进程副作用）PROCESS_SENSITIVE_ADAPTER_KEYS（:1214-1224）可甩，但受两约束：①环境级判定后不再甩桥接类（它们同样依赖网络）；②同轮甩入桥接类的次数受 maxTotalAttempts 既有闸约束（不新增）
人肉relay / clipboard禁（manualRelayAutoFallbackPolicy.js 既有——保持）

本表落地形态：新叶子 runtime/node/backend/src/services/gateway/fallbackEligibilityPolicy.js（纯叶子：零 IO、确定性、绝不抛、不读 env），承载 D1 表 + D2 证据聚合，供 §3.4 的消费点统一调用。

D2（环境级判定提前）environmentOutageSignal 聚合#

  • 位置：新叶子（可并入 fallbackEligibilityPolicy.js 同模块双导出，或独立 environmentOutageSignal.js——实施时按文件行数 2000 上限取其一）。
  • 输入：{ attempts, env }（attempts 为已有结构，含 adapterKey/errorType/error/statusCode）。
  • 输出：{ environmental: boolean, evidence: string[], remoteAdaptersFailed: number }。
  • 判定纯函数、绝不抛；timeout 计入证据但降权（timeout 也可能是慢端点）。
  • 消费点一：级联循环内，在一个远端适配器失败后调用；environmental:true → 对剩余远端适配器逐条 allAttempts.push({...virtualSkip:true, errorType:'env_outage_skip'}) + emitStatus('检测到跨通道网络不可达，暂停远端尝试，转为等待网络恢复') + continue 跳过（本地通道不跳）。
  • 消费点二：jitter 重跑前置判定；environmental:true → 跳过 jitter（:6245 处），直接进「等待网络恢复」（:6295）。
  • 消费点三：buildChannelFailureAdvice 之后（:6477-6508）——环境级命中时改用环境级文案（见 D3-3）。

D3（披露三件套）#

cascade: [ { adapter, errorType, cause, decision:'fallback'|'skip'|'failed' } ],  // 逐跳链,虚拟跳过也计入(cause 标 virtualSkip)
switchedFrom: 'claude' | '',      // 与 served 不同的首跳来源

⚑ 本次由 <served 显示名> 完成（首选 <switchedFrom 显示名> 因 <switchReason 中文> 不可用，已自动兜底）。如需固定通道：khy provider use。

不注入回复正文（避免污染下游复制/解析）——notice 是独立行。

6. 反模式（这条路别走）#

✗ 别做为什么
见 network 就停（不加跨通道复现条件）单通道 network 是通道级故障（该端点死了），甩下一通道恰恰是对的。停的条件必须是「≥2 个不同远端 key 同型失败」或环境特征码——「一次失败就宣布网络全断」会把单点故障误判成环境故障，让本可兜底的请求直接失败
把环境级判定做成「再探一个 HTTP 请求」增加热路径延迟且探针本身也可能失败；跨通道复现证据（D2-A）零成本、纯离线可测。探针是反模式，证据聚合才是
把披露塞进状态帧就算完139 已踩过：「状态行转瞬即逝、不可存留」（139 §6）。披露必须进可存留面（routeFact 字段 / notice 行 / 信封）
给「环境级跳过」记真实失败会毒化熔断与健康度（把网络问题记成通道坏）。必须 virtualSkip:true 同型（照抄 :3998-4006）
在成功回复正文里注入「本次由 X 完成」污染下游：复制、diff、二次解析都会吃到注入行。用独立 notice 行
为「甩快点」把桥接类提到队列最前桥接类有本机进程副作用（spawn CLI/IDE），且 139 病史显示「自动甩到未选通道」正是用户投诉源。提升资格只属于进程级 failover（S5）既有条件，不得新开
三期收紧 bad_request 时直接踢出 DEAD_ENDPOINT 集合会让「中继站拒特定请求格式 → 换通道可成功」的既有场景卡死（adaptiveParamStrip 的存在证明这类真实存在）。必须先有 cascade 样本细分「端点语义 vs 请求语义」，再按证据收紧
把本策略实现成新的「总调度器」收拢是「多调用点消费同一叶子」，不是「新造一层路由」。routing 的真源仍是 aiGatewayRoutingMethods.js

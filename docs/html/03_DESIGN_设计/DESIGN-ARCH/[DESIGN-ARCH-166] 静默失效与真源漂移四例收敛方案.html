0. 一句话结论#

2026-09-29 的一次截图诊断（.khy 体积提示 + 半行 WARNING: Package(s) not found: khy-os）挖出四条彼此独立、却同属两个病因的缺陷：

  • 病因 A —— 能力/输出绕过了既有契约（「代码全在、判据全绿、在某个入口上从不生效」）：
    • ① 子进程 fd 2 继承绕过了 consoleMute 的 TUI 会话静音，是 [DESIGN-ARCH-156] §1.5 写者清单里漏掉的第 4 类写者；
    • ④ trimQuarantine() 已存在、已导出、参数正确，但只挂在 khyquant 模式的 runCleanup 上 —— khy 入口从不调它。
  • 病因 B —— 同一件事有两份语义输入，只对齐了一半：
    • ③ assessRuntimeFootprint 抄了 RUNTIME_TARGETS 的 rel 列表，漏抄 RUNTIME_KEEP_PREFIXES ⇒ 提示报「可回收 187 MB」，实际只有 55.4 MB。
  • 第三族 —— catch {} 把可诊断的失败变成不可诊断：
    • ② 4 个名为 *.json 的空目录顶掉了同名文件，写入 EISDIR 被 catch 吞掉 ⇒ skills 缓存与工具权限静默不落盘。

四条修法的共同约束：规则棘轮 94/94 已满（新增一条须先退役一条）、TUI 门控实测 236 > MAX_GATES 227 已超限（零余量）。因此本方案不新增规则 ID、不新增 KHY_* 门控，全部落在既有机制上。

1. 现状实证（file:line 可复核）#

1.1 ① 子进程 fd 出口 —— 单写者名单里漏掉的一类#

症状（截图）：WARNING: Package(s) not found: khy-os 落在输入框与状态栏下方，不在 TUI 的受管区域内。

根因：services/backend/src/services/khySelfUpdateService.js:229-237

function _readInstalledVersion(execImpl, pkgName) {
  const info = execImpl(`${_pipCmd()} show ${pkgName}`, { encoding: 'utf-8', timeout: 5000 });
  //                                                        ^^^^^^^^ 未指定 stdio

Node 的行为（实测，两条对照）：

调用形态子进程 stderr 去向
execSync(cmd, {encoding, timeout})（无 stdio）转发到父进程 stderr ⇒ 落在终端上
execSync(cmd, {stdio:['pipe','pipe','pipe']})被 pipe 捕获，不出现在终端

触发链（全部为启动路径，非用户命令）：

bootstrap/prefetch.js:296-313   versionUpdateNotice（+5s 后台 runner）
  └─ services/updateCoordinator.js:435 checkUpdate
       └─ services/updateCoordinator.js:371-377 checkPackage
            └─ khySelfUpdateService.js:173 checkUpdate
                 └─ :239 _detectInstalledPackage   ← 逐个试候选表
                      └─ :231 _readInstalledVersion ← 裸 execSync，stderr 泄漏

为什么本机必然命中：versionService.js:28 PACKAGE_CANDIDATES = ['khy-os', 'khy-quant']，而本机是源码树运行：

$ pip show khy-os      → WARNING: Package(s) not found: khy-os   ← 与截图逐字节一致
$ pip show khy-quant   → Name: khy-quant / Version: 0.1.78        ← 命中，故只出现一条告警

「只出现一条」这一点反证了泄漏源是 _detectInstalledPackage 的第一轮循环。

同族既有机制（本方案要复用的）：services/backend/src/cli/tui/consoleMute.js:1-21 的注释把失败模式写成了「英文内部日志压在状态栏下面、重绘后还残留」，并登记为 BUG-13 家族（含 BUG-17 watchdog、BUG-29 陈旧行）。接线在 cli/tui/app.js:316-332，逃生阀 KHY_TUI_CONSOLE_LOG（consoleMute.js:36）。

它治的是 winston 的 console._stdout/_stderr.write；本方案的 ① 治的是「子进程继承数字 fd 2」——同族、不同逃逸路径。

[DESIGN-ARCH-156] §1.5 的写者清单（① ink stdout Proxy、② 带外看板、③ 主题条 OSC/启动锚点/DECSET 裸写）不含子进程 fd 继承；其 §8 已预告「名单继续有效，但新增绕过者的判定标准变成『是否走了 frameWriter』」。⇒ ① 是本方案要补登记的第 4 类。

门控预算实测：node scripts/ci/check-tui-gates.js → FAIL — 236 unique KHY_* tokens (limit 227)。⇒ ① 的防复发不得新增 token。

1.2 ② 幽灵 *.json 目录 —— 4 个存储写入 EISDIR#

.khy/ 顶层存在 4 个名字以 .json 结尾的空目录（创建时间 Sep 25 14:47）：

ai_gateway_customer_usage.json/    ai_gateway_pricing.json/
skills_cache.json/                 tool_permissions.json/

写入实测（4/4 失败）：

WRITE-FAIL tool_permissions.json           -> EISDIR: illegal operation on a directory
WRITE-FAIL skills_cache.json               -> EISDIR: illegal operation on a directory
WRITE-FAIL ai_gateway_pricing.json         -> EISDIR: illegal operation on a directory
WRITE-FAIL ai_gateway_customer_usage.json  -> EISDIR: illegal operation on a directory

根因：services/backend/src/utils/dataHome.js:346-350

function getDataDir(...segments) {
  const dir = path.join(getDataHome(), ...segments);
  _ensureDir(dir);          // ← 对「拼接后的完整路径」无条件 mkdir
  return dir;
}

配套 _ensureDir（:506-516）把错误也吞了：catch { /* ignore */ }。getAppDataDir（:600-602）同构。

⇒ 任何 getDataDir('xxx.json') 这类调用方误用都会造出一个同名空目录，且不报错。

仓库已知但未修：services/backend/src/services/domain/backup/backup/backupAssetPlan.js:237-251 注释原文：

幽灵 *.json 目录:既存 bug 的产物,不是状态。……根因在调用方误用,应另开任务修；备份侧只需认出它们不是状态。

备份侧只做了剪枝（isPhantomJsonDir:249-251 → classifyDir:264-266 prune），根因仍在。

静默失效的两个实证点：

  • services/skillRegistry.js:145-161 saveCache() 的 writeFileSync 落在 catch { /* ignore */ } 里 ⇒ skills 缓存永远写不进；loadCache:126-138 同样静默（existsSync 对目录返回 true → readFileSync 抛 EISDIR → 被吞）。
  • services/tool/toolCallingBuiltins.js:52 PERMISSIONS_FILE = path.join(_appHome(), 'tool_permissions.json') ⇒ 工具权限无法持久化。

★ 影响面实测（决定修法强度）：全仓 get(Data|AppData)Dir('<含扩展名的段>') 只有 2 处命中，且都是「警告不要这么写」的注释（backupAssetPlan.js:241、tipHistoryStore.js:28）——没有任何活跃误用调用点。⇒ 加 fail-fast 的爆炸半径 = 0，这是本方案里风险最低的一处改动。

附带发现：另有 api_keys.json.stale-dir-20260828/、custom_providers.json.stale-dir-20260828/ 两个空目录；对应的 api_keys.json / custom_providers.json 已是正常文件（说明曾被人工恢复）。stale-dir- 这个命名全仓无代码生产者——只有 docs/10_规范/registry/DATA-LOCATIONS.json:103 把它登记为机器树模式（"machineTreePatterns" 里的 "\\.stale-dir-"）。生成它那一步不在仓里，见 §12-Q4。

totalBytes = 58096106 = 55.4 MB
    28.3 MB  .khy/audit          10.8 MB  .khy/logs        10.8 MB  .khy/tmp

⇒ 187.1 − 55.4 = 131.7 MB，正好等于被保留的 tmp/quarantine-20260915。

这个不变量在两处被明文写死，却被违反：

位置原文

cli/handlers/clean.js:476-477（push 内）「预报告的数字必须等于实际会删的量，否则用户跑完发现对不上，下次就不信了。」

★ 修法的分层约束（这一步决定了落点，别踩）：cleanupService.js 在 services/，clean.js 在 cli/handlers/。services/backend/scripts/archDebtScan.js:12,239-256 的 R1 分层倒置明文规定：

⇒ 不能用「让 cleanupService require clean.js」这种最直觉的写法——它会当场把 check:arch-debt 变红。真源必须下沉到两侧都能消费的叶子。

★ 架构上它就是指定层（不是「恰好可行」）：docs/10_规范/registry/DOMAIN-DEPS.json 把 constants/ 与 utils/ 同列为 D3「共享底座」，其原文定义是「被大量复用的策略与设施：只被依赖，不反向依赖」，roots 显式含 services/backend/src/constants，mayDependOn 仅 ["D3"]，evidence 举的例子正是 utils/dataHome.js（入度 323）与 constants/serviceDefaults.js。⇒ ③ 的真源下沉到 constants/ 是走 D3 的既有职责，且叶子零 require 天然满足 d3-purity（check-repo-layout 的 37 处告警全与本方案无关）。判据真源 [RESEARCH-018] §4 C-5/C-7。

⚠ A5'（④，执行时新增）—— 光补调用是 no-op，必须同时修读取路径#

2026-09-29 执行步 1 时实测发现：A5 单独落地后，它要修的那个文件一行都不会被裁。链条如下（每一步都有可跑判据）：

步事实判据
1文件 574,366,048 B（547.8 MB），而 QUARANTINE_MAX_BYTES = 20 MBfs.statSync(...).size
2走 cleanupService.js 的「超字节上限」分支size > QUARANTINE_MAX_BYTES
3该分支用 fs.readFileSync(filePath, 'utf-8') 整文件读旧 :912
4文件 超过 Node 单字符串上限 0x1fffffe8（≈512 MB）⇒ 必抛ERR_STRING_TOO_LONG: Cannot create a string longer than 0x1fffffe8 characters
5旧实现的 catch { continue; } 把它吞成 {trimmed:false}旧 :921-923
6结论：永不裁，且静默实测裁前/裁后同尺寸

同一文件上还有第二个反直觉事实：单行均值 761 KB（尾部 8 MB 窗口内仅 11 行完整记录，全文件约 754 行）。因此 QUARANTINE_MAX_LINES = 5000 对它是无约束力的——5000 行合 3.6 GB；旧「超限保留最后 floor(5000/2)=2500 行」的语义在该文件上根本不可表达（2500 行 ≈ 1.8 GB，比文件本身还大）。真正起作用的只有字节上限，所以修法必须按字节而非按行。

修法（三处，同属 cleanupService.js）：

  1. 新增有界尾读助手 _readTailText(filePath, maxBytes)：openSync + readSync 只读尾部 min(size, maxBytes) 字节，返回 { text, truncated }（truncated=true 表示窗口首行被切断）。代价有界，绝不整文件加载。
  2. 两个「超限」分支改为按字节保留尾部（trimQuarantine / trimTrainingData）：取尾窗 → 丢弃被切断的首行（半条 JSON 留下会让下游 JSON.parse 炸）→ 写回。
  3. 失败不再静默：trimQuarantine 的 catch { continue } 改为记录 lastError，最终返回 { trimmed:false, error }。承 §4-P2（静默 catch 只许用在失败无害上）——此处失败正是全部意义所在，属必须可诊断。

同时把两处摘要文案（runCleanup 的 results.summary.actions）从 ${before} → ${after} lines 改为 _trimmedAction()：按行裁的仍报行数（既有文案不变），按字节裁的报「保留多少行 + 释放多少」，避免打印 undefined → 28 lines。

验收（真实尺度，原文件只读）：在 547.8 MB 文件的副本上跑 trimQuarantine() ⇒ {trimmed:true, after:28, freedBytes:553687864}，裁后 19.72 MB ≤ 20 MB，尾部逐字节与原文一致，耗时 368 ms（回应 §12-Q6：无感）。

★ 方法论教训（已回写 §6-B4）：「调用面计数 > 0」不足以判定「真裁掉了」。B4 打桩计数在 A5 单独落地时全绿——函数确实被调了，只是内部抛错被吞。判据必须下沉到字节路径（不许整文件读 + 结果尺寸真的下降）。这是本方案自身病因 C 的一个实例：我差点把它当成「已修」上报。

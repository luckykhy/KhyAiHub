一、第三次订正一个判断#

本仓此前两次就「数值漂移能否机检」下过判断，两次都错：

版本判断实测结果
初版「数值、口径、命令与代码不符无法机械判定」对绝大多数数字成立
二版「内容级漂移不在射程」被 DOCS-006 推翻（端点字面量可逐字比对）
本条——对「同名常量」这一类成立

推翻的推理：文档写下 <常量名> = <值> 时，文档与代码说的是同一个名字——
这给了机器一个可逐字比对的锚点。文档写 MAX_GATES = 227、代码写
const MAX_GATES = 237，两者指的是同一个东西，无需任何启发式推断。

二、判据（两条，都不执行任何命令）#

#判据说明
N1常量值：文档写 <常量名> = <值>，代码里该常量有唯一确定的值两者不符即漂移
N2行号：文档写 file.js:41 MAX_GATES = ...，而该常量实际在第 50 行引用的行号已失效

三、修复时为什么改「行号」而不是「追行号」#

[DESIGN-DOC-004] 之外的 [DESIGN-DOC-003]（README 内容规范）与
RULES-REGISTRY 的 DOCS-004 都已写明：

引用代码与文档位置一律给符号名或小节标题，不得给行号
（行号是最易漂移的副本）

所以修法不是把 :32 追成 :50——下次在文件前部插一行又失效——
而是去掉行号，只留符号名：check-tui-gates.js 的 MAX_GATES = 237。

这条守卫同时在守 DOCS-004 的约束：它把「文档引了失效行号」变成可判定。

四、刻意不做的三件事#

4.1 不执行文档里的任何命令#

文档写 node scripts/foo.js 就跑它，等于让一份文档获得执行权——
那不是校验，是攻击面。需重跑才能得到的读数（如 archDebtScan 的 R1/R3、
check-tui-gates 的 token 计数）须由白名单注册表显式登记后才可跑，
不在本条射程。

本条只做读文件 + 逐字比对，不 spawn 任何进程。

4.2 同名多值不判#

代码里 MAX_GATES 若在两处定义为不同值，说明它有上下文差异
（配置 vs 默认值），机器判不出——跳过而不是猜。

4.3 纯叙述性数字不判#

「20 条红线」「6 个阶段」「3 个组件」这类数字没有对应的代码字面量，
本条不管。实测这类在 330 份文档里约 6900 处——占了绝大多数。

4.4 布尔型常量不判#

KHY_X = 1 表示「开关打开」，不是可比的数值。实测这类占常量主张的大头
（KHY_CC_TUI 46 处、KHY_SELECT 16 处、KHY_FAST_STARTUP 16 处……），
全部取值 0/1。把它们算作漂移会把守卫变成噪声源。

五、覆盖面与局限#

覆盖不覆盖
文档写下「同名常量 = 数值」且代码里该常量值唯一的情形运行读数类（R1=28、门禁 exit 0）——需重跑，白名单登记后才可判
文档引用了失效行号纯叙述性数字（约 6900 处）
——布尔型常量（取值 0/1）
——同名多值的常量

实测可判定率 43/83 ≈ 52%——即约一半的常量型数值主张机器能判，
另一半（同名多值、布尔型、代码里根本没有该常量）留给人工。
这个比例说明：数值漂移不是「全部可机检」，但有一部分是，
而这一部分恰好是最容易出错的那部分（多个文档引用同一常量却各自记着
不同值——它们的过期时刻各不相同，天然会分叉）。

六、落地阶段与升阶#

STAGE = 'S1'：观察者，只记录不阻断、恒 exit 0（[DESIGN-PROCESS-002] PP-1）。
升阶须同时改三处：scripts/ci/check-doc-numbers.js 的 STAGE、
RULES-REGISTRY.json 中 DOCS-007 的 severity、FEATURE-OWNERSHIP.json
中 doc-numbers-guard 的 stage。一次一阶（PP-6），由人决定。

severity 必须显式写 advisory——check-rollout-stage.js:197 的 PP-3
会复算 gateStrength()，未声明时 P1 会派生为 blocking 而报 error。

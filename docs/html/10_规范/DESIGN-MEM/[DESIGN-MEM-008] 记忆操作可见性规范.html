3. 方案#

3.1 分层决策：复用既有 noticeInbox，不新造通道#

不要再往 onStatus({phase:'init'}) 里塞更长的字符串（那是 F4/F5 的加深）。
既有 services/backend/src/cli/tui/noticeInbox.js 正是为这个场景设计的：

// 契约（noticeInbox.js 头注）
//   push(line) 返回 true = 已有人在屏幕上安置它
//                 false = 无人认领，调用方**必须**回到旧行为。绝不静默丢弃。

它是 TUI 侧「宿主想让用户看见、但不能自己写屏」的收件箱（BUG-17 产物），
订阅点已存在于 ink-components/App.js:2308，落成 role:'notice'。

处方：把记忆告知语从「状态通道」迁到「notice 通道」，并保留状态通道作降级。

memoryOpsNotice.formatRecallNotice(filenames, ctx)   ← 纯叶（已有，扩展签名）
        │
        ├─→ noticeInbox.push(line)        主通道（TUI：落 role:'notice' 持久行）
        │      │ 返回 false（无订阅者/门关）
        │      └─→ 回落到 onStatus        降级通道（REPL：走既有渲染）
        └─→ （若既不认领又无 onStatus）→ 不输出，且**不得**静默吞掉观测

⚠ 纪律：noticeInbox.push() 返回 false 时不许当作成功。这是本仓
「闸挂在哪层决定它管不管」的同类陷阱——push 返回 false 表示没人接。

3.2 V2「用以完成什么」的派生规则（纯叶、确定性）#

来源：按用户选择，从召回结果反推，不依赖模型自述。

memoryOpsNotice 新增纯函数 deriveIntentClause(ctx)（ctx 形如 { types: string[] }）：

输入输出「为了…」子句
召回含 project/reference 型为了对齐项目约定 / 为了查证外部资料
召回含 feedback 型为了遵守你此前给过的协作偏好
召回含 user 型为了沿用你的既有设定
混合 / 未知取首个命中型的标签；全空 / 无 ctx → 省略子句（绝不编造）

⚠⚠ type 的取数口径（实现者必读，取错即静默失真）：
必须取 frontmatter.type，不得按文件所在目录推断。取证（2026-09-24）：

事实证据
存储是扁平的，写入不建 type 子目录memdir.js:508/562 path.join(memoryDir, filename)；真源 memdir/paths.js（<root>/.khy/memory/）
召回结果同时带 filename 与 frontmattermemdir.js:689 scored.push({ filename, frontmatter, body, score })
filename 是纯文件名（不含路径）memdir.js:382 return { filename, filepath } 两者分离

⇒ 按目录推断 type 会得到 unknown（根目录文件）或错型（user/ 例外）。
deriveIntentClause 不接收路径，只接收已汇总的 types 数组。

⚠⚠ 措辞纪律（V4 的强要求，实施时最易违反）：
意图子句在既有文案中只做「插入」，不得改动任何既有字符。
真源原文是 召回 N 条相关记忆：… ——
不得顺手改成「回忆起」「回忆到」「记得」等更"自然"的词。
理由：ctx 缺省时整行必须与今日逐字节相等（见下方原型验证），
改词即等于在"回退"路径上也改了输出，V4 不成立。
经原型实测，把「召回」写成「回忆起」会使 6/6 输入全部 diff —— 这是真实踩过的坑。

渲染样例（确定性、可单测断言；注意动词是「召回」）：

召回 2 条相关记忆（为了遵守你此前给过的协作偏好）：feedback_tool-execution-results、feedback_system-收尾保障

诚实边界：意图子句是类型标签的派生陈述，不是对模型真实动机的断言。
措辞用「为了…」而非「因为你需要…」——不替用户/模型宣称动机。

3.2.2 可选加固：字符串入参应 fail-soft（非本次必须，建议顺手修）#

原型实测发现的既有行为（非本规范引入）：formatRecallNotice 的契约声明入参是
Array<string>|Set<string>，但实现（:119）接受任意可迭代对象：

} else if (filenames && typeof filenames[Symbol.iterator] === 'function') {
  list = Array.from(filenames);   // ← 字符串也可迭代 ⇒ 被逐字符拆开
}

实测后果：'bad' → 召回 3 条相关记忆：b、a、d；
'a.md' → 召回 4 条相关记忆：a、.、m 等 4 条。

当前不是活的 bug——唯一调用点 aiChatCore.js:2333 传的是 _memSurfaced（Set），
永远命中 Set 分支。但它与本仓「低精度守卫比没有守卫更糟」同族：
宽容的归一化让畸形输入产出荒谬输出，而不是 fail-soft 返 ''。

建议（可并入本次改动，也可另开）：在可迭代分支前加
typeof filenames === 'string' 的判断 → 规范化为 [filenames] 或直接返 ''。
⚠ 若改，必须同时更新契约注释，否则注释与实现继续背离。

3.5 V5 过程态：spinner 显示「正在回忆…」（进行时）#

新增判据 V5：主动记忆不能只有事后一行结果，必须同时有进行时的过程——
在回忆发生时 spinner 本身改文案并继续转动，用户看到「正在回忆相关记忆…」，
而不是只在结束后弹一行。

§3.1–§3.4 解决的全是结果态（召回完成后告知「召回了什么、用以完成什么」）。
但召回发生在发请求之前，而既有的 onStatus 在该时段只有 phase:'request'
⇒ spinner 显示「请求上游模型」 ⇒ 回忆过程完全不可见。

3.5.1 范式：复用 compacting / compacted 的「过程态 + 终止符」#

本仓已有同类问题的正解（aiChatCore.js 的压缩）：过程态必须配一个终止符，
代码注释里明写「缺终止符 ⇒ 进度条永久留屏」。V5 照搬该范式：

态phasestage语义
过程态memory-recallstarting开始回忆（spinner 切文案，继续转）
终止符memory-recalldone回忆结束（spinner 切回常规文案）

3.5.2 硬约束（缺一即退化或留屏）#

#约束违反后果
C1starting 与 done 必须成对发出缺 done ⇒ spinner 永久停在「正在回忆…」（同 compacting 无 compacted）
C2起始点必须在 require('../services/memoryEngine') 成功之后引擎不可用时发出「无终止符的过程态」⇒ 留屏
C3终止符必须在 finally 里发异常/早退路径漏发 ⇒ 留屏
C4过程态不停 spinner、不落持久行与结果态混淆；过程态是「改文案」不是「新增一行」
C5文案单一真源 RECALL_PROCESS_TEXT（memoryOpsNotice.js）三处消费者各写一份 ⇒ 漂移后「改文案即破回退」（V4 同族教训）
C6判别用 phase/stage 字段，不用文案前缀低精度判据；文案一改即静默失效（§5 反模式）

3.5.3 最短可视窗口（否则过程态根本看不见）#

⚠ 这是 V5 最容易漏的一条：REPL spinner 的 _render() 每 120ms 才重绘一帧
（KHY_SPINNER_INTERVAL_MS），而真实召回常几十毫秒就结束。
若不等下限，starting 会在下一帧到来之前就被 done 切走 ⇒
代码全对、测试全绿，但用户一帧都看不到。

项值
门KHY_MEMORY_RECALL_MIN_MS

## 三、四个阶段与出口条件

> 单人产能下的排序原则：**低成本高确定的先做，高风险需测试背书的后做，防守性的持续做**。
> 每个阶段的出口条件都是**可证伪**的——达不到就不进下一阶段。

**改了什么**：
1. **新纯叶子 `src/services/gateway/conditionalRoute.js`**（约 190 行）：零 IO、零 require、绝不抛。

   - `matchConditional`：顺序命中即返回，未命中走 `default`，两者都无 → `null`

2. `src/services/gateway/autoModelRouting.js`（+约 40 行）：在 `rank()` 里接入，经 `opts.conditional` 可选开启；返回值新增 `conditional` 读数（`applied`/`target`/`via`/`matchedCount`）

**两个设计决定，都是被测试当场教出来的**：
- **优先级提升而非硬过滤**：Portkey 的 `then` 是「只走该 target」，由 fallback 链兜底；khy-os 暂无该链，硬过滤会在 target 不可用时**掏空池子**。提升的语义是「条件命中时优先这个 provider，它不可用就自然落到后面」——意图一致，且永不掏空。
- **必须排在 `rankAutoModels` 之后**：第一版把提升放在输入侧，测试当场抓到 `ranked[0]` 仍是分数最高的那个——`rankAutoModels` 会按自己的分数重排，输入侧调序被整个丢掉。这是「加一个可选轴」最典型的死法。

**另修叶子一处**：空 query `{}` 最初被实现成 vacuously true，一条漏写 query 的条件会**永远命中**并把全量流量导向它的 `then`。改为不命中。

**验收（14/14 全绿）**：
- **不给 `opts.conditional` ⇒ `conditional` 读数为 `null`**（不是空对象——消费方要能区分「没开」与「开了没命中」）
- **不给 conditional 与 给一个无命中且无 default 的 conditional ⇒ `ranked` 逐字节一致**（JSON 深比较）
- `conditional` 不是对象（如字符串）⇒ 按没给处理，不抛、不改位次
- 命中时 `ranked[0].adapter === target` 且读数可观测
- `default` 指向不存在的 adapter ⇒ `applied:false` 但**池子不掏空、winner 仍在**
- 不认识的算子 / 坏正则 / 空 `$or` / 非标量比较 ⇒ 一律不命中，绝不抛

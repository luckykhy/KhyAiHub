# 长任务偏离与完成判据缺失 — 取证与方案提案

> 状态：**已落地（2026-09-23 当日）**。落地记录见文末「七、落地记录」；交付以
> `.ai/hq/PROGRESS.json` 的 T-024（review，evidence=T-024-acceptance-gate）为准。
> 依据：2026-09-23 对 `.ai/hq/`、`services/backend/src/cli/`、`scripts/ci/` 的只读取证。
> 所有结论均可按 file:line 复核。

---

## 一、先说结论

**你以为的问题是「任务会偏离」。实测出来的问题是：任务在离开你的视野后，没有任何机制知道它已经死了。**

`khy hq verify` 当前报 `0 error / 0 条 warning`。而同一时刻，仓里有 3 条任务正卡在
中间态、2 条任务的目标真源文件根本不在仓内、3 条 Bug 进入待验证时零留痕。
**体检全绿，任务在死。** 这不是"判据不够严"，是**判据查的对象错了**——
它查的是「数据格式是否自洽」，你关心的是「任务是否还在朝目标走」。

所以方案要修的不是 `acceptance` 字段的质量，而是**三个当前的零点**：

| 零点 | 位置 | 后果 |
|---|---|---|
| 没有「任务←→改动←→存证」的绑定 | `hqStore.js:674` `validateTask` 只看枚举/格式 | 存了 52 个证据目录，**没有一个指向任务** |
| 没有「doing 任务还活着吗」的判据 | `hqStore.js:773` 只查 `review/done` 带占用 | `T-020`/`T-021` 挂 4 天无人知 |
| 没有「验收标准是可执行的」这个要求 | `hqStore.js:674` 不校验 `acceptance` 内容 | 判据是散文，AI 可以"读懂了"然后翻状态 |

## 二、证据

### 2.1 三条悬挂任务（最直接的实证）

`.ai/hq/PROGRESS.json` 中 `doing` / `review` 的 3 条，**全部无 `claimed_by`、无 `lease_expires`**：

| ID | 状态 | 优先级 | updated | notes | 停滞 |
|---|---|---|---|---|---|
| `T-020` | doing | P2 | 2026-09-19 | 1 | 4 天 |
| `T-021` | doing | P2 | 2026-09-19 | 1 | 4 天 |
| `T-023` | review | **P1** | 2026-09-20 | 2 | 3 天 |

`T-023` 是 P1，`review` 卡 3 天。它的第二条备注结尾写着：

> 「至此 T-023 **机器可验证面全部闭环**，done 翻转**待人工确认**。」

—— 机器已经做完了它能做的一切，剩下一步在等人。**没有任何东西会提醒你这件事**。
`khy hq status` 会把它算进"待验收任务"计数（`handlers/hq.js:178`），但那只是一个数字，
不会拦你、不会催你、不会告诉你"它停了"。

### 2.2 目标真源被指向一个迁移中消失的路径（T-020 / T-021 的真正病根）

`T-020` 的验收第 1 条：

> 「严格按 `_meta/SPLIT-PLAN.md` 批次协议执行」

`T-021` 的验收第 3 条：

> 「C3+ **按 SPLIT-PLAN** 工厂模式逐阶段拆分」

实测：

```
services/backend/src/cli/_meta/SPLIT-PLAN.md        不存在
services/backend/_meta/SPLIT-PLAN.md                不存在
_meta/SPLIT-PLAN.md                                 不存在
在 services/backend + docs + .ai 三层递归搜索 SPLIT-PLAN  →  仓内零命中
```

对应的 `T-020` note 已经自己承认了这件事：

> 「`_meta/SPLIT-PLAN.md` **在仓内已不存在**（仅存 HQ 归档
> `D:/Portable/BuildArtifacts/hq-archive-2026-09-17/SPLIT-PLAN.md`）……
> 恢复执行前**需把 SPLIT-PLAN 从归档救回仓内**。」

但**它其实早就被救回来了**——以另一个名字、在另一个地方：

```
docs/08_MGMT_项目管理/MGMT-PLAN/[MGMT-PLAN-008] replSession与toolUseLoopCore拆分分批计划.md
```

该文件首行自称 `# SPLIT-PLAN.md`，105 行，含完整批次表 B1–B11 / C1–C3+。
`T-020` 的备注把**「文件不存在」和「文件改名了」这两种情况混为一谈**，
于是任务被判成"恢复执行前需救回真源"，卡了 4 天。

同时 `T-021` 的终点判据写的文件路径也不对：

| T-021 验收写的 | 实测 | 真实位置 |
|---|---|---|
| `toolUseLoopCore.js` ≤800 行 | 仓内**有两个** | `services/backend/src/services/tool/toolUseLoopCore.js` = **10313 行** |
| | | `services/backend/src/services/toolUseLoopCore.js` = **2 行** |

**一个指向工具函数真源、一个指向两行转发壳。判据没有说清是哪个，就无法机器核对。**

**这一条是全场最便宜的胜利：**
把 `T-020`/`T-021` 的 `acceptance` 里的 `_meta/SPLIT-PLAN.md` 改指
`docs/08_MGMT_项目管理/MGMT-PLAN/[MGMT-PLAN-008] …md`，并写明 `toolUseLoopCore.js` 的完整路径，
这两条任务当场从"真源丢失、无法恢复"变成"有作战地图、可以继续"。

### 2.3 「完成判据」的实证规律：有命令的验收才完成，纯散文的验收会悬挂

我把 23 条任务按「`acceptance` 里有没有可执行命令」分组：

| 分组 | 条数 | done | doing | review |
|---|---|---|---|---|
| **含明确命令**（`npm run` / `node scripts` / `npx` / `khy `） | 14 | 5 | 0 | 0 |
| **不含命令**（纯描述性验收） | 9 | 0 | 2 | 1 |

**5/5 已完成的任务全部落在"有命令"组。3/3 悬挂的任务全部落在"无命令"组。**

这个样本小，不敢说因果。但它指向一个具体机制：**验收里有没有一条能跑的命令，
决定了验收能不能被机器执行——不能机器执行的验收，只能靠人，而人会忘。**
`T-020`/`T-021` 的 `npx jest 四数不劣化` 是好判据，但被埋在第三、四条，
前两条是"按 SPLIT-PLAN 执行"这种无法执行的散文；执行者卡在散文上，好判据没机会生效。

### 2.4 Bug 侧同样零留痕

13 条 Bug：`closed 7 / open 3 / pending_verify 3`。

`BUG-009`、`BUG-011`、`BUG-013` 三条处于 `pending_verify`（待验证），**`notes` 全部为 0 条**。

也就是说：修复完成 → 进入待验证 → **没有记录"验了什么、怎么验的、谁验的"**。
`closed` 组里 `BUG-004` 的 `root_cause` / `fix_summary` 为空也照关不误。

而仓库里**已经有**一份写得极其到位的验证提示词 ——
`.ai/hq/prompts/bugfix/02-回归验证.md`：

> 【角色】你是一名苛刻的 QA 工程师，任务是**证伪**一个声称已修复的 Bug。
> 你的职责是找出它仍然坏的理由；找不出才允许通过。
> 5. 结论只能是二选一：PASS：列出你做过的**每一项验证及结果证据（命令输出摘要）**。

**提示词要求输出证据，但没有任何地方接收这个证据。** 要求发出去了，回执没有落点。
这跟 `check-agent-feedback.js` 的处境一模一样——见 2.6。

### 2.5 已有的存证机制是**完好的**，只是没接到任务上

这一条是反直觉的，也是方案可以很轻的原因。

`.khy/feedback/` 实测：**52 个目录，0 个空**。内容质量相当高：

而且 `check-agent-feedback.js` 的判定逻辑是**真的在判**（不是空转）：

各自要求不同文件；`readEvidence` 读不到就判 `fix-without-repro` /

## 三、根因

把上面五条证据串起来，根因是**一条**，不是两条：

```
任务状态机（hqStore.js）跟改动存证（.khy/feedback/）之间没有契约。

  ┌─ 入口 ─────────────┐        ┌─ 过程 ─────────────┐        ┌─ 出口 ─────────┐
  │ hq next 挑任务      │        │ AI 干活             │        │ task set done   │
  │ 渲染提示词          │        │ 存 .khy/feedback/   │        │ 裸命令，无前置  │
  │ acceptance 塞进去   │        │ 目录名靠手工拼      │        │ 无需任何证据    │
  └────────────────────┘        └────────────────────┘        └────────────────┘
         ▲                               │                              ▲
         │                               │ 无绑定（零 feedback 提及）    │
         └───────────────────────────────┴──────────────────────────────┘
```

- **「偏离」的根因**：任务只锁了「目标」（`acceptance`），没锁「边界」——
  没有「不做什么」清单，没有中期对账点。而 `T-020`/`T-021` 的 `acceptance` 还把目标
  指向了一个**迁移中丢失路径的**文件，导致"目标"本身失真。
  `RUNTIME-008` 的 BUILD 五问里本来就有第 4 问「成功长什么样？（命令 + 期望输出）」
  和第 5 问「**不做什么**」—— 但这套问法只在**改动级**生效（`--changed` 扫 git diff），
  **任务级从未用过**。
- **「完成无判据」的根因**：`review → done` 是 `TASK_TRANSITIONS` 里的一个裸箭头
  （`hqStore.js:114` `review: ['done', 'doing']`），`validateTask` 不检查任何证据。
  判据存在（`acceptance` 字段 100% 填写），判据执行不存在。

## 四、办法

一句话：**不造新机制，只把已经存在的两端接上。**

四个动作，按性价比排序。

### 动作 1（零成本，今天就能做）：把 `T-020` / `T-021` 的判据改指真实路径

`_meta/SPLIT-PLAN.md` → `docs/08_MGMT_项目管理/MGMT-PLAN/[MGMT-PLAN-008] replSession与toolUseLoopCore拆分分批计划.md`；
`toolUseLoopCore.js` 写明完整路径 `services/backend/src/services/tool/toolUseLoopCore.js`。

**效果**：两条挂了 4 天的任务从"真源丢失"变成"可继续"。
**顺带**：这暴露出一个**通用病**——`acceptance` 里的路径引用**从不被校验**，
文档改名/迁移后判据就静默失效。这正是"长任务偏离"的一种具体形态：
**不是 AI 走偏了，是路标被搬走了而没人知道。**

### 动作 2（核心，约 1 天）：给任务加 `evidence` 字段，让存证有落点

在 `PROGRESS.json` 的 task 上加一个可选字段，复用**已有**的 `.khy/feedback/<task-id>/` 契约：

```json
{
  "id": "T-023",
  "status": "review",
  "acceptance": "…",
  "evidence": "T-023-keymanager",
  "scope_guard": ["不改 services/backend 以外", "不动 keyStore 的对外契约"],
  "baseline_metrics": { "jest_suites": 1231, "jest_failed": 24 }
}
```

- `evidence`：**显式**指向 `.khy/feedback/<dir>/`，替掉"目录名靠手工拼"。
  命名约定改为 `<task-id>-<slug>`（如 `T-023-keymanager`），
  存量 52 个目录**不追溯、不改名**（`validateTask` 对可选字段"出现即校验，存量不追溯"
  是仓里已有的范式，见 `hqStore.js:691`）。
- `baseline_metrics`：**强制"不劣化"类判据有基线数字**。
  `T-020` 写「jest 四数不劣化于批次前基线」，但基线数字不在任务里——
  **"不劣化于批次前"这句话本身不可机器核对，因为没人记得批次前是什么数字。**

### 动作 3（核心，约 1–2 天）：`review → done` 加前置校验

把 `hq hq task set <ID> done` 从裸命令改成**需要附验收清算**。
判定复用 `khy hq next` → `khy hq verify`（**只读**，不新增检查器、不进 `scripts/ci/`，
因此**不触发 `check-wiring.js` 孤儿判定、不需要门引用、不新增规则 ID**）。

要点，全部是仓里既有做法的搬用：

1. **按 `acceptance` 分句逐条要结果**。23 条任务的 `acceptance` 已用 `；` 或 `1) 2) 3)`
   分句（实测：`T-001` 5 句、`T-013` 6 句、`T-014`/`T-015` 7 句）。
   分句是可解析的——`hq command` 逐条打印，要求 `[PASS/FAIL/SKIP:理由]`。
2. **`evidence` 目录必须存在且非空**（沿用 `readEvidence` 的读法：trim 后非空才算数）。
3. **对含数字的判据做机器核对**。`T-020` 的「≤800 行」、`T-023` 的
   「jest 四数」都是可算的。`baseline_metrics` 有值就自动 diff，
   没值就要求人工填空——**先让"不劣化"这句话有数字**。
4. **`SKIP` 必须带理由**，理由进 `notes`。防止"逐条勾选"退化成"逐条打勾"。
5. **状态机保持硬约束**：`canTransition` 仍是唯一裁决点（`hqStore.js:16` 的自我要求）。
   加的是**迁移前置条件**，不是新状态。

**为什么不做成 CI 检查器**：这个判据查的是 `.ai/hq/` 的状态，
而 `.ai/hq/` 是**多机共享的任务账本、按天变动**，不是代码。
把它做成 commit 门会让"改任务状态"变成阻塞式操作，反而促使用户绕过。
**放在命令路径上**——这也正是 `hqStore.js:646-650` 已经写明的裁决：

> 「`meta` 不升级成仓库级门禁，而是**降级为命令写入路径校验** ——
> 「能落在命令写入路径上的约束，就不要升级成检查器」。」

同一条裁决，直接适用。

### 动作 4（真正的"防偏离"，约 0.5 天）：把 BUILD 五问从"改动级"提到"任务级"

`RUNTIME-008` 的五问已在 `.khy/feedback/<id>/requirement-5q.md` 落地，
含"第 4 问成功长什么样（命令+期望输出）"和"第 5 问不做什么"。
现在**只在 `--changed` 判定到 BUILD 模态时**才要。

动作 2 的 `scope_guard` 字段就是五问的"不做什么"部分**在任务级**的落地：
任务开工（`todo → doing`）时要求填 `scope_guard`，执行中任何改动**越出 `scope_guard`** ，
下次 `hq next`/`hq status` 时**报出来**（不拦、不判错，只是让"偏离"变成可见）。

**"可见"就够了**。实测中 `T-020` 的目标真源丢了 4 天没人知道——
问题从来不是"没人管"，是"没人知道"。

## 五、这条路别走（反模式）

以下四条，每一条都是**这个仓库已经踩过的坑**，按 `[DESIGN-DELIV-001]` 的记录照抄：

1. **别把新判据做成恒 exit 0 的记分板。**
   §1.2 已记录 `check-zcode-baseline.js` 的教训：打印 7 PASS 但恒返回 0。
   本方案的验收清算走 `khy hq` 命令，**必须在 `done` 那一刻返回非零并拒绝**，
   给出可复现的 `--scenario` 演示，并做**反向验证**：故意让一条 `acceptance` 不勾选，
   确认 `task set done` **真的被拒**。做不到这一步，就是又造了一个 §1.2。

2. **别把机制停在 S1 墓碑。**
   §1.3 已记录"登记为观察者后从未结算"。`check-agent-feedback.js` 就在墓碑上（`STAGE='S1'`）。
   本方案**不复刻**：它不登记为 S1 观察者，**从第一天就是命令路径上的硬返回**。
   如果非要选阶段，就明说"命令路径校验不参与 rollout 分阶"，
   因为 rollout 分阶是为**跨仓库的自动门**设计的，命令路径校验的"最小可行强度"
   就是"拒绝写入"，从 S1 开始没有意义。
   ⚠ 这一条如果走 `RULES-REGISTRY.json` 登记，需要按 `[DESIGN-DELIV-001]` §4.3
   的论证路径处理：**"复用已验证机制 + 引用权威外部判定 ⇒ 不构成新建机制"**。
   本方案的判定完全复用 `EVIDENCE` 契约与 `readEvidence`，属于复用。

3. **别只加字段不进流程。**
   `cod` / `conf` / `size` 是现成的反面教材：字段定义了，`validateTask`（`hqStore.js:692-700`）
   也校验了，**23 条任务一条都没填** ⇒ `PROCESS-102` 的档内评分决胜**从未生效过一次**，
   任何同档并列必然落到 G4 问人。
   **所以动作 2 的字段必须和动作 3 的校验同批落地。只加 `evidence` 字段不加校验，
   就是再造一个 `cod/conf/size`。**

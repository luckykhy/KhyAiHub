# [DESIGN-LOG-002] 手机端日志规范

> **定位**：规定 khy-os 手机端 APK（Flutter 客户端）的日志形态与查阅方式。
> **边界**：服务端日志由 [`[DESIGN-LOG-001]`]([DESIGN-LOG-001]%20日志规范.md) 管辖，本条不重复其内容。
> **结论**：按天分文件、错误优先、未捕获异常必落盘、导出包自足——四条让「用户报障 → 研发定位」不靠来回追问。

---

## 一、概述

手机端的日志有两个读者：**用户**（遇到问题要能自己看一眼）和
**研发**（拿到日志要能直接定位）。两者的诉求相反：用户要的是「哪一天出错了」，
研发要的是「错在哪一行」。所以格式以机器可读为底，界面以错误为顶。

摘要：

| 项 | 约定 |
|---|---|
| 落盘 | 按天分文件，一行一条 JSON（JSONL） |
| 错误 | error / fatal 双写：主文件保上下文，错误投影文件供快速检索 |
| 崩溃 | FlutterError / 异步错误 / Zone 错误三处必装钩子 |
| 留存 | 保留 14 天；单日超上限后只留警告与错误 |
| 查阅 | 设置 → 诊断工具 → 日志查看：先看哪天，再看错在哪 |

---

## 二、五条红线

| # | 红线 | 判据 |
|---|------|------|
| R1 | **按天分文件**：一天一个文件，文件名带日期 | 不得写进单一无限增长的日志文件 |
| R2 | **错误双写且跨天可查**：error / fatal 条目除主文件外必须进错误投影文件 | 进程重启后仍能按天检索到历史错误 |
| R3 | **未捕获异常必须落盘**：FlutterError、PlatformDispatcher、Zone 三处都要装钩子 | 崩了但日志里没有，等于没崩 |
| R4 | **错误必须结构化**：带错误码、级别、上下文、原始异常、堆栈 | 一句「出错了」不算错误记录 |
| R5 | **导出必须自足**：分析包含版本、平台、错误总览、错误明细与当日日志 | 拿到就能分析，不必再问 |

### 反例 → 正例

| 反例 | 正例 |
|------|------|
| 单文件 `khy-os.log` 无限增长 | `khy-os-2026-10-23.jsonl` 按天分文件 |
| 错误只存在内存里，重启即丢 | 错误投影文件随天落盘，跨重启可查 |
| 只捕获 try/catch 里的异常 | 三处全局钩子兜底，崩溃也留证据 |
| 日志里只有「请求失败」 | `E102` + 错误类型 + 上下文 + 堆栈 |
| 导出一坨裸文本给研发 | 分析包：环境头 + 错误总览 + 错误明细 + 当日日志 |

## 三、日志条目格式

一行一条 JSON，字段缺省即不出现（不写 null 占位）。

| 字段 | 含义 |
|------|------|
| `ts` | 本地时区 ISO 8601 时间戳（毫秒） |
| `seq` | 会话内自增序号 |
| `level` | `debug` / `info` / `warn` / `error` / `fatal` |
| `cat` | 分类：`network` / `dns` / `auth` / `ui` / `config` / `api` / `tool` / `device` / `system` / `unknown` |
| `code` | 错误码（仅错误类条目） |
| `msg` | 人类可读描述 |
| `ctx` | 上下文键值对（界面、模式、耗时、状态码等） |
| `err` | 原始异常文本 |
| `stack` | 堆栈（最多保留调用点若干帧） |
| `screen` | 记录时所在界面 |

级别语义：`debug` 仅开发期输出，`info` 正常操作，`warn` 可恢复异常，
`error` 需关注的错误，`fatal` 致命错误。

---

## 四、错误码体系

前两位是域，第三位是序号。新增错误必须落在既有域内，域用尽才开新段。

| 段 | 域 | 示例 |
|---|---|---|
| E1xx | 网络 | E101 DNS、E102 连接、E103 超时、E104 4xx、E105 5xx |
| E2xx | API | E201 认证、E202 参数、E203 模型、E204 限流 |
| E3xx | 工具 | E301 工具执行、E302 无障碍、E303 截屏、E304 Shell |
| E4xx | 系统 | E401 权限、E402 配置、E403 存储 |
| E5xx | 未知 | E500 |
| E6xx | 客户端 | E601 崩溃、E602 会话失效、E603 设备能力、E604 本地存储 |

---

## 五、留存策略

- 保留 14 天，超期文件在启动时清掉。
- 单日文件体积上限 8 MB；超限后普通条目不再落盘，**警告与错误仍须落盘**。
- 迁移前的旧版文本日志（`khy-os.log`）保持可读，界面单列一条，不做格式转换。

## 六、界面契约

| 位置 | 约定 |
|------|------|
| 入口 | 设置 → 诊断工具 → 日志查看 |
| 天列表 | 每行一天：今天 / 昨天 / 日期 + 错误条数 + 体积；当天有错则带红标与计数徽章 |
| 详情页 | 默认落在「错误」页签；「全部」页签可按级别筛、按关键词搜 |
| 错误卡 | 错误码、描述、时间、分类、界面、上下文、原始异常、堆栈同屏可见 |
| 操作 | 复制分析包、清空当日、清空全部（均需二次确认） |

## 七、导出：给智能体的分析包

手机端不引入文件分享依赖，导出即「复制到剪贴板」，由用户粘贴给研发智能体。
分析包必须自足，结构固定：

1. **环境头**——导出时间、应用版本、运行平台、设备、日志范围。
2. **错误总览**——按错误码聚合的条数与含义。
3. **错误明细**——逐条列出时间、分类、上下文、原始异常、堆栈，按时间倒序。
4. **每日日志**——当日全部条目，按时间顺序。

拿到这段文本的人不必再问「哪个版本」「哪天出的」「错在哪」。

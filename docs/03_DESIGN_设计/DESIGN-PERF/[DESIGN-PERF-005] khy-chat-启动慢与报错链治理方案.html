零、一句话结论#

用户报的三件事（慢 / 报错 / 动画不好看）是三个独立缺陷，根因不在一处，但都收敛在同一条启动链上：

用户感知真根因关键判据
慢（约 90s 卡在 83%）管理台 web 后端（server.js）冷启动 initDatabase ~90s，而它串在 daemon 链上；khy chat 的等待预算跑不满它日志 09:51:30 启动 Web 后端 → 09:53:02 已就绪 = 92s；WEB_BACKEND_WAIT_MS=120_000 vs CLI 预算 180_000（余额仅 88s）
报错（MCP 超时 + 守护自杀）① deepseek-eyes 是可选工具（python -m deepseek_eyes），冷启偶发 >30s 被硬超时；② 守护的 startup-timeout 标签名不副实 —— 实为「启动宽限 600s 内零会话」，与启动快慢无关.khy/mcp.json 定义；mcp/index.js:448 硬超时；ai-manage-daemon.js:986-990 判定分支
动画不好看进度条百分比的时间模型已改对（percentAt 平滑），但渲染节拍仍是 250ms 离散重画 + spinner 80ms；且 ink 首帧渲染期整块阻塞主线程，期间任何渲染器都动不了bootPhaseLine.js:55 PERCENT_TICK_MS=250；BootScreen.js:56 FRAME_MS=80；app.js:345-368 的两段 render

核心判断：这三件事不该由「启动链并行化」治 —— 那是大改。最小代价的最高收益是两刀：
(A) 把 server.js 的非关键后台初始化移出健康判据（让 web 后端 ~1s 就 /api/health 200），
(B) 把 MCP 自动连接与守护存活彻底解耦。
动画（C）是独立的观感项，可单独立项，与 A/B 无依赖。

1.3 本次实测的「结构事实」探针输出（判据，非耗时）#

探针：临时 hook Module.prototype.require，检查 ReplSession 启动图中是否出现重依赖。

require(commandAutoRegistry)  =   2.9ms
require(replSession)          = 206.2ms
winstonEagerlyLoaded          = false      ← 【判据】winston 未被 eager 拉入
inkLoadedDuringRepl           = false      ← 【判据】ink 未在 replSession 图内
inkColdTouchMs                = 1020~1080ms（ESM 动态 import）
appModuleLoadMs               = 434.5ms

结论：「启动慢」不能归因于 require 图。本次实测 khy version 3 轮 1937 / 3006 / 3807ms（方差极大，含 Python launcher ~600-1200ms），khy chat 3087~9167ms —— 即 CLI 自身在 3~9s 内走完，而用户感知的「慢」是之后卡在 daemon 段（92s + 28s MCP）。

测量方法论声明（沿用 [DESIGN-PERF-003]）：本机耗时抖动极大（同配置 394~939ms），故本文以「结构事实」为主判据（布尔量），耗时仅作参考并标注方差。

三、目标形态#

3.1 病灶 1（慢）：web 后端「就绪」判据与「后台初始化」解耦#

⛔ 实施阶段更正（2026-10-01）：本节假设 已被证伪#

本节原文把 92s 归因为「DB / 后台初始化挡住 health 端点」。A0 探针实测推翻了它：

initDatabase()             =    82ms   ← 不是它
AKShare 标注同步            =  3100ms   ← 不是它（方案 §1.2 事实 3 的 29s 是本机冷启噪声/口径差）
require(instrumentService) = 45920ms   ← 【真凶，占 92s 的一半】

真根因链（file:line 可复核）：

server.js 后台初始化 → eager require → domain/extensions/.../quantApp.loadModule(...)
→ software/khyquant/services/instrumentService.js:6 require('./pythonDataSourceService')
→ pythonDataSourceService.js:629 module.exports = new PythonDataSourceService()
⇒ 模块加载即构造 ⇒ 构造函数调 findPython()
⇒ utils/pythonPath.js:202（canRunPython）对每个候选 execSync spawn 一次 python
⇒ 本机单次 python -c "pass" 实测 3.8–7.8s（Defender 扫描税）
⇒ 多候选累加 = 45.9s 白等，且与业务毫无关系。

实际修法（与本节的 health/ready 解耦不同，见 §10 实施记录）：

  1. pythonPath.js：canRunPython 加 fast-path（绝对路径 + 文件存在 → 采信，不 spawn），

开关 KHY_PYTHON_TRUST_PATH（默认开）。

  1. 三个 service 的 pythonPath 改惰性 getter，模块级 new 改懒 Proxy。

本节的 health/ready 解耦仍然有价值、但降级为「次要」：它治的是「daemon 等业务级判据」，
而实测 listen 后约 8.3s 就已 服务器已就绪，真正的 45.9s 在 listen 之前的模块加载里 ——
也就是说即使把 health 解耦做满，不改 python 解析时机，92s 仍有 ~46s。
详见 §10：/api/ready 已按本节设计落地（保留语义分离），但主收益来自根因修复。

现状病灶：/api/health 的语义被后台初始化绑架 —— daemon 的 probeWebBackendHealth 探测的是「后台初始化是否完成」而非「服务是否可服务」。

⚠ 诚实边界：server.js:784-799 显示 listen() 在后台初始化之前、并已打印「服务器已就绪，后台初始化中...」。因此代码层面 listen 确实先行；但实测 /api/health 直到 09:53:02 才返回 200（web_backend.log），说明健康端点实际等到了后台初始化完成（或其 handler 依赖了尚未就绪的 DB/sequelize）。具体卡点已在实施阶段用探针钉死（见上「实施阶段更正」与 §10）。

目标形态：

web_server（server.js）：
  listen()                       → 立即 /api/health 返回 200 {status:'ok'}      ← 只反映「进程活着 + 路由挂载」
  /api/ready                     → 200 需 DB 就绪 + 迁移完成                    ← 新增，反映「可承载业务」
  后台初始化（DB/迁移/种子/AKShare）→ 全部 fire-and-forget，不阻塞上述两个端点

daemon（ai-manage-daemon.js）：
  等待 web 后端用 /api/health（快，~1s）→ 不再用业务级判据
  若需业务就绪 → 异步补一个 /api/ready 轮询，**不阻塞启动链**

关键约束：/api/health 的语义变更必须与既有消费者对齐。当前消费者至少包括 check-health 系路由（server.js:668）、server.js:672 存活探针、daemon probeWebBackendHealth、可能的外部探活。这是一个「改语义」的动作，必须先做 §7.1 A0 的消费者普查（见 §6 风险 R1）。

收益：daemon 链上 92s → ~1~3s（实测 /api/health handler 自身 22ms）。

3.2 病灶 2（报错）：MCP 自动连接与守护存活解耦#

现状病灶：deepseek-eyes 是可选工具，但它的连接失败会在用户终端打出一行红字 ✗ ... timed out after 30000ms，且失败轮次让整条启动观感更差；同时守护的 startup-timeout 标签误导 —— 用户把它读成「启动超时」，实际是「600s 内没有任何浏览器会话接入」。

目标形态：

项改法
MCP 失败文案从 ✗（错误）降级为 !（降级/可选），并明确标注「可选工具，不影响使用」；失败详情收进日志，终端只留一行
MCP 连接预算保留 30s 单 server 上限，但加整段墙钟上限（[DESIGN-ARCH-169] §0 病灶 6 同款建议），避免多 server 串行累加
startup-timeout 标签改名不改 key（与 169 §3.2 处理方式一致）：日志人类可读段改成「启动宽限 600s 内无任何会话接入（非启动失败）」；机器 reason key 保持 startup-timeout 不动（日志 grep 与既有测试匹配它）
守护自杀的可见性自杀前若 phase === 'ready'（即启动早已成功），日志必须写明「启动已成功，此为会话空置回收」 —— 否则用户永远误读为启动失败

依据：daemon 自己已有正确文案（ai-manage-daemon.js:997-1002 的括号注释），但用户看到的是关掉守护进程这半句 + startup-timeout 这个词，误导性来自词本身而非描述。

3.3 病灶 3（动画）：启动屏的「诚实连续」而非「丝滑」#

现状：时间模型已对（percentAt 平滑），但渲染节拍粗：PERCENT_TICK_MS=250（4fps 的百分比）+ FRAME_MS=80（12.5fps spinner），且 ink 首帧渲染期整块阻塞。

目标形态（低风险、可独立落地）：

改法落点判据
百分比重画节拍 250ms → 120msbootPhaseLine.js:55与 PERCENT_CREEP_MS=12000（时间常数）匹配，4fps→8.3fps 可感知更顺
spinner 帧率与规范对齐BootScreen.js:56 FRAME_MS=80⚠ 须先核对 [DESIGN-ARCH-102] §6.4 / perfTunables：PERF-004 已证明此值存在「规范↔实现」漂移，别再加第三源
不承诺 60fps——ink 首帧阻塞是结构性的（app.js:345-368），该窗口物理上动不了；方案承诺的是「进度被诚实、连续地报告」

⚠ 本节与 [DESIGN-PERF-004] 有重叠风险：PERF-004 治「运行期动画节拍」，本节治「启动屏节拍」。实施前须先确认 PERF-004 是否已接线（其状态为「提案（未接线）」）—— 若已接线则本节只做增量，不重复造旋钮。

★ 10.5.1 归因更正：R-b 是承重件，R-a 是次要防线#

实施后做了一轮归因分离（把 KHY_PYTHON_TRUST_PATH 两边都跑一遍），结果推翻了我最初的归因：

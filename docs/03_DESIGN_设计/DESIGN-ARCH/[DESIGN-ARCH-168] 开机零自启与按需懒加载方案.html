[DESIGN-ARCH-168] 开机零自启与按需懒加载方案#

定位：本文只管这一台 Windows 电脑——登录那一刻被谁拉起来了、该不该拉、要用时怎么拉。
本文不管：任何软件内部的懒加载机制、仓库代码的启动性能、khy-os 或任何其他项目的进程模型。
（初稿曾把 khy-os 内部的端生命周期一并写进来，那是另一个问题，已整体删除。）

状态：P3 已执行（2026-09-30 10:34）。11 项全部落地并经独立复核 + 守卫交叉印证。
改动下次登录才生效。账本 machineState: APPLIED，存档 autostart-backup-20260930-103411.json。

配套工具：D:\Portable\Scripts\maintenance\开机自启管理.bat（菜单入口）+ autostart\*.ps1 ×5。
入口选项 1–4 只读，5 才会写系统。

取证时间：2026-09-30。§1 全部数字与本文七处「工具化/执行时才发现」均由当日实测产出。

本文不新增规则，不携带 <!-- RULES-REGISTRY --> 标记。

0. 一句话结论#

开机那 120 秒卡，不是应用太多，是没有任何一份名单负责回答「这些应用值不值得在这 120 秒里启动」。
清单散在四个互不相认的地方（Run 键 / 计划任务 / 服务 / Startup 文件夹），
谁都能往里加，谁都不负责减——包括从来没人在任务管理器里关过任何一项（§1 证据）。

方案是先减法后加法：

不该醒的不醒（减法）→ 醒的用一次就够（按需入口）→ 别让它自己爬回来（自愈守卫）

为什么默认是减不是加：绝大多数开机自启是装软件时写死的，用户从没主动选过。
所以默认减掉，想回一个就回一个，而不是先问「你要加哪些」。

实测结论：登录波内 14 项，建议禁 11 项（7 个 Run + 4 个计划任务），服务层一个都不动。
零新建入口——四个要按需启动的应用开始菜单快捷方式本来就全在（§4.1）。

1. 现状实证（2026-09-30 本机实测，可复跑）#

启动源数量是否抢登录波
Run 键（HKCU 8 + HKLM 1）9是
计划任务 · Logon 触发5是
Startup 文件夹0（用户级与全局级都只有 desktop.ini）否
服务 · StartMode=Auto（非 Windows 路径）18部分（服务在 boot 阶段，早于登录）

1.1 四条必须说清的推论#

① 9 个 Run 项全部处于启用态，且一个都不是用户选的。
StartupApproved 里 8 个 HKCU 项首字节均为 02（启用），HKLM 的 SecurityHealth 为 06（启用）。
这些值是装软件时的默认值——任务管理器「启动应用」页里它们全是绿的，因为没人手动关过。
这说明现状是「全默认」，不是「用户的选择」。 减法的前提就在这里。

② 登录波里只有一个「真·天天用的应用」。
PixPin（截图）是唯一的高频需求项。其余是浏览器预启动（4）、后台更新器（5）、网盘（2）、
安全托盘（1）、本机自定义项（1）。更新器在登录波里启动是纯粹的浪费——更新不需要和用户抢那 120 秒。

③ 服务这一层一个都不动。 18 个 Auto 服务里：
Defender 3 个（关掉丢实时防护）、ClickToRunSvc（Office 更新依赖）、
ToDesk_Service（远程自救通道） 属于 keep；
华为/驱动/音频/系统组件 10 个属于 out-of-scope——卸载禁用是 PC Manager 的管辖范围，不越界；
剩 3 个（AppGalleryService / OfficePLUS Service / edgeupdate）用途需判断，进 need-confirm。

⚠ ToDesk_Service 明确不建议关。 它是「人不在家时能自救」的通道，
关掉等于用一点后台资源换掉一条退路。这个取舍只能由人做，本文只提出、不代劳。

④ 之前记的 StartupApproved 格式有个坑。
HKCU\...\StartupApproved\Run 的启用/禁用字节是 02/03，
而 HKLM\...\StartupApproved\Run 是 06/07。
只读 HKCU 会把 HKLM 项显示成「未登记」——看起来像没被管过，实际是读漏了。
扫描器第一次跑就踩了这个（把 SecurityHealth 报成「未登记」），已改为三处全读。

1.2 逐项建议#

档项禁掉失去什么
killGoogleChromeAutoLaunch_*、MicrosoftEdgeAutoLaunch_* ×3首次打开慢几百毫秒
killGoogleUpdaterTaskUser*（Run + 任务）、QuarkUpdaterTaskUser*（Run + 任务）、QianwenUpdaterTaskUser*（任务）这三个浏览器不自动更新，需手动
demandOneDrive（Run 1 + 任务 1，两个都在登录波里起同一个东西）文件不自动同步、资源管理器左侧无 OneDrive 项
delayPixPin\Autorun（PT3S → 建议 PT10M）快捷键晚 10 分钟可用。本轮不处理（改延迟要重建任务，不和「禁用」混一次改动）

need-confirmWorkBuddy.WorkBuddy、AppGalleryService、OfficePLUS Service、edgeupdate需你判断
out-of-scope华为/驱动/音频/系统组件 10 个不越界处理

3. 抑制手段的选型#

手段做法抗更新器复活可回滚判级
删 / 改名 Run 值直接改注册表项差——装软件/更新器会重写差——没留原始值就找不回来✗ 不用
写 StartupApproved任务管理器「启动」页禁用的同一份数据中——更新器改 Run 不会自动清这个位，但重装/大版本升级可能重置好✓ 默认
计划任务 Disable-ScheduledTask任务级禁用，系统 cmdlet中——同上；-Force 重注册会重置好✓ 推荐
服务 StartMode服务级n/a好△ 需管理员；本轮一个都不用

默认用 StartupApproved，三条理由：
① 它是用户已经在用的机制（任务管理器干的同一件事），不是本文发明的状态；
② 它不改 Run 值本身，所以更新器重写 Run 不会与我们打架——只是会被自愈守卫再关一次（§5）；
③ 恢复成本是一次赋值。

3.1 【工具化时才发现】12 字节不需要猜#

初稿写「完整的 12 字节结构必须实测取样，不凭记忆写死」。写工具时把这句落实了，结论比预想的好：

HKCU OneDrive          : 02-00-00-00-00-00-00-00-00-00-00-00
HKCU Chrome            : 02-00-00-00-00-00-00-00-00-00-00-00
HKLM SecurityHealth    : 06-00-00-00-00-00-00-00-00-00-00-00

本机全部 9 项都是「首字节 = 状态，后 11 字节全零」。

于是执行策略不是「构造一个禁用值」，而是：读出真实存在的 12 字节，只把第 0 位从 02 改成 03，其余 10 字节原样写回。
这比原设想更安全——不构造任何字节，所以即使对 Windows 内部布局的推断有误，最坏结果也只是改错一位，且能被审计发现。
写入走 .NET API 显式指定 RegistryValueKind.Binary（Set-ItemProperty 对 REG_BINARY 的类型推断不可靠，写错类型会让 Windows 静默忽略这个禁用项，表现为「禁了但还在启动」）。

没有 ApprovedBytes 的项一律拒写：那种情况必须先在任务管理器里手动禁用一次，让 Windows 自己生成样本，再重扫。拒写是正确行为，不是失败。

4. 按需入口：本机不需要新建任何东西#

原方案给了「文件关联 / 快捷方式 / PATH shim」三选一。实测后本机四者的入口全都已存在：

应用开始菜单快捷方式指向exe 存在
Chrome✅…\Local\Google\Chrome\Application\chrome.exe✅
Edge✅C:\Program Files (x86)\Microsoft\Edge\Application\msedge.exe✅
OneDrive✅…\Local\Microsoft\OneDrive\OneDrive.exe✅
PixPin✅D:\Portable\PixPin\PixPin\PixPin.exe✅

结论：禁掉的只是登录波里的预热，不是用户的入口。 所以本方案零新建入口——
这比原设计少一步，且少一个「为了少启动东西而多启动一个常驻 launcher」的自相矛盾（§4.2）。

这条也直接消解了风险 R4（关掉后发现「原来我每天都要用」）对浏览器与 OneDrive 的适用性：
它们本来就有入口。

4.1 若将来某项真的没有入口#

优先级：① 文件关联（目标是「文件打开器」时）→ ② 快捷方式（通用）→ ③ PATH shim（命令行用户）。
不选「常驻 launcher 脚本」——它自己也在登录波里，是自相矛盾的方案。

入口若必须自己写，实现要求：幂等（先探，活着就返回，不重复拉起）、单飞（并发共享锁）、
有界等待的是「拉起」不是「运行」（起来就立即返回，绝不等它退出）、诚实报错（不许静默失败或假装成功）。

5. 自愈守卫：没有它，两周后回到原样#

这是最容易被跳过、也最决定成败的一环。 更新器、装软件、大版本升级都会把 Run 项复活。

三段式：① 登录后 +5m 巡检（不是 +3s——此时各更新器刚跑完，复查才有意义）、
② 每日兜底（覆盖「没重新登录但期间被升级复活」）、③ 只读模式先跑一周（只报差异不动手）。

5.1 【工具化时才发现】更新器的名字带版本号，精确匹配必然失效#

GoogleUpdaterTaskUser156.0.8067.0      ← 账本里的名字
GoogleUpdaterTaskUser157.0.xxxx         ← 一次 Chrome 升级后
QuarkUpdaterTaskUser1.0.0.21            ← 夸克升级后
QianwenUpdaterTaskUser1.0.0.7
OneDrive\26.168.0830.0006\OneDriveLauncher.exe

注册表值名和 exe 路径里都嵌着版本号。 所以守卫必须按模式匹配，不能按精确名——
账本因此额外携带 Match 正则字段（由扫描阶段生成）。

5.2 守卫的两条硬边界（写进代码注释了）#

  1. 只动账本里 Tier ∈ {kill, demand} 且当前实际存在的匹配项。 账本外的一律不管。
  2. 没有删除动作。 只有「禁用 / 恢复」两种写操作。删注册表项不在能力范围内——

删错一个就再也回不来了，而收益是零。

5.3 【工具化时才发现】注册表与计划任务是两个命名空间#

写守卫时第一版把它们放进同一个池子查，结果：计划任务
\GoogleUser\GoogleUpdater\GoogleUpdaterTaskUser156.0.8067.0{5554A084-...}
与注册表值 GoogleUpdaterTaskUser156.0.8067.0 共享一段子串，
于是任务条目把注册表项错误命中，报告里凭空多出 4 条漂移。

必须分来源处理：注册表侧走 $actual 快照 + 首字节比对，任务侧走 Get-ScheduledTask 的 .State。
修正后守卫报出 11 项漂移，与 apply 的 11 项计划完全一致（7 Run + 4 Task）——两份工具互相印证。

6.1 P0 的诚实局限：拿到的是稳态，不是登录波#

改前基线（logon-wave-before-20260930-102839.json）记录了 16 个被关注进程存活：
msedge ×2、OneDrive ×2、PixPin。Chrome 当时没在跑（只有 Edge），更新器进程早已退出。

但这是在会话中途测的稳态，不是登录瞬间的波。 原因是顺序问题：
测量必须紧贴登录时刻，而 P3 一旦执行，下次登录就已经是「改后」状态了——
登录波的 before 数据已经取不回来了。

所以 P0/P3 的结论要分开看：

可比不可比
进程存活与否（Edge / OneDrive / PixPin 改后是否还在）——这是本方案的核心问题，有效登录波期间的 CPU% 与磁盘 IO——before 是稳态、after 是波峰，不可比

若必须要登录波的 before/after 对照，唯一诚实的办法是：
回退 → 在登录时刻挂一个采样任务取 before 波 → 再执行 P3 → 下次登录取 after 波 → 摘掉采样任务。
代价是两次重启 + 一个临时登录任务（本方案正在减少自启，临时加一个采样任务有点讽刺，但它是拿到数据的唯一途径）。
当前不做——「进程是否还在自启」已经能回答本方案要回答的问题。

6.3 【执行时才发现】根路径计划任务：不能用 Split('\',2)#

\OneDrive Startup Task-S-1-5-21-...-1001 是根路径任务——去掉开头的 \ 之后整串里再没有 \。
原写法 TrimStart('\').Split('\',2) 只切出 1 个元素，取 $parts[1] 得到 null，
Disable-ScheduledTask 报「参数为 Null 或空」。这是静默漏项的典型：报错被捕获后继续，
汇总行只显示「成功 10，失败 1」，很容易被当成偶发而不追。

修法：按最后一个 \ 切，切点之前补回尾部 \：

\OneDrive Startup Task-S-...            → Path=[\]  Name=[OneDrive Startup Task-S-...]
\GoogleUser\GoogleUpdater\GoogleUpd...  → Path=[\GoogleUser\GoogleUpdater\]  Name=[GoogleUpd...]

apply / restore / guard 三处同一个 bug，已一并修掉。

6.4 【执行时才发现】可重入的 apply 必须累积存档原值#

第一次执行失败 1 项后要重跑。若不处理，重跑会把「已禁用」当原值存进新存档，
于是 restore 恢复不回启用态——回滚能力被静默废掉，而回滚是本方案的最后一道保险。

修法：写新存档前先扫全部历史 autostart-backup-*.json，同名项沿用最早的原始值。
本次实测生效：重跑时提示「找到 11 项历史存档，将沿用其原值」，新存档里 7 项 Run 记录的是
02-...（真原值）而非当前的 03-...。

同时加了幂等：已是目标态的项直接跳过（本次「已是目标态跳过 10 项」），不重复写、不污染新存档。

6.5 P5 已上线：开机自动跑，不需要人管（2026-09-30 11:5x）#

按需求「重启后不用跑」，守卫调度已注册并实测触发验证：

两条任务故意是不同模式，理由：
Logon+5min 是最可能发现漂移的时刻（各更新器刚跑完），但也是用户正要开始干活的时刻——
那时只报不动，把写操作放到凌晨。发现要快，动手续要静。
代价是漂移最多存在 24h；要登录即修就 -Install -FixAtLogon 重装（一个参数）。

延迟取 5min 而不是 3s：+3s 时各更新器还没跑完，巡检必然看不到它们将要做的改动，白跑一趟。
这正是 PixPin 现在是 PT3S 的同一个教训。

两条路径都实测触发过（不是只看注册成功）：手动 Start-ScheduledTask 各跑一次，
日志分别增长 367 B / 301 B，AUTO-FIX 那次在 0 漂移时正确地什么都没改。

日志：autostart\guard-log-<年月>.log，追加写。追加而非覆盖的理由——
守卫的价值恰恰在于「历史上漂移过几次」这件事被记下来。

6.6 【必须记账】守卫本身就是我新增的一个自启项#

本方案的目标是减少登录波里的项，而 P5 往回加了 1 个：一个 Logon+5min 触发的
隐藏 PowerShell 进程。这是自相矛盾的一处，必须写明而不是藏起来。

取舍是划算的，但要诚实对比：

6.7 【执行时才发现】批量正则改脚本会改到函数自己#

给守卫加日志时，用正则把所有 Write-Host 批量替换成 Write-Line 。
这条正则同时命中了新写的 Write-Line 函数体内部那一句 ——
函数变成了自己调自己，运行直接 CallDepthOverflow，且因为在
Start-Job 里而表现为「脚本卡住不动」而不是干脆报错。

修法：那一句必须回到 Write-Host；并在函数里留注释说明为什么。
教训：批量改脚本后必须回看被改函数自己的定义——
正则改的是文本，不理解「这一行是实现，不是调用」。

7. 稳定性加固（2026-09-30 14:3x）#

前面五节把「功能对不对」做完了。这一节只回答一件事：它坏了你怎么知道。

7.1 最坏的一种失效：守卫崩了却不留痕#

实测（不是推演）：把账本移走再跑守卫——
崩在 throw "账本不存在"，而日志写在函数末尾的正常路径上，一个字都没写。

这是最坏的组合：守卫坏了，而它的存在证据（没有漂移记录）与「一切正常」完全无法区分。

修法：整个运行体包进 try / catch / finally，日志写在 finally。
现在四种退出路径——正常、无漂移、已修正、崩溃——全部留痕，崩溃记录长这样：

===== 2026-09-30 14:18:19  模式=READ-ONLY  结局=崩溃(账本不存在：…先跑 scan_autostart.ps1 重建)  符合=0  漂移=0  …  =====
  !! 守卫异常终止：账本不存在：…
  !! 本次未做任何修正。若是被禁的项复活了，它们会一直留在复活状态。

日志上限 2MB 自动轮转一份：日志无上限的话一年后近万行，
Add-Content 每次都要重开一个越来越大的文件。

7.2 心跳：守卫死了必须能被发现#

光有日志不够——没人会去看日志。所以 manage_guard_task.ps1 -Action Status 做四类判据：

判据阈值为什么要它
logon 任务上次运行 > 7 天超过一周没登录过机器，属正常
daily 任务上次运行 > 2.4 天它本该每天 03:17 跑一次；2.4 天没跑 = 死了
LastTaskResult≠ 0任务跑过但失败
回退存档缺失 / 0 条目 / 解析失败它是整个方案唯一的退路。备份坏了而你还不知道 = 禁用成功但不可撤销
账本缺失守卫会崩溃

误报比不报更糟——会训练你忽略红色。所以安装后有 3 天宽限期：
重新注册任务必然把 LastRunTime 清成「从未运行」，那是注册动作的副作用而非守卫坏了，
宽限期内显示黄色「刚安装待首跑」而不是红色。安装时刻记在 guard-installed.txt。
（这条是在实测中真出现过一次误报后加的。）

7.3 【稳定性加固时才发现】写在脚本内部的 BOM 自检是无效代码#

先说清楚触发场景：.ps1 缺 UTF-8 BOM 时，PowerShell 5.1 按 ANSI(GBK) 解码，
中文被破坏、字符串终止符也被破坏 → 整文件 ParserError。

关键在于：PowerShell 在执行任何语句之前先解析整个文件。
于是「脚本内部检查自己有没有 BOM」检查的是一个永远不会执行到的位置。
实测：剥掉 BOM 后 ParseError 报在第 1 行，而我写在第 22 行的自检根本没机会跑。

已把那 5 处自检全部撤除（留着就是误导性的死代码），改为独立诊断器
autostart\check_bom.ps1，挂在菜单 [c]：

  • 它自己必须是纯 ASCII 且无 BOM——否则它也会被同样的机制打死。

（第一版我给它写了中文注释，它立刻把自己判成 FAIL。改成 0 个非 ASCII 字符。）

  • 诊断路径不能依赖被诊断对象：菜单 .bat 是纯 ASCII，

所以即使 7 个中文脚本全部烂掉，从菜单调它仍然能给出答案。已实测验证。

  • 只管自己的文件：仓库里另有 9 个历史 .bat 有 LF-only 等问题，

但那是别人的脚本。一个对无关文件乱报的检查器会被无视，
所以按 ASCII 标记 Autostart Manager 识别归属，其余报「skipped」。

判定规则（实测得出）：.ps1 含 CJK → 必须有 BOM；.ps1 纯 ASCII → BOM 可选；
.bat → 必须无 BOM + 必须 CRLF + 必须无 CJK。

7.4 【稳定性加固时才发现】"{$($x)} 字面量" 不插值#

"{$([int]$age.TotalDays)} 天前" 在本机 PowerShell 里原样输出 {0} 天前。
它偏偏出现在「报告守卫是否还活着」那行上——
也就是稳定性告警本身显示错了。已改为先算进变量再用 -f；并全仓扫过，只此一处。

安静的显示错误比崩溃更危险：崩溃你立刻知道，错误的「一切正常」你不会去看。

8.2 【关键】「有没有窗口」不是判据，「是否被需要」我判不出来#

初版判据是「无窗口 + CPU 不涨 + 够大 = 闲置可回收」。实测两次连续运行给出互相矛盾的结果：
msedgewebview2 / Weixin 一轮被判孤儿、下一轮变 busy。

错因：沿 PPID 上溯最终总会走到 wininit.exe / svchost.exe，而它们的父 PID 必然查不到
（系统启动时就没有父）。于是「祖先的父死了」被当成「我是孤儿」——
clash-verge.exe 自己活得好好的（有窗口、正在跑你的代理），却被算成「根的父已退出」。

而且在 Electron/Chromium 树上「孤儿」这个概念根本不成立：启动器派生子进程后就退出
（msedge 浏览器进程 44324 活着，它的父 51432 早退了），
按「父死了就是孤儿」会把一个正常浏览器判成垃圾。

具体差点造成的伤害（这就是为什么要实测）：

若按初版自动回收后果
msedgewebview2 423MB根是 clash-verge.exe —— 当场断网
WeChatAppEx 435MB根是 Weixin.exe —— 微信小程序崩掉
WorkBuddy 440MB与 WorkBuddyAI 同产品家族，后者有窗口在用

而 quark 在第一轮审计里还是「0 窗口」，第二轮变成「1 窗口可见」——
你当时正开着它。窗口检查救了一次，但下一次就未必。

因此改成诚实的四类判定（能确定的只有这些）：

判定依据能否自动处置
in-use有可见窗口否
busy采样期 CPU 增量 ≥ 0.5s否
never-touch硬编码名单：Defender / 安全中心 / ToDesk / dwm / explorer / 系统壳永不
undecided账本里是 need-confirm / keep / delay否——等人拍板
unknown-candidate无窗口 + 不忙 + ≥100MB，但看不出是否还需要否，必须点名

unknown-candidate 的措辞是刻意的：不说「闲置」，说「无法判定是否还需要」。
并删掉了 -All 一键全关——判据既然不可靠，批量自动关闭必然误伤。
关闭必须 -Targets 显式点名 + 交互输入 YES 二次确认。

8.3 账本同时约束启动期与运行期#

WorkBuddy.exe 有 15 个渲染进程占 440MB，账本里 WorkBuddy 是 need-confirm（Run 项仍启用）。
若运行期不看账本，就会替人做决定把它的渲染进程杀掉。现在账本说「人还没决定」的进程，
运行期也不碰（undecided 档）——两个时期共用一个判断源。

唯一摆动的是 msedgewebview2 在 busy 与 unknown-candidate 之间，
因其 CPU 增量在 0.54–0.63s 之间跨过 0.5s 阈值——这是诚实的活动度差异，不是结构性误判。

WeChatAppEx 435MB、msedge 320MB、copilotapp 115MB、OneDrive 112MB。
本轮一个都没关——判据既已被证伪，就不该由我替你决定关哪个。

9.1 两个编码坑（都已踩过并修好）#

① .ps1 必须存 UTF-8 with BOM。
PowerShell 5.1 按 ANSI(GBK) 读无 BOM 的 .ps1，中文规则表会被静默解码破坏成语法错误。
扫描器首次运行就是这样炸的。脚本已加 BOM 自检——缺 BOM 直接 throw，不允许静默跑出错误结果。
apply / restore / guard / measure 同样必须带 BOM。

② 菜单 .bat 必须纯 ASCII，且不能用 chcp。
cmd.exe 是逐字节边执行边读 .bat 的，中途 chcp 65001 会让后续字节用新代码页解码、
已解析的部分用旧的——实测直接把菜单解析撕碎（某一行被当成命令执行）。
所以菜单文本全英文，中文交给各自设好 OutputEncoding 的 .ps1。
另：.bat 必须 CRLF 换行（LF-only 会让 echo 被截成 ho），且存 UTF-8 无 BOM
（有 BOM 会被 cmd 当普通字符打印）。

9.2 与既有脚本的关系#

Scripts\maintenance\启动项优化.bat 早于本方案存在，且从未真正禁过任何一项：
它 reg export 备份了 Run 键（这部分有价值，保留），随后生成一份 markdown 清单，
内容是 Spotify / Discord / Steam 之类的通用样板（与这台机器无关），
最后 echo 提示「请打开任务管理器手动禁用」。本方案取代它的「分析 + 清单」职责。

10. 复现#

# 只读盘点
& 'D:\Portable\Scripts\maintenance\autostart\scan_autostart.ps1'

# 某一项当前的启用字节（HKCU 是 02/03，HKLM 是 06/07）
(Get-ItemProperty 'HKCU:\Software\Microsoft\Windows\CurrentVersion\Explorer\StartupApproved\Run').
  PSObject.Properties | Where-Object Name -notlike 'PS*' |
  ForEach-Object { "$($_.Name) : $([BitConverter]::ToString($_.Value[0..1]))" }

# 登录触发的计划任务
Get-ScheduledTask | Where-Object TaskPath -notlike '\Microsoft\*' |
  ForEach-Object { "$($_.TaskPath)$($_.TaskName) :: " +
    (($_.Triggers | ForEach-Object { $_.CimClass.CimClassName }) -join '+') }

# 自动启动的第三方服务
Get-CimInstance Win32_Service |
  Where-Object { $_.StartMode -eq 'Auto' -and $_.PathName -notmatch '^[Cc]:\\Windows' } |
  Select-Object Name, State, PathName

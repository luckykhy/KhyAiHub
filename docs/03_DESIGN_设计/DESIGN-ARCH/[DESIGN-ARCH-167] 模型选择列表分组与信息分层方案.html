[DESIGN-ARCH-167] 模型选择列表分组与信息分层方案#

隶属：本文属 TUI 设计族（总纲 [DESIGN-ARCH-122]）；规则冲突一律以 [DESIGN-ARCH-102] Khy TUI 统一规则手册 为准。

定位：本文管 /model 选择列表（ModelPicker）的信息架构——「哪些条目是一家的、每行哪段是主信息哪段是次信息」。它不管：哪些模型有资格进列表（那是 [DESIGN-ARCH-100] 模型列表真值校验与过滤规范 的射程）、列表项的语义锚点（ccMessageProjection）、CLI（非 TUI）命令输出的层次化（[DESIGN-ARCH-159]）。

状态：已落地（2026-10-01）。改动 A/B 已落进 services/，并覆盖两个消费表面（TUI ModelPicker 与经典 REPL /model）；分组与分层语义由共享叶子 cli/modelChoiceGrouping.js 单点给出（否则就是第二真源）。裁决记录见 §12。

取证时间：初稿 2026-09-29；落地与真数据复核 2026-09-30 ~ 2026-10-01（实测数字均附可复跑的命令）。

0. 一句话结论#

用户说「列表划分不够清楚」，病根不在渲染层缺分组行，而在数据层把分组维度丢了：

gatewayModelChoices.js 的外层循环 for (const s of enabledAdapters)（:525）本来就是分组循环，但它在拼 name 字符串时（:576）把分组降级成了一个 dim 后缀 (执行:${s.name}/${s.type})（:574）——分组的语义在这行代码上被丢掉了，选择器拿到的选项对象只有 {disabled, externalAgent, name, value} 四个字段，没有任何分组字段。

于是 49 个模型只能平铺，而「谁和谁是一家的」被塞进每行末尾的括号里；同时每行内部六段信息（状态 / 模型名 / 能力 / 来源 / 通道 / 延迟）没有一列对齐，模型名被推到第 20 列开外。

本方案两个改动，都不增加一帧高度（实测帧高与改前逐档相等）：

#改动落点实测收益
A分组标题行（只进渲染维度，不进光标维度）ModelPicker.js + 选项对象加 group 字段页内出现 ── OpenCode Zen · 18 个 ──；帧高零增长
B行内信息分层（主信息靠左 / 次信息右对齐成一列）ModelPicker.js + wrapCell.js 加 padCell长标签截断率 10/10 → 0/10（80×24 真数据）

两个由真数据 A/B 逼出来的补充（都不是初稿想到的，见 §11）：

  • 同一套语义必须覆盖两个表面：ModelPicker（ink）与经典 REPL /model（inquirer）吃的是同一份 modelChoices，但只有前者被治过 ⇒ 经典路径仍是平铺，宽度中位 91 列（80 列终端下每行折 2 行）。已抽共享叶子一并治（§12-Q12）。
  • Auto 行只留 ★ Auto + 预览：80×24 真帧里全表只剩这 1 行被 … 截断，而切掉的恰好是最有信息量的预览，17 字样板文反而完整 ⇒ 说明让位给预览（§12-Q11）。

3. 设计公理（不可让渡）#

#公理理由

4. 设计#

4.1 改动 A：分组标题行（渲染维度）#

分组与分层的纯函数（落地时已抽到共享叶子 cli/modelChoiceGrouping.js —— 两个消费表面共用一份，零 require、零 IO）：

// 模型条目 → 渲染条目（在组边界插入标题行）
buildEntries(models, query) -> [
  { kind:'section', name, count, meta } | { kind:'model', mi, choice }, ...
]
// 大小写折叠后的组键。**只作比较键** —— 标题名仍取 `groupKeyOf` 的首现原拼写
groupFoldOf(choice) -> string
// 按组键**首现序**做稳定归并（纯置换：不丢 / 不重 / 组内保序 / 组间保持首现相对顺序）
stableGroupOrder(models) -> models'
// 渲染条目 → 上屏的两段文本（主信息 / 次信息）；孤儿段的 groupMeta 回落也在这里
layeredTextOf(entry) -> { primary, secondary }
// 数字键与屏幕序号同源的那座桥（窗口内第 1..9 个**模型行**的条目下标）
digitTargets(entries, start, end) / digitIndexOf(entries, start, end, i) / entryIndexOfModel(entries, mi)

为什么必须抽成叶子：经典 REPL /model 与 TUI 吃的是同一份 modelChoices（§12-Q12）。若两边各写一份分组逻辑，就是第二真源——一处改了另一处静默漂移。放 cli/ 根下而不是 cli/tui/ 下，是因为 cli/handlers/** 不得反向依赖 cli/tui/**（分层倒置，archDebtScan 的 R1）。

三个关键点：

  1. filtered（模型维度）语义一字不变；它外面再套一层显示序：shown = 浏览态 ? stableGroupOrder(filtered) : filtered，entries = buildEntries(shown, query) 供渲染。⚠ 引入 shown 的那一刻，所有依赖模型下标的路径必须一次全部改绑（cursor / 数字键 / choose / initialCursor / （n/N） 分母）—— 漏一处就重现「屏幕上第 n 行 ≠ 按 n 选中的模型」。搜索态不归并（结果已按相关度排好，再按组归并会把相关度打散）。
  2. pageSize 数的是条目（entries.length）⇒ 标题行占额度，帧高账本与改前同一套算式：2(边框) + header + [搜索回声] + footer + pageSize。没有任何一行游离在账外（实测六档逐档相等，§9）。
  3. 数字键与序号同源：useInput 里 digitTargets(entries, start, end)[n-1] → 取 entries[ei].mi → setCursor(mi)；渲染里 digitIndexOf(...) 写「n.」。这是对旧版「两处各自推导」的收口（ModelPicker.js:227-231 与 :171-175 的注释记着旧版因此出过「按数字跳到别的模型」）。
  4. row === index 不变式：光标 / 数字键 / choose / （n/N） 活在模型下标维度；标题行只进渲染维度。判据不能看 ❯ 的位置（高亮走 e.mi === cursor，而 e.mi 已在显示序，绑错数组时 ❯ 看起来照样对）—— 只能看 onResolve 拿到的 value（§12-Q10）。

单模型组不画标题（MIN_GROUP_FOR_SECTION = 2）：行内标签已自证「它是谁家的」，标题是纯开销。这条同时给标题行数封了顶——每个画标题的组至少 2 个模型 ⇒ 页内标题行 ≤ 页内模型行（最坏 1:1，实测 80×24 为 2:10）。没有这条，49 个单模型组能画出 49 行标题、0 个模型。

4.3 标题行行数上界（可证）#

设页内模型行 $m$、标题行 $s$。每个标题行属于一个「≥2 个模型的组」；页内出现的标题行对应的组，其首个模型必在同一页内（标题行紧邻其首模型之前）。最坏情况是页首恰好落在多个组的边界：

$$s \le m \quad\Rightarrow\quad \text{页内条目} = m + s \le 2m$$

即标题行最多占掉半页。实测 80×24：$m=10, s=2$。代价如实写在这里：页内可见模型数从 12 降到 10（−17%），换来的是「一眼看出分组」。这是本方案唯一的负面读数，不粉饰。

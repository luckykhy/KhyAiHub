[DESIGN-ARCH-180] 驻留资源提示判据错配修复方案#

隶属：启动性能族（[DESIGN-ARCH-178] 的直接后续）；运行时可观测族（runtimeResourceProbe）
状态：已落地（A + B，2026-10-04；偏离见 §12） · 日期：2026-10-04 · 编号：[DESIGN-ARCH-180] · 落点目录：docs/03_DESIGN_设计/
证据基准：2026-10-04 本机实测（khy doctor 短进程 + node-pty 真实 TUI 会话 + 用户截图）
与 178 号的关系：178 修的是「首帧 44s」的性能病灶；本方案修的是178 留下的判据被误用到稳态
所产生的常驻告警。178 的 P0 已落地（实测 981 模块，达标），本方案不改 178 的任何判据。

0. 一句话#

启动期那条「资源 已统计本会话进程…超出判据」不是资源失控，是判据错配：
BUDGET_MODULES = 1000 抄自 [DESIGN-ARCH-178] §7 的首帧前验收目标，
而 runtimeResourceProbe 在会话稳态测量 ⇒ 每次启动必然超标 —— 一条永远为真的告警。
本方案 = 判据按测量时点分档（A）+ 启动提示按受众分流并补判据明细（B）。

1. 现状证据#

1.1 提示的发出链（file:line）#

环节位置说明
文案生成runtime/node/backend/src/services/runtimeResourceProbe.js:268 buildResidencyNotice()无超标项时返回 null（静默是常态）
触发runtime/node/backend/src/bootstrap/prefetch.js:169 emitFootprintNotice()轻量模式 runtimeFootprintNotice(+3.5s)；完整模式 cleanupService(+3s)
判据runtimeResourceProbe.js:26 BUDGET_MODULES = 1000；:41-42 HANDLE_BUDGET_TIMERS = 20 / HANDLE_BUDGET_WATCHERS = 2单一真源
另一消费面runtime/node/backend/src/cli/handlers/init.js:1216 _residentResourceChecks()khy doctor 的「驻留资源」段，与启动提示共用 assessResidency（刻意「同一把尺」）

1.2 判据的出处：它是「首帧目标」，不是「稳态基线」#

[DESIGN-ARCH-178] §7 验收表第 2 条：

#判据门槛
2V1 模块数≤ 1000（现状 1523）

该判据的探针跑到 require('./tui/app.js') 停手 —— 量的是首帧前的 require.cache。
178 的 P0（redis 顶层副作用改惰性）已于 2026-10-04 落地，实测 V1 = 981，达标。

1.3 实测：判据与测量时点错配#

场景测量时点模块数活体资源
perf 探针（178 §7）首帧前（require('./tui/app.js')）981 ✓—
node bin/khy.js doctor（本机，短进程）启动后稳态1084 ⚠10 项（定时器 1 · 监视 0）✓
真实 TUI 会话（node-pty，本机）REPL ready 后 +3s2079 ⚠机器余量一并超标
用户截图（交互会话）会话期1475 ⚠91 项 ⚠

⇒ 同一把尺量两个时点。稳态必然包含首帧之后懒加载进来的工具注册表 / 网关 / ink 全树
（[DESIGN-ARCH-012] 工具延迟加载、178 §3.3 的 setImmediate 预热）⇒ 恒超标。

runtimeResourceProbe.js:262-263 自己的注释写着：
「a boot line that always fires trains everyone to ignore it」
（每帧都响的仪表会让人学会忽略它）—— 而它正是那条。

1.4 附带缺陷：提示把判据明细丢掉了#

buildResidencyNotice:271：

const readings = over.map((f) => `${f.label} ${f.detail.split('（')[0].trim()}`).join(' · ');

detail 的全角括号里装的正是判据（（上限 1000） / （定时器 X · 文件监视 Y）），
被 split('（')[0] 整段丢掉 ⇒ 用户看到「活体资源 91 项」却看不出是哪个判据超。
这是截图无法自解的直接原因。

1.5 现状：零文档背书、零守卫#

本方案之前，runtimeResourceProbe 在 docs/ 与 scripts/ 全无引用；
BUDGET_MODULES 的 1000 只活在代码注释里，没有任何棘轮守着它。

2. 设计公理#

#公理依据
A1判据必须与测量时点同源首帧预算不能量稳态，否则永远是噪声（§1.3）
A2会话提示只报「用户可处置」的项模块图的处置是「改代码」，不是会话内动作；对用户是噪声
A3同一把尺：doctor 与启动提示的判定不得分叉runtimeResourceProbe.js:165-167 的既有设计意图
A4强度与「有可行解」同步低余量机器上用户没有回退手段 ⇒ 不升 error（本仓既有公理）

3. 与既有机制的边界#

既有件管什么本方案做什么边界
[DESIGN-ARCH-178] §7首帧前模块数 ≤1000 的验收判据不动；只把它登记为 frame 档的语义真源178 管首帧，本方案管稳态
[DESIGN-ARCH-062] 生命周期边界后台常驻 vs 按需加载的层级声明（serviceLifecyclePolicy.js）不动；句柄超标的 hint 仍指向它062 管「谁该常驻」，本方案管「超标了怎么说」
khy doctor「驻留资源」段完整驻留体检（含磁盘树走查）不动；只让它的模块判据按 cli 档判定仍是同一份 assessResidency
check-tui-gates（MAX_GATES=227）KHY_* 门控棘轮零新增门控（A4：不引入开关）—

4. 目标形态#

4.1 A —— 判据按测量时点分档#

// runtimeResourceProbe.js —— 模块图预算按测量时点分档（单一真源）
const MODULE_BUDGET = Object.freeze({
  frame: 1000, // 首帧前；[DESIGN-ARCH-178] §7 验收判据，只有 perf 探针消费
  cli: 1200,   // 短进程命令（khy doctor 等）实测 1084，留 ~10% 余量
  tui: 2200,   // 交互会话实测 2079，留 ~6% 余量
});
const DEFAULT_PHASE = 'tui'; // fail-open：忘传 phase 时取最宽松档，不制造噪声
  • collectRuntimeCensus(opts) 接受 opts.phase，把对应预算写进 snap.modules.budget
  • 调用点显式声明时点：prefetch.js:169 → { phase: 'tui' }；init.js:1218 → { phase: 'cli' }
  • BUDGET_MODULES 保留为 MODULE_BUDGET.frame 的兼容别名（既有测试引用它）

棘轮纪律：三个值只许下调。用设计锁测试钉住（要改大必须同时改测试，属有意动作）。

4.2 B —— 启动提示受众分流 + 补判据明细#

// 模块图的处置是「改代码」，属开发者向；会话提示只报用户可处置的项。
// 它仍在 khy doctor 的「驻留资源」段完整可见（同一把尺，受众不同）。
const SESSION_AUDIENCE = new Set(['memory', 'handles', 'machine', 'children', 'dataHome']);
const over = assessResidency(snap).filter((f) => f.exceeded && SESSION_AUDIENCE.has(f.id));

每个 finding 新增 reading 字段（短串，带分子/分母）：

findingreading
memoryRSS 240/220 MB
handles定时器 22/20 · 监视 3/2
machine空闲 12%/≥15%
dataHome509/500 MB

⇒ 提示从 …：活体句柄 活体资源 91 项，均超出判据。
变为 …：活体句柄 定时器 22/20 · 监视 3/2，超出判据。

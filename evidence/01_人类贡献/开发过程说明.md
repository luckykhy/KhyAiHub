# 开发过程说明（C-E1 / C-X1）

这份文件回答「**这个人到底是怎么做这个软件的**」，并给出每个环节的原始存证位置。
它不叙述功能，只叙述过程——登记审查关心的正是过程。

## 一、开发形态：单人 + 编码智能体，按「三模态契约」推进

本仓把工程过程写成了可校验的规则（`AGENTS.md` 工程规则 5/6/7 = `RUNTIME-007/008/009`），
每一次改动按主模态留下不同存证，全部落在 `.khy/feedback/<任务-id>/`：

| 模态 | 规则 | 必须留下的存证 | 实测数量 |
|---|---|---|---|
| **修复**（FIX） | 规则 5 修复先复现 | `complaint.md` → `repro-before.txt` → `differential.md` → `repro-after.txt` | 主诉 146 ｜ 复现前 171 ｜ 鉴别诊断 114 ｜ 复诊 149 |
| **新增**（BUILD） | 规则 6 新增先提问 | `requirement-5q.md`（谁用/何时用/替代做法/成功长什么样/不做会怎样，每条带 `source: 用户原话`） | 21 |
| **删除**（DELETE） | 规则 7 删除先报部位 | `scrub-plan.md` + **可执行**的 `rollback.txt` | 回滚 47 ｜ 模态声明 22 |
| 合计任务目录 | — | — | **245**（`ls .khy/feedback \| wc -l` 得 247 行，其中 2 项为散文件） |

**「复现修复往返数」= 141**：同一目录里既有 `repro-before.txt` 又有 `repro-after.txt`，
即「先看到病、改完再跑同一条命令复诊」完整走通的次数。存证活跃跨度 10 天（2026-09-18 → 09-27）。

> 为什么这一节对软著有用：它证明代码不是「一键生成后没看过」。
> 每一次修复都有病案、有候选病因、有改前改后的真实输出。

复算：
```bash
find .khy/feedback -maxdepth 2 -type f | sed 's#.*/##' | sort | uniq -c
ls .khy/feedback | wc -l
```

## 四、进入登记材料的代码，人怎么解释（C-X1 / C-X2）

判据是**可解释性**，不是生成方式。本仓的可解释性由三样东西支撑：

1. **层级单一真源** `[DESIGN-LAY-005]`：L0 `kernel/` → L6 `tools/` 的依赖方向由
   `npm run check:layout` 强制，任何一个模块「凭什么能引用另一个」有规则可查。
2. **规则绑定层** `scripts/ruleguard/`：94 条规则登记在 `RULES-REGISTRY.json`，
   82 条有执行器；`npm run rules:apply -- <文件>` 可直接问「改这个文件适用哪些规则」。
3. **设计文档** `docs/03_DESIGN_设计/` 234 份：机制、取舍、被否决的方案都留了字。
   索引见 `../02_独创性/设计决策.md`。

第三方与生成物**逐文件剔除**并公开明细（`../02_独创性/原创代码规模.md`）：
kernel 手写层 33,866 行，另 3,912 行 vendor 被排除在原创口径之外。

## 五、验收：改完跑什么

```bash
npm run rules:gate            # PR 档：按登记表派生门成员，逐条执行
npm run check:layout          # 顶层目录层级与依赖方向
npm run check:copyright       # 本底档齐件 + 图片非空
node scripts/ci/check-agent-rules.js --changed   # 四条工程红线
```

`node services/backend/bin/khy.js hq verify` 应报 `0 error / 0 warning`。

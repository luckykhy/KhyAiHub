发布记录（C-MAT2 软件名称与版本稳定）#

本文件只写仓库里可核到的发布事实。软著登记表的「版本号」栏现行值是 V1.2.0，
取自本文件的 G1 发布轨道现值（人明示「先沿用现在的，只有我说修改了才修改」，见 决策记录.md D-名2）——
两者刻意相等，因此截图里的版本串与申请表天然一致，无需修图。
但登记值本身的真源仍是 [MGMT-OTHER-006] §一，不是本文件；本文件若与它冲突，以 [MGMT-OTHER-006] 为准。

⚠ 1.2.0 尚未打 tag（实测最新为 v1.1.15，见 §二）。登记口径把「首次发表日期」锚在
首个 wheel 的上传日（[MGMT-OTHER-006] §一），不是 tag；发表状态与版本号是两个独立字段，
官方并无「首次登记必须 V1.0」的要求。故此处只登记一个可核事实：版本号栏与 tag 轨道当前不同步，
若要在递交前补发 v1.2.0，走 PROCESS-005，由人决定。

一、三条独立版本轨道（真源 = scripts/ci/check-version-sync.js 的 specs 数组）#

轨道含义当前值校验源
G1主包 khy-os（pip + npm 渠道）1.2.0pyproject.toml、packaging/npm/package.json、services/backend/package.json、packaging/modules/modules.json
G2ai-backend 生态（随 wheel 捆绑发布）1.6.5services/ai-backend/package.json、platform/packages/shared/package.json
G3浏览器 UI 共享包及其消费者0.1.0platform/packages/ui-shared/package.json 与两个前端的依赖声明

G1/G2 刻意不同（1.2.0 vs 1.6.5）：两条发布单元节奏不同，这不是漂移。
规则见 [DESIGN-SEMVER-002]，强制入口：

node scripts/ci/check-version-sync.js     # 组内必须完全一致，组间允许不同

复算：

node -e "console.log(require('./services/backend/package.json').version)"
grep -n '^version' pyproject.toml

三、CHANGELOG 段落（版本段推导的依据）#

grep -n '^## ' CHANGELOG.md
段位置类型
1.2.0CHANGELOG.md:8### Fixed + ### Added → MINOR
1.1.14:53修复段
1.1.12:118修复段
1.1.9:139修复段
1.1.8:241修复段

本仓的版本段是可机判的：### Added → MINOR，### Changed/Removed/Security → MAJOR/MINOR，
仅 ### Fixed → PATCH（[DESIGN-SEMVER-002]）。先写 CHANGELOG 段、再 bump 版本号，
由 changelog-new.js --check 以 pyproject.toml 为锚校验。

四、发布链路（谁自动、谁人工）#

环节触发是否人工点头
写 CHANGELOG 段 → bump 三源版本号人决定发版✅ 人
推 main人执行 commit/push（红线 R1 禁止 AI 自动提交）✅ 人
推 vX.Y.Z tag人执行✅ 人（唯一一次点头）
tag 之后：测试→版本校验→release-gate→构建→签名→SBOM→发包→Release 资产CI 自动❌ 不再人工
Gitee 镜像同步推 main / tag 自动❌

四条硬阻断（check-version-sync、changelog-new --check、release-gate.js、tag 与 pyproject.toml 相等）
禁止改成 continue-on-error。完整规则见 AGENTS.md「何时 bump、推哪里、什么自动触发」与 [DESIGN-SEMVER-002]。

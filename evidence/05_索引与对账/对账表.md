## 二、口径冲突的处理方式（本表的价值所在）

同一件事往往有两个以上口径。本仓的做法是**两个都记、标明口径**，而不是挑一个好看的：

| 议题 | 口径 A | 口径 B | 用法 |
|---|---|---|---|
| 提交数 | `main` 62 | 全分支 920 | `main` 是 2026-09-24 重建的短历史；说「开发过程」用 B，说「当前分支」用 A |
| AI 署名提交 | `main` 0 | 全分支 88（9.6%） | C-M3 的合规判断用 A；治理范围与诚实申报用 B |
| 代码行数 | 累计新增 2,480,083 行（git numstat） | kernel 手写 33,866 行 | 前者含锁文件/生成物/文档，**不可**用作原创性主张；后者才是登记材料建议口径 |
| 版本号 | G1 `1.2.0`（四源一致，仓库发布轨道） | `.ai/hq/PROGRESS.json` 的 `khy_os_version` = `1.1.11`（台账字段滞后） | 日常与守卫以 G1 为准；台账值不引用。**软著登记栏填 `V1.2.0` = G1 现值**（人明示「先沿用现在的」，D-名2），故截图版本串与申请表天然一致、无需修图；代价是登记后版本号只允许增减「V」，见 `[MGMT-OTHER-006]` §三。⚠ `1.2.0` 尚未打 tag（最新 `v1.1.15`） |
| 测量用的 ref | `HEAD`（正常检出时） | `main`（HEAD 未出生时自动退化）/ `--all`（连 main 都没有时） | 采集器把实际 ref 记在 `contribution-metrics.json` → `人类贡献度量.git.测量ref` 与 `测量口径`；两者不一致时必须声明 |

## 四、完整性核对

```bash
node scripts/evidence/build-index.js          # 重生成 证据总清单.json（逐文件 sha256/字节/行数）
node scripts/docs/build_docs_site.js          # 重生成各 md 的 html 孪生
node scripts/evidence/build-index.js          # 再跑一次，让清单记到刚生成的孪生
npm run check:copyright                        # 底档齐件 + 无 0 字节图片
node -e "const l=require('./evidence/05_索引与对账/证据总清单.json');console.log(l.条目数)"
```

**清单追踪 html 孪生，所以顺序有讲究**：`build-index` 自己会重生成 3 份 md，
若在孪生之前跑，孪生就落后一版；上表三步（清单 → 孪生 → 清单）才是收敛顺序。

**自指不入哈希**：`证据总清单.json` 里含自身条目，其 `生成时间` 与 `字节/sha256`
每次重跑必变（实测连跑两次只差这 3 行：第 2、483、484 行）。这是清单的时间戳，
不是被篡改的痕迹——核对图片时按 PNG 条目对，不要按自身条目对。

`证据总清单.json` 里每个 PNG 条目带 `宽/高/sha256`；任何一张被手工替换过，
sha256 与尺寸都会变，与本表 §一 的「16 张」以及两份清单即可对出。

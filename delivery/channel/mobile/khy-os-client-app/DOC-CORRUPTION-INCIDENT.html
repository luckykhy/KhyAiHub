VERIFICATION.md 损坏事故记录（2026-11-14 08:0x）#

发生了什么#

delivery/mobile/khy-os-client-app/VERIFICATION.md 被永久损坏：
1507 个 U+FFFD 替换字符（不可逆），全部中文段落变成 mojibake。
文件仍在原处，但内容不可读。

直接原因#

我在修正章节编号时用了 PowerShell：

$c = Get-Content $p -Raw      # 按 GBK 解码 UTF-8 文件
$c = $c -replace '...', '...' # 字符串替换
Set-Content $p -Value $c -Encoding UTF8   # 把 GBK 误读的文本按 UTF-8 写回

Get-Content/Set-Content 往返一次，每个中文字符被重新编码，字节膨胀
（105KB → 117KB），内容永久损坏。GBK 往返只能救回幸存字节，U+FFFD 无法还原。

为什么这件事特别严重#

  1. 这是本次任务唯一的交付文档，记录了 13 个问题、四条约束核验、五个方法论；
  2. 这个坑，VERIFICATION.md 自己就记着——早前轮次明确写过：

「PowerShell Set-Content/Get-Content 往返编辑含中文的 .md 文件会写成
mojibake，必须用 write/edit 工具」。我不仅没遵守，还在同一天写下了
方法论第六条「让现实当输入，而不是让记忆当输入」——然后转头就用记忆
（「我记得该用 edit」）代替了现实（实际敲的是 Set-Content）；

  1. 该文件从未提交 git（untracked），所以没有版本可回滚。

教训（比前六条都硬）#

「我知道」不等于「我会做」。前六条方法论都在讲这个，但都是在讲
判据/兜底/文档缓存，这一条是我自己被执行端直接击中：

一条写下来的规则，如果没有变成「不可绕过的操作形式」，就等于没有。
我十几轮来一直用 edit/write 工具改这个文件，成功的次数足够多，
让我产生了「我很擅长改它」的错觉——而错觉正是事故的温床。

正确的操作形式应该是：改这个文件只能有一个入口（edit/write 工具），
PowerShell 的 Set-Content 根本不具备写它的能力——就像这个项目里
khy_devcheck.ps1 取代手打 adb 命令一样。

恢复尝试#

  • git 回滚：不可用（文件 untracked）；
  • GBK 往返还原：不可逆（1507 个 U+FFFD）；
  • 从对话历史重建：可行但昂贵——内容绝大部分在上下文里（刚验证 11/12

关键段落仍在），缺「遗留待办」一节与散布的中文。若决定重建，应先用
edit/write 工具，且每写 200 行校验一次关键词。

当前状态#

原文件保留在原地（作为事故现场，不删除——删除会让人以为没发生过）。
本文件是事故记录。重建决策权在用户：重建需要约 20 轮工具调用，
且重建件应当视为「恢复的副本」而非原件。

evidence/ —— 软件著作权登记底档（人类贡献与原创性证据）#

本目录是入库的自留底档：登记被追问「这软件是谁做的、人做了什么、AI 做了什么」时，
这里放着能当场翻出来、且每一条都能在本机重跑验证的答复。

  • 建立依据：[DESIGN-IP-001] C-E4（判据真源）
  • 入库裁决：D-E1（2026-09-28，人工决定本目录进 git、不加进 .gitignore），见 01_人类贡献/决策记录.md
  • 层级登记：[DESIGN-LAY-005] §1.2 —— evidence/ 是证据横切目录
  • 机器校验：npm run check:copyright（缺件 / 空图片会被判 error）

一、本目录的两条铁律#

  1. 不手写数字。 所有度量数字由 scripts/evidence/ 下的采集器从仓库实测得出，

再渲染成文档与图片。任何一份文件里的数字都能用同一条「复算命令」重跑出来；
重跑不一致说明数据漂移，以重跑结果为准并重新生成。

  1. 不摆拍、不隐瞒。 图片分「可作登记材料」与「仅作开发过程证据」两类，

逐张在清单里标注；AI 参与范围、被剔除的第三方代码、含 AI 署名的历史提交，
全部如实写出，不做粉饰。

四、怎么重新生成全套证据#

npm run evidence:all      # 采集 → 生成文档 → 渲染图表 → 采集真实运行截图
npm run check:copyright   # 校验底档齐件、图片非空

分步入口：evidence:collect / evidence:build / evidence:images / evidence:runtime。
采集器不写业务数据，只读仓库与台账；evidence:runtime 跑的是只读命令，
其中 gateway status 一条会对外探测通道连通性并可能触发一次最小模型调用
（即不保证零成本），已在 03_图片/图片证据说明.md §二与 运行截图清单.json（对外探测: true）标注。
（--version / commands / hq status / storage status），不触发任何模型外呼。

五、边界：本目录不是登记材料本身#

登记提交的是源程序前/后各 30 页 + 操作手册 + 申请表。递交件的工作区是
06_申报材料/（仓库内的独立文件夹，不与 docs/ 混放）：那里只放
「将随申请出去的东西」与一份核对表，不放过程证据。
本目录其余部分是被追问时的答复依据，不随申请递交。因此它与登记材料的取舍不同：
这里保留了对己不利的记录（例如全分支仍有 88 条含 AI 署名的历史提交），
如实申报优于事后被问出来。

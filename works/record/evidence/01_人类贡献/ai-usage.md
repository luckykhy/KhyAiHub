# AI 参与范围自述（C-M2 / C-M3）

> 这份文件回答登记时的一个必问：「这个项目用了多少 AI？人做了什么？」
> 口径依据 `[DESIGN-IP-001]` C-M1：**判据是「有没有人的意愿」，不是「有没有用 AI」。**
> 因此下面的自述不试图缩小 AI 的参与比例（那是虚报），而是把**分工**说清楚。

---

## 一、结论先说

| 问题 | 回答 |
|---|---|
| 谁发起这个项目？ | 单人开发者（git 作者唯一：`孔浩原 <2578974124@qq.com>`，`main` 口径 62/62 提交） |
| 写代码用 AI 吗？ | **用，且是主力编码手**。架构与算法方案大量由 AI 提出并实现 |
| 人做了什么？ | 提需求、定优先级、拍板取舍、验收结果、判「这个方案不要」、决定何时停 |
| AI 能自己决定什么？ | 允许：技术方案、模块拆分、算法选择（C-M2 白名单）；禁止：commit/push、改名、删除有文档背书的代码（C-M3 黑名单 + 红线 R1） |
| 结果谁负责？ | 人。所有进入登记的代码由人运行、复现、验收（见 `开发过程说明.md`） |

## 三、AI 署名的历史与治理（对己不利但如实写）

| 口径 | 实测 | 说明 |
|---|---|---|
| `main` 分支含 AI 署名提交 | **0** | C-M3 要求登记口径下提交信息不带 `Co-Authored-By: <AI>` / `Generated with <AI>` |
| 全分支含 AI 署名提交 | **88 / 920（9.6%）** | 历史开发期留下的尾注，存在于未合并/已废弃分支 |

复算（务必带 ref，HEAD 可能正处重建中而未出生）：
```bash
git log main --format='%an <%ae>' | sort | uniq -c     # 62 条，作者唯一
git rev-list --count --all                              # 920
```
| 治理入口 | `npm run strip:ai-attribution`（干跑）→ `:apply` | 一次性清除尾注的维护脚本，人在本地执行 |

`main` 之所以只有 62 条提交而全分支 920 条：`main` 是**被重建的短历史**。
两个口径必须分开引用，不能拿 62 说「开发过程就这么短」，
也不能拿 920 与 62 互相打脸。完整数字与复算命令见 `../04_机器可读/contribution-metrics.json`。

## 四、AI 被禁止做的事（机制强制，不是口头承诺）

| 禁区 | 强制方式 |
|---|---|
| 自动 commit / push | 红线 R1（`PROCESS-001`，P0）；无自动提交路径，提交由人执行 |
| 提交信息带 AI 署名 | C-M3 + `scripts/ci/check-copyright-readiness.js` |
| 静默删除有文档背书的代码 | 规则 7（`RUNTIME-009`）：删除前必须报部位并留可执行回滚；文档背书者拒绝放行 |
| 未复现就「修好」 | 规则 5（`RUNTIME-007`）：缺 `repro-before.txt` 判 error |
| 自作主张加功能 | 规则 6（`RUNTIME-008`）：新增前须答需求五问并落 `requirement-5q.md`，且带 `source: <用户原话>` |
| 默认继承工具权限 | 规则 10（`RUNTIME-010`）：默认拒绝，权力只能被显式授予 |

规则与执行器的对应关系见 `docs/10_规范/registry/RULES-REGISTRY.json`（94 条规则，82 条有执行器）。
